5. **C 逐項調整**：

6. **確認上場**：三個時期實際會用的設定並列，標出哪些是覆寫、哪些是勝利條件填的。

每一列都有狀態標籤：**預設**（跟著模板）、**已覆寫**（玩家選的）、**勝利條件**（替玩家填的）、**模板固定**（只有一個值）。Registry 有、但這個模板目前不提供的選擇畫成灰色「未開放」標籤，它不是按鈕、不能點。

## 2. 「野區入侵」是否真的執行

工具：`tools/owner_preview/diag_invade_v21.mjs`。走正式開局入口，藍方用指定模板，20 個 Seed，觀察開局 90 秒。資料：`diag/invade.json`。

| | v21 野區入侵 | v21 前期野區入侵（m7） | v20 m7 |
|---|---|---|---|
| 設定的入侵機率 | 0.7 | 0.8 | 0.8 |
| 沒觸發 | 7 | 6 | 6 |
| 觸發但沒抵達 | 0 | 0 | 0 |
| 觸發且抵達入侵點（距離 ≤ 6） | 13 | 14 | 14 |
| 打野越過河道中線 | 13/13 | 14/14 | 14/14 |
| 入侵期間對敵方野怪造成傷害的場數 | **0** | **0** | **0** |
| 入侵擊殺合計 | **0** | **0** | **0** |
| `invadeAttempts` 合計 | 13 | 14 | 14 |

因果鏈逐段：

1. **模板 → 解析**：成立。模板的 `invadeChance` 正確進到引擎。
2. **開局判定**：成立。觸發率與設定值相符（13/20、14/20）。
3. **尋路與抵達**：成立。打野一路走到敵方 Buff 房間入口（入侵點），平均在第 30 秒左右到，沒有中途撤退。
4. **到了之後做了什麼**：**什麼都沒做。** 入侵窗只有 35 秒，走過去就用掉約 30 秒；野怪也是第 30 秒才出生。打野在入口站約 5 秒，沒有打任何敵方野怪，窗一結束就走回自家野區。
5. **事件紀錄**：`invadeAttempts` 只代表「開局擲骰中了」，不代表做了任何事。

**結論：會觸發、會走到，但沒有實質的入侵行為。** 27 場觸發（v21 兩個模板）裡，偷到野怪 0 次、入侵擊殺 0 次。

- 這是 **v20 既有行為**，v20 的 m7 逐項相同。入侵窗在 `matchProgression.js:370` 被設成 35 秒，註解寫明「只走前段偵察，不在開局直接穿越到敵方腹地」。
- 所以它算不算 Bug 要看產品定義：照程式註解，它本來就只是偵察；照模板名稱「野區入侵」，玩家會期待偷野或抓人。
- 要讓它名實相符，必須改 `LogicEngine` 或規則數值，屬於模擬語意變更 ⇒ **需要 Owner 核准，本輪沒有動。**

沒有驗的：戰術書裡「打野重心＝入侵」這個選項單獨的效果；紅方（AI）入侵時的情形。

## 3. 開局打 Buff 耗時異常

**結論：是真正的 Bug，可重現，v20 正式站也有。**

工具：`tools/owner_preview/trace_camp_v21.mjs`（逐 tick 追蹤）與 `diag_camp_leash_v21.mjs`（20 個 Seed 統計）。資料：`diag/buff_trace_seed11_v21.txt`、`diag/leash.json`。

### 3.1 現象（Seed 11，紅方打野打自家 Buff）

- 第 40 秒開打。主怪（252 血）4.5 秒就打死。
- 剩下兩隻小怪各 84 血。第一隻也正常打死。
- **最後一隻**：血量打到 8，然後跳回 84；再打到 8，又跳回 84。每 3 秒一輪，從第 48 秒一直重複到觀察結束（第 75 秒）還沒打死。
- 這段時間打野自己從 704 血掉到 475 血。

### 3.2 根因（三條規則互相打架）

1. 打野會走向「最近的那一隻存活野怪」（`_campStandTarget`，`LogicEngine.js:1295`）。
2. 整個野怪營會追著打野移動（`:4589-4601`），而小怪的位置是「營地中心＋固定偏移」，所以營地一追，小怪也跟著移動，打野又繼續追。兩者一起往外漂。
3. 打野離營地出生點超過 7.5（`campLeashRange`）時，營地判定目標離開 ⇒ 進入回營狀態 ⇒ 走回出生點 ⇒ **存活的野怪回滿血、傷害歸屬清空**（`:4570-4587`）。

血量條跳回去是如實顯示，不是畫面同步問題。

### 3.3 影響範圍（20 個 Seed，開局 10 分鐘）

| | v20 | v21 |
|---|---|---|
| 藍方 Buff：發生回滿的場數 | 20/20 | 20/20 |
| 藍方 Buff：回滿次數合計 | 527 | 474 |
| 紅方 Buff：發生回滿的場數 | 20/20 | 18/20 |
| 紅方 Buff：回滿次數合計 | 528 | 562 |
| 藍方 Buff 第一次清完的時刻（中位數） | 95.5 秒 | 95.5 秒 |
| 紅方 Buff 第一次清完的時刻（中位數） | 151.5 秒 | 151.5 秒 |

野怪第 30 秒出生，所以一座 420 血的 Buff 營要打 65 到 120 秒，平均每場每座回滿約 26 次。一般營地（偏移較小）輕微得多（每場不到 1 到 3 次）。

- **不是 v21 造成的。** v20 一樣。打野走向單隻野怪的邏輯是 2026-09-25（v12）加的，脫戰回滿是 2026-07-29 加的，兩者合起來才出問題。
- 紅藍兩側清完時間差很多（95.5 對 151.5 秒），這本身可能是一個側別不對稱的來源，本輪沒有進一步查。

### 3.4 修法（需要 Owner 核准，本輪沒有動）

修它一定要改 `LogicEngine.js`，會改變所有對局的結果 ⇒ 要升模擬版本、重錄 Golden、重測真實性表。候選：

| 做法 | 內容 | 風險 |
|---|---|---|
| A（建議） | 打野的站位目標限制在營地出生點的脫戰半徑內 | 改動最小；只影響打野站位 |
| B | 營地追擊時不離開出生點超過某個距離 | 也會改變野怪打人的範圍 |
| C | 打野還在仇恨範圍內時，回營不回血 | 改變「拖怪」的既有防護 |

這個 Bug 讓打野前兩分鐘幾乎都耗在第一座 Buff 上，會連帶影響抓人節奏與前期經濟。所有已量過的 v20／v21 平衡數字都是在這個 Bug 存在的情況下量的。

## 4. Lag 調查

### 4.1 模擬引擎（`tools/owner_preview/perf_sim_tick_v21.mjs`，5 場完整對局）

| | v20 | v21 |
|---|---|---|
| 每 tick 平均 | 1.50 ms | 1.39 ms |
| p95／p99 | 3.37／5.52 ms | 3.26／5.26 ms |
| 超過 16 ms 的 tick | 4／12,671 | 3／12,088 |

**引擎不是瓶頸，v21 也沒有比 v20 慢。**

### 4.2 瀏覽器（`tools/owner_preview/perf_battle_v21.mjs`，真 GPU：AMD Radeon 內顯，隔離的 Chrome）

| 設定 | 桌機 1× | 桌機 4× | 桌機 4× 近戰 | 390 4× | 4× 主執行緒忙碌 | 4× JS 記憶體 |
|---|---|---|---|---|---|---|
| v21 dev（你之前看的那種） | 60.0 fps | 57.9 fps，卡頓 2 幀，最長 200 ms | 59.3 | 59.3，卡頓 1 幀 | **90.8%** | **205 MB** |
| v21 打包版 | 60.0 | 58.7，卡頓 2 幀，最長 217 ms | 59.5 | 59.4，卡頓 3 幀 | 83.0% | 87 MB |
| v20 打包版 | 60.0 | 59.7，卡頓 0 幀 | 59.9 | 59.4，卡頓 3 幀 | 84.8% | 75 MB |

（卡頓＝單幀超過 50 ms。每段取樣 15 到 20 秒。）

CPU 取樣（dev 模式才分得出來源，4× 導播 20 秒）：three.js 約 43%、React Three Fiber 約 9%、react-dom 約 6%、對戰呈現程式約 7%、**引擎 1.6%**、GC 1.5%。

### 4.3 判讀

- **在乾淨的 Chrome 裡，我沒有重現持續性的 Lag。** 三種設定平均都在 58 到 60 fps。
- v21 與 v20 的差別很小：4× 時 v21 多了 2 幀超過 50 ms 的卡頓（v20 是 0）。只有一次取樣，不能下結論。
- **主執行緒幾乎沒有餘裕**：60 fps 的同時已經忙到 83% 到 91%。瓶頸是 three.js 的渲染提交（CPU 端），不是引擎，也不是 GPU 填充。任何額外負擔都會直接掉幀。
- **dev 模式比打包版重**：JS 記憶體 2.4 倍（205 對 87 MB），主執行緒多忙約 8 個百分點。
- 你試玩時這台電腦有 41 個 Chrome 行程（5.8 GB），認可記憶體用到 22 到 26 GB（上限 27.8 到 30.9 GB），而且當時預覽伺服器就是被記憶體保護停掉的。**最可能的原因是記憶體吃緊加上 dev 模式，但我沒有在那個條件下量過，這是推測。**

### 4.4 可確認的改善

**沒有程式上的效能修改。** 可確認的只有一項：改用打包版預覽（§5 的第二個網址）後，同樣場景的 JS 記憶體從 205 MB 降到 87 MB，主執行緒忙碌從 90.8% 降到 83.0%。幀率在乾淨環境下沒有差別。

沒有降低任何畫質設定。

### 手機為什麼還開不了

這台電腦的 Wi-Fi 連的是「vivo X80 2」（手機熱點），所以手機和電腦在同一個網段。但是：

- Windows 把這個網路歸類為「公用」。
- 防火牆有兩條明確的規則：**封鎖 node.exe 在公用網路上的所有連入**。
- 我這個工作階段不是系統管理員，改不了；而且改防火牆應該由你決定。

我沒有改用別的伺服器程式去繞過這條規則。**所以手機網址沒有經過 Android 實測。**

### 最小方案（要你核准並用系統管理員身分執行）

```
Set-NetConnectionProfile -InterfaceAlias 'Wi-Fi' -NetworkCategory Private
New-NetFirewallRule -DisplayName 'ESMO v21 phone preview 5641' -Direction Inbound -Program 'C:\Program Files\nodejs\node.exe' -Protocol TCP -LocalPort 5641 -RemoteAddress LocalSubnet -Profile Private -Action Allow
```

只開 5641 這一個 port、只允許同網段、只在「私人」網路生效。看完後復原：

```
Remove-NetFirewallRule -DisplayName 'ESMO v21 phone preview 5641'
Set-NetConnectionProfile -InterfaceAlias 'Wi-Fi' -NetworkCategory Public
```

跨網路 HTTPS（Tailscale Serve）：這台電腦沒有安裝 Tailscale，要用的話需要你在電腦與手機都安裝並登入，這要你授權。
