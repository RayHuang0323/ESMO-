## 案 1　恢復進行中的比賽：`matchSetupHash` 沒有人讀

**現況（讀程式確認）**

- 進行中的比賽會把整份規則集與 `matchSetupHash` 寫進存檔（`useLocalServer.js:282-285`）。
- 恢復時用同一個 Seed 從頭 tick 追到存檔時間。規則集重新解析：落盤的規則集要通過 `createMatchSetup` 才沿用；正式規則集的層值釘在登錄值，所以落盤的 safeRoute "v3" 對上現在登錄的 "v5" 會被判不合法，改用旗標解析。
- 整個 `src` 裡 `matchSetupHash` 只有三種出現：定義、寫入、回傳。沒有任何地方拿存下來的值比對。

**影響**

- 正式站：三個旗標全關，規則集是 `career.v20`，層值沒換過 ⇒ 碰不到。
- 開了 v23 旗標的預覽或開發 build：跨版本恢復的比賽會在中途換規則，前半段重算的結果和當時玩家看到的不同，畫面沒有提示。
- Replay 與已結束的比賽不受影響（只播放存下來的畫面、不重算）。

**為什麼這一輪不修**

修法是「恢復時重算 `matchSetupHash`，和存下來的值不同就明確放棄恢復並提示」。這會改變恢復行為（原本會恢復的比賽變成不恢復），也會動到存檔流程與 UI，屬於行為變更。依指示獨立列案。

**提案（待核准）**

| 步驟 | 內容 | 改對戰語意嗎 |
|---|---|---|
| 1a | 恢復時比對雜湊；不同 ⇒ 不恢復，顯示「這場比賽是用舊版規則開始的，無法繼續」，把該場記為未完成 | 否（但改恢復行為） |
| 1b | gate：落盤規則集被改過時，恢復必須明確失敗，不得靜默改用旗標解析 | — |

## 案 3　`verify.mjs --resume` 沿用舊的 PASS（已修補）

**原本**：狀態檔每段只記 PASS／FAIL。`--resume` 只看狀態，所以程式改過之後，舊的 PASS 照樣被跳過。

**現在**（`tools/verify.mjs`，+約 70 行，只有加法；由 Opus 5.5 依規格修改，我審查並補上「未提交內容雜湊」）

- 每段結果多存一個出處：commit、模擬版本與指紋、工作樹是否乾淨、未提交內容的雜湊。
- `--resume` 只在「commit 相同、指紋相同、未提交內容相同」時沿用 PASS；否則重跑並印出原因。
- 沒有出處的舊紀錄一律視為過期。
- `--list` 顯示每段是 current／stale／no-prov；`--dry-run` 只列出會跑哪些段、為什麼，不執行、不寫狀態檔。
- `--trust-legacy-state` 可以明確要求沿用任何 PASS（會印警告）。

**實測**（用暫時的狀態檔，測完已刪除）

| 情境 | 結果 |
|---|---|
| 沒有出處的 PASS | 重跑：`STALE PASS (no provenance recorded)` |
| 出處是別的 commit | 重跑 |
| 出處與現在相同（含相同的未提交內容） | 沿用 |
| 上次 FAIL | 重跑 |
| `--trust-legacy-state` | 三個 PASS 全部沿用，印出警告 |

沒有實測到的分支：只有指紋不同、其他都相同的情況（邏輯與 commit 比對相同）。

**要注意**：合併到其他分支之後，別人第一次 `--resume` 會看到所有舊 PASS 被判過期。這是預期行為。這支工具其他代理也在用，這個改動目前只在本分支。

## 案 4　v21 層隔離證明（條件式核准的前置）

**背景**：真實性表量的是 `balanceTool.v21`。現行規則是「量測時載入過的檔案只要有一支變了就過期」，其中包含 `simulationVersion.js`。所以 v22、v23 每換一次層值，v21 的量測就全部過期，即使 v21 的對局一個 tick 都沒變。

Owner 的條件：先完成 v21 雜湊釘點、零呼叫與隔離證據，不得直接排除檔案檢查。

**這一輪完成的證據**

新 gate：`node tools/check_layer_isolation_v21.mjs`（約 1～2 分鐘，9 場整場對局）。

| 證據 | 內容 | 結果 |
|---|---|---|
| L1 結構 | `balanceTool.v21`、`career.v21` 沒有 jungleCamp／invasion／safeRoute 層；v21 對局裡 7 個層開關全關 | 見下方 gate 輸出 |
| L2 零呼叫 | v21 對局整場，16 個 v22／v23 才有的引擎方法 0 次呼叫 | 同上 |
| L3 雜湊 | 9 場 v21 對局（工具路徑 6、生涯路徑 3）的整場逐 tick 雜湊，等於在 **v21 凍結點 `78ccc817` 的原始碼**上錄下的值 | 9／9 相同 |

L3 的錄法：`git archive 78ccc817 src tools` 匯出到 repo 外（`C:\Users\ifikn\esmo-measure\v21-freeze-78ccc817\`），把同一支 `pin_v21_stream.mjs` 放進去執行（當時的版本表顯示 `moba-sim.v21`／`620196ccea5a8249`），再在目前的程式執行，逐值比對。兩份原始輸出在 `v23_freeze/v21_pins_at_78ccc817.json` 與 `v21_pins_at_aa45009b.json`。

**這份證明的界線**

- 釘點是 9 場，不是所有輸入。它涵蓋 5 種模板組合與兩條路徑，沒有逐一涵蓋真實性表的 91 列選項。
- 零呼叫是用實例上的計數包裝量的；L3 的雜湊是在包裝之後算的，所以同時證明包裝不影響對局。
- **真實性表現有的資料不是在 v21 凍結點量的**（量測指紋是 `0578…`，凍結值是 `620196…`）。所以這份證明救不回現有資料；它的作用是：之後在目前的程式上重測一次 v21，那一輪結果在 v22／v23／v24 的層內改動下可以不必再重測。

**還沒做的（等核准）**

真實性表的過期規則一個字都沒改。建議的改法是「加一條看得見的豁免」，不是把檔案移出比對：

1. 檔案比對照舊。不同 ⇒ 預設過期。
2. 如果不同的檔案都在「層隔離清單」裡，而且 `check_layer_isolation_v21` 在同一個 commit 通過 ⇒ 那一列標成「層隔離豁免」，不是「有效」；表上與報告裡都看得見，並附上 gate 的 commit。
3. 任何一項不成立 ⇒ 照舊整輪重測。
4. 釘點要擴充到真實性表實際量的選項（每個維度至少一個選項、兩個 Seed），否則豁免只能用在已釘住的模板。
