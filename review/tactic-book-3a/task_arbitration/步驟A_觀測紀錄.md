# 任務仲裁 TaskArbitration.v1 步驟 A：只寫紀錄（2026-11-14）

依據：Owner Review 決策 3。**只新增觀測紀錄與原因碼，不改任務優先權、不改對戰結果。** 鎖定與遲滯（步驟 B、C）沒有實作。

## 1. 做法：觀測器放在引擎外面

v23 已凍結，`src/LogicEngine.js` 任何一個位元組的改動都會讓凍結 gate 變紅。所以步驟 A 沒有改引擎，觀測器是一支獨立的模組：

- `tools/lib/taskArbitrationObs.mjs`：`attachTaskArbitration(engine)`。在引擎**實例**上包 21 個方法（原樣呼叫、原樣回傳），並在每個 tick 前後讀狀態。不寫任何引擎或英雄欄位。
- `tools/owner_preview/task_arbitration_v1.mjs`：跑對局、輸出每場的紀錄摘要；`--selfcheck` 比對有掛與沒掛觀測器的逐 tick 雜湊。
- `tools/check_task_arbitration_obs_v1.mjs`：gate（約 11 秒）。

由 Opus 5.5 依規格撰寫；我讀過分類邏輯、跑過 gate 與 40 場資料，並拿它和上一輪獨立寫的診斷工具對帳。

**把觀測器搬進引擎（讓正式對局也能輸出紀錄）是另一件事**：那會改動語意檔，必須在 `moba-sim.v24` 候選裡做、重新登記指紋。獨立列案，沒有做。

## 2. 每名英雄每 tick 的一筆紀錄

| 欄位 | 內容 |
|---|---|
| `winner` | 第一段贏的任務：撤退、入侵、追擊、脫戰、決策層避塔、物件窗、主動權攻城、隊友呼叫、團戰集結、局部決策、預設（再分：對線、打野、抓人、遊走、推進、其他） |

| `suppressed` | 這個 tick 前提也成立、但優先序較低而沒被採用的任務 |
| `rewrites` | 第二段實際改了移動目標的層，依套用順序：站位、再任務承諾、塔區退出、發呆再任務、塔邊等待、安全路線、嘲諷 |
| `approx` | 這一筆的原因碼是不是近似 |

## 7. 新發現：再任務承諾幾乎沒有在運作

- 40 場裡「再任務承諾」這一層改寫 0 次。
- 我另外直接數承諾存在的時間（Seeds 93005、93021）：17,884 個英雄 tick 裡 3 個、22,153 個裡 21 個，都不到 0.1%，而且都是「跟兵線」「打野」「集合」。
- 原因：規則裡 `taskCommitPush` 是 false（`matchProgression.js:855`），所以發呆再任務最常派出的「推進」不會被承諾。
- 這解釋了上一輪的「對線 ↔ 推進來回占全部來回的 65%」：v19 的承諾機制對推進是關的。
- 限制：承諾存在的 tick 太少，所以我沒辦法獨立確認觀測器在這一層完全沒有漏接。0 次與「幾乎不存在」一致，但不是證明。

這是既有設定，不是這一輪造成的，也沒有改。它直接影響步驟 C（遲滯）的設計：也許不需要新的遲滯規則，而是重新評估 `taskCommitPush`。要量測才知道，列入後續。
