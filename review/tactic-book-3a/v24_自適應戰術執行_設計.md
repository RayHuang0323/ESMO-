## 3. 決策契約：TacticalExecution.v1

五步循環不變：

```
意圖（Director 查表）→ 評估（引擎算，只用已知資訊）→ 編隊與承諾 → 執行（沿用現有英雄狀態）→ 結束（完成／中止／未出發，一律記原因）
```

### 3.1 意圖

| 欄位 | 內容 |
|---|---|
| `kind` | `invade`｜`defend`（回防）｜`rescue`（救援）。第一個候選版本只做這三種 |
| `posture` | `auto`｜`conservative`｜`aggressive`｜`allIn` |
| `window` | 有效時間範圍 |
| `target` | 目標提示（哪一側野區）；可為空 |

- `invade` 由戰術書給（玩家選了入侵模板，或 AI 教練排了入侵）。
- `defend` 與 `rescue` 是所有隊伍都有的反應意圖，不需要玩家選。

### 3.2 評估時點

不是每個 tick 都算。只在以下時點算一次，結果承諾到下一個時點：

1. 意圖的時間窗打開時。
2. 之後每 `evalPeriod` 秒（建議 5 秒，Sprint 0 校準）。
3. 情境改變：編隊成員陣亡或撤退、看見新的敵方英雄、目標消失。

每次評估**一定**產生一筆紀錄：`go`（出發，含人數與名單）、`declined:<原因>`（不出發）、`hold`（維持進行中的執行）。不允許沒有紀錄。

### 3.3 三組分數

**(a) 每名隊員的可用度**

| 因素 | 讀什麼 | 素質 |
|---|---|---|
| 血量 | 目前血量比例；剛復活、回城中、撤退中 ⇒ 不可用 | — |
| 到場時間 | 用既有導航求到目標入口的路徑長度 ÷ 移速（路徑要避開敵塔，沿用 safeRoute） | — |
| 兵線代價 | 自己那一路的兵線位置。推過河道 ⇒ 代價低；壓在自家塔下 ⇒ 代價高 | — |
| 對位壓力 | **看得見的**對位敵人是否在線上、是否正在推塔 | 地圖意識 |
| 個人傾向 | 現有的能力修正：`invadeAdj`、`roamGateAdj`、`commitAdj` | 決策、配合、勇氣 |

**(b) 目標價值**：野怪營是否存活、剩餘血量、是不是 Buff、離重生多久；入口到目標的距離；撤退路線長度（用 safeRoute 求，求不到 ⇒ 價值大減）。

**(c) 威脅**：只用 §4 的已知資訊。

| 因素 | 讀什麼 |
|---|---|
| 敵方到場時間 | 每名**已知位置**的敵方英雄到目標的路徑時間 |
| 未知敵人 | 位置未知的敵方英雄，依「最後看見的位置與時間」推一個保守的到場時間；從沒看過 ⇒ 視為在自己那一路的常態位置 |
| 敵方戰力 | 已知者的血量、等級 |
| 塔 | 目標與撤退路線是否在敵塔危險半徑附近 |

輸出：我方可到場戰力 ÷ 敵方同時間可到場戰力，以及人數方案。

16 項素質的用法守三條既有紅線：
1. 只做**門檻平移**（出發門檻、中止門檻、可用度門檻），不乘進傷害、移速、血量。
2. 中性素質 ⇒ 平移量為 0 ⇒ 與「不看素質」的結果逐位元相同。這一條要寫成 gate。
3. 不新增素質係數表。只用 `_mod(p)` 已經算好的那幾個修正量。Owner 2026-11-12 的決定是「不新增 16 項素質係數」。

### 3.4 編隊：1～4 人

候選順序：打野（帶隊）→ 中路 → 輔助 → 靠近目標那一路的邊路。ADC 不參加。

| 傾向 | 人數 | 出發門檻 | 中止門檻 |
|---|---|---|---|
| 保守 | 1～2 | 高 | 早 |
| 自動 | 1～3 | 中；人數依威脅調整 | 中 |
| 積極 | 2～3 | 低；願意付兵線代價 | 晚 |
| 全力 | 3～4 | 最低；忽略兵線代價 | 只在明顯輸掉交戰時走 |

- 門檻的實際數值由 Sprint 0 量出來，這份設計不定。
- 人數由評估決定，不擲骰。同一個 Seed 重跑相同；陣容或戰況變了，人數會跟著變。
- 跟隊者的新行為只有一種：「護送」。站在帶隊者與敵方來向之間，不打野怪，有敵人接近時交戰。

### 3.5 敵方回防與隊友救援（同一套評估，反向使用）

**回防（`defend`）**
- 觸發只有兩種，都是防守方「合理知道」的事：
  1. 防守方的野怪營被攻擊，而且營地在防守方任一英雄或塔的視野內。
  2. 入侵者被防守方看見（§4）。
- 觸發後，防守方對「回防」做同樣的評估：誰能抽身、到場時間、戰力比。回防 1～4 人，也可能評估後不回防（`declined`）。
- 雙方同時入侵：各自獨立評估；在河道相遇時由現有的交戰判斷接手，不寫特例。

**救援（`rescue`）**
- 觸發：編隊成員血量低於門檻、或被人數壓制，而且正在撤退。
- 評估：救援者到場時間 < 被救者預估存活時間，而且到場後的戰力比不低於門檻。否則 `declined:too_far` 或 `declined:outnumbered`。
- 現有的 Team Call（`_issueCallV20` 的 `lowhp`／`retreat`）已經有呼叫與回應分數。救援沿用它發出呼叫，只把「回應與否」改讀評估結果，不另建一套。

### 3.6 安全撤退

- 編隊撤退沿用現有的個人撤退生命週期（撤退、退守自家塔、回城），不新增狀態。
- 路線沿用 safeRoute v5：避開敵塔；被包住而且附近沒有敵方英雄時留在射程外回城，有威脅才走成本最小的穿越路線。
- 新增的只有「一起走」：帶隊者中止時，跟隊者同一刻收到中止，不會留一個人在敵方野區。
- 出發前就要確認撤退路線存在。求不到安全撤退路線 ⇒ 目標價值大減，通常會變成 `declined:no_exit`。

### 3.7 原因碼（一張表，三種意圖共用）

| 原因碼 | 意思 | 現況 |
|---|---|---|
| `hp` | 帶隊者血量不足 | 已有 |
| `outnumbered` | 敵方到場戰力超過門檻 | 已有（改用到場時間與已知資訊） |
| `no_target` | 沒有可打的目標 | 已有 |
| `lost_race` | 目標被對方先拿走 | 已有 |
| `killed` | 帶隊者陣亡 | 已有 |
| `retreat` | 個人撤退邏輯接手 | 已有 |
| `window` | 時間窗結束 | 已有 |
| `ally_down` | 跟隊者陣亡，剩餘戰力低於門檻 | 新增 |
| `lane_emergency` | 隊員原本那一路的塔正在被拆 | 新增 |
| `objective_call` | 更高優先的物件開打 | 新增 |

## 4. 資訊公平：AI 知道什麼

| 資訊 | 可不可以用 | 依據 |
|---|---|---|
| 己方英雄、己方小兵、己方塔的完整狀態 | 可以 | — |
| 敵方英雄**現在**的位置、血量 | 只有被己方看見時（任一己方英雄 16 單位內、非隱身），沿用 `_seenV20` | 現有規則 |
| 敵方英雄最後一次被看見的位置與時間 | 可以（新增一張每隊的記憶表，只在看見時更新） | 新增 |
| 敵方英雄等級、裝備 | 只用最後一次看見時的值 | 新增 |
| 野怪營是否存活 | 己方野區：可以。敵方野區：只有看見時才知道，否則用「上次看見的狀態＋重生時間」推估 | 新增 |
| 塔的存亡與血量 | 可以（全圖公開資訊） | — |
| 敵方的戰術書、意圖、評估結果 | **不可以** | — |

範圍控制：
- 這張表**只約束 v24 新增的評估函式**。既有判斷裡直接讀全部敵方英雄的 18 處不在 v24 的範圍內，改它們會動到 v20 以來的所有行為。那是另一個需要 Owner 決定的題目，列在 §9。
- 塔與小兵是否提供視野：第一版**不提供**（只有英雄），和 `_seenV20` 一致。這會讓回防比較難觸發。Sprint 0 會量「觸發率」，太低再提方案。
- gate 要掃原始碼：新評估函式裡出現對敵方英雄的讀取，必須經過記憶表的讀取函式。

建議先只核准 **Sprint 0**。理由：
- 不改語意、不動任何候選證據。
- 門檻數值有量測依據之後，Sprint 1 的範圍才定得準。
- 「只用已知資訊」會讓威脅估計變差多少，現在沒有數字。這個數字決定回防設計能不能成立。

Sprint 0 的工作量：一個新工具（約 300 行，掛在引擎實例上，不改原型）、一份事先登記、約 200 組對局（單線約 70 分鐘）、一份結果文件。

## 7. 開工前要先處理的衝突

這三件是本輪讀碼與量測看到的，不先處理，Sprint 1 的結果會被它們汙染：

1. **任務優先序**。入侵的 `tacTgt` 現在優先於決策層避塔、物件窗、隊友呼叫與團戰（Gank 與游走不是，它們是最低優先的換路改寫；2026-11-14 更正）。v24 的編隊如果沿用 `tacTgt`，四個人會一起無視龍與團戰。設計上的優先序是：撤退 > 物件召集 > 進行中的執行 > 新的出發。Sprint 1 要把 v24 的執行放在物件窗之後，而且只在 v24 層生效。
2. **Gank 與入侵搶同一名打野**。現在的寫法是入侵窗內不 Gank。v24 把入侵變成整場都可能評估之後，要明訂：進行中的 Gank 不被新的入侵評估打斷；入侵進行中不發起 Gank。
3. **Gank 選路對「殘血、壓線」目標敏感**。v2→v3 的 Gank 出發 −6.9% 就是這個（`v23_導航與移動安全.md` §B）。v24 的回防會讓更多人離線，這個效果會再出現。Sprint 0 要把「Gank 出發數」列為觀測項，不列為成敗判準。
