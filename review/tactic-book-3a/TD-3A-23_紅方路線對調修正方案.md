## 2. 統一的映射方案

### 2.1 規則（一句話）

**契約與計畫是己方視角；Director 是戰術資料唯一的「己方→世界」轉換點；引擎只看世界路名；要拿給契約層讀的輸出（例如證據計數），在讀取端用同一對函式轉回己方視角。**

| 層 | 路名 | 誰負責轉換 |
|---|---|---|
| 契約／計畫／Resolver／Registry／模板／UI 設定畫面 | 己方 | 不轉換 |
| Tactical Director 的 `knobs(side)`（引擎面） | 世界 | Director 在建立時用 `worldLaneForSide`／`sideRelativeLane` 轉一次 |
| Tactical Director 的 `directive(side, t)`（契約視圖） | 己方 | 不轉換（用設定的那一份） |
| 引擎（選手、塔、兵線、抓人、遊走、呼叫、計數） | 世界 | 不轉換 |
| 證據／戰術執行計數的讀者（Challenge 證據列、QM 工具、未來紅方的 BattleEndScreen） | 己方 | 一個共用 helper（§2.7） |

### 2.2 轉換公式（沿用既有函式）

世界路 `L` 的值＝己方路 `sideRelativeLane(side, L)` 的值；單一路名欄位用 `worldLaneForSide(side, lane)`。

```js
// 提案草稿（未實作）——放在 battle/moba/tactics/tacticalDirector.js
import { worldLaneForSide, sideRelativeLane } from "../../../gameData.js";
const LANES = ["top", "mid", "bot"];
//  按路分的 knob 欄位登記表：新增任何按路分的欄位都必須登記在這裡（§4-a 的 A2 會檢查）。
export const LANE_KEYED_KNOBS = Object.freeze({ laneOffset: "keys", gankWeights: "keys", splitLane: "value" });
function toWorldKnobs(side, k) {
  if (side !== "red") return k;                       // 藍方：兩套路名相同 ⇒ 回傳同一參照
  const keyed = (o) => Object.fromEntries(LANES.map((L) => [L, o[sideRelativeLane(side, L)]]));
  return { ...k, laneOffset: keyed(k.laneOffset), gankWeights: keyed(k.gankWeights),
    splitLane: k.splitLane == null ? null : worldLaneForSide(side, k.splitLane) };
}
```

- 鍵依 `top, mid, bot` 的固定順序建立 ⇒ 物件鍵順序與藍方相同（避免任何依鍵順序迭代的程式出現差異）。

### 2.3 三個旋鈕怎麼轉

| 旋鈕 | 轉換 | 數值 |
|---|---|---|
| `laneOffset` | 鍵 top↔bot 互換（mid 不動） | 不改 |
| `gankWeights` | 鍵 top↔bot 互換（mid 不動） | 不改 |
| `splitLane` | 值 top↔bot 互換；mid、null 不動 | — |

## 6. `simulationVersion.js` 量測失效評估（獨立一節，保守）

### 6.1 機制

- 〔事實〕真實性表記錄量測 worker 實際載入的每個 repo 檔與其正規化雜湊（`meta.loadedFiles`），任何一個變了就判過期（`tacticMeasureProvenance.mjs:6-15, 145-155`）；另有 `simVersion` 等雜湊欄位逐欄比對（`:30, 80-93`）。
- 〔事實〕`src/platform/contracts/simulationVersion.js` 在 `loadedFiles` 裡（現行 fixture 的 70 個載入檔之一）。只要重新登記指紋就會改這個檔 ⇒ 表必然過期 ⇒ 約 70 分鐘重測，**即使改動對行為完全中性**（08:13611）。

### 6.2 模擬執行期從這個檔拿什麼

〔事實〕`src/` 內 import 它的只有這些，而且只取版本字串／版本清單／`canReplay`：

| 檔案 | 取用 | 是否影響對局結果 |
|---|---|---|
| `battle/moba/matchAssemblerDepsCore.js:33, 83` | `MOBA_SIMULATION_VERSION`（寫進 deps manifest 當標籤） | 否（標籤） |
| `platform/contracts/squadSnapshot.js:57, 176, 207` | `MOBA_SIMULATION_VERSION`（新快照的預設欄位） | 否 |
| `platform/challenge/snapshotAuthority.js:45, 252`、`challengeRunner.js:40` | 同上 | 否 |
| `platform/contracts/challengeInstance.js:37, 221` | `MOBA_SIMULATION_VERSION`、`canReplay` | 否（決定能否重播，不改結果） |
| `platform/online/matchTicket.js:31, 134`、`battleTalentBinding.js:24` | `KNOWN_SIMULATION_VERSIONS`／版本字串 | 否 |

- 〔事實〕`SIMULATION_SEMANTICS_FILES`、`KNOWN_TRANSITIVE_GAPS`、`SIMULATION_SEMANTICS_FINGERPRINTS`（`simulationVersion.js:88, 235, 269`）在 `src/` 內**沒有任何讀者**；讀它們的全是 `tools/`。計數方法（可重現）：
  - 三個常數名：`rg -c "SIMULATION_SEMANTICS_FINGERPRINTS|SIMULATION_SEMANTICS_FILES|KNOWN_TRANSITIVE_GAPS" tools` ⇒ **19 支、59 行**（`rg -c` 數的是命中行數；同一行出現多次的以 `rg -o … tools | wc -l` 計為 72 次出現）。
  - 以路徑字串引用這個檔（import 或文字讀取都算）：`rg -l "simulationVersion\.js" tools --glob "*.mjs"` ⇒ **31 支**；`tools/fixtures` 另有 **2 個** fixture 提到它。（初稿寫的「22 支以文字讀取」是只數 `read("…simulationVersion.js")` 等少數寫法的結果，不完整，以 31 支為準。）

### 6.3 三個選項

**(a) 維持現狀。**
- 優點：零新風險；所有既有 gate 與說法不變。
- 代價〔事實〕：語意清單 49 支裡有 10 支不會被量測 worker 載入（`heroProgress.js`、`challengeRunner.js`、`draftPolicy.js`、`draftResult.js`、`mobaDraftAssignment.js`、`matchLineup.js`、`challengeMatchSetup.js`、`mobaRosterAdapter.js`、`liveMatchSetup.js`、`matchAssemblerDeps.js`），另有 3 支刻意用行為雜湊保護、不記文字（`tacticMeasureProvenance.mjs:37-41`）。改這 13 支任何一支都要重新登記指紋 ⇒ 透過 `simulationVersion.js` 讓表過期。近 5 次重新登記裡有 3 次屬這種情形（T10 Phase 2 的排除表、T12 的 `liveMatchSetup.js`、3a-A 的撤下表，`simulationVersion.js:521-530`）。也就是說，**「三支例外檔不讓表過期」的設計，在現行流程下實際上沒有效果**。
- 間接風險〔推估〕：重複付出的 70 分鐘會形成壓力，最後最容易被採用的是「直接把 `simulationVersion.js` 整個豁免」——那正是 08:13611 警告的「縮小安全 gate 涵蓋範圍」。

**(b) 把指紋登記資料拆到模擬永遠不 import 的檔。**
- 作法：`SIMULATION_SEMANTICS_FILES`、`KNOWN_TRANSITIVE_GAPS`、`SIMULATION_SEMANTICS_FINGERPRINTS` 搬到新檔（例如 `src/platform/contracts/simulationFingerprints.js`）；`simulationVersion.js` 只留版本字串、版本清單、`canReplay`。新檔**不得**被 `simulationVersion.js` re-export（re-export 會讓它被載入，等於沒拆）。
- 是否行為中性：〔事實〕搬走的三個常數在 `src/` 沒有讀者（§6.2）⇒ 任何對局的輸入、執行與輸出都不變。〔推估〕可用既有 gate 證明：v20 黃金 153／153、v21-A 131／131 逐位元相同；`check_match_setup_3a` 釘的 v1–v20 指紋表雜湊（`tools/check_match_setup_3a.mjs:57, 425`）改從新檔讀，**值必須完全相同**（內容只是搬家），這就是「沒有偷改任何一格」的證明。
- 仍然保留的保護：`simulationVersion.js` 本身仍被載入、仍被記錄；升版（改 `MOBA_SIMULATION_VERSION`）仍經 `simVersion` 雜湊讓表過期（正確的過期）；所有會被載入的語意檔仍各自被記錄。**沒有任何會被載入的檔被豁免**——它不是「排除」，是讓「不影響模擬的資料」不再住在「模擬會載入的檔」裡。
- 能省到什麼〔推估〕：只省「改動只落在 worker 不載入的語意檔、或三支行為雜湊檔」的情形。**C3–C6 主要改引擎與 Director，這些檔本來就被載入，(b) 一分鐘都省不到**；TD-3A-23 修正本身也一樣（§5.4）。
- 風險：
  1. 工具端改動面大：用到三個常數的 19 支（59 行）要改，以路徑引用這個檔的 31 支要逐支確認；任一支漏改就會讀到 `undefined` 或空表。⇒ 必須加「表非空、鍵數與搬家前相同」的斷言，避免 gate 在空表上**空轉變綠**。
  2. `tools/check_hero_skills_phase1.mjs:81` 用 `git show dc520f1:src/platform/contracts/simulationVersion.js` 讀歷史版本，那是歷史 blob，不受影響；但凡是拿「現在的檔」與歷史比對的工具都要逐支確認。
  3. 需要一條新 gate：`src/` 裡沒有任何檔 import 新檔（比對 import 識別字，先剝註解；新檔的檔頭說明一定會寫「模擬不得 import 本檔」，用文字比對會假紅——CLAUDE.md 記載過同類事故）。
  4. 拆檔這次本身會改 `simulationVersion.js` ⇒ 表會再過期一次（最後一次）。應與下一次本來就要重測的改動合併。

**(c) 行為探針重新認證（行為中性時，用一組探針對局證明逐位元相同，就把表的雜湊重新蓋章、不整輪重測）。**
- 風險：
  1. 探針覆蓋不到的狀態不能保證相同；真實性表是約 91 列 × 40 seeds 的大組合，小探針綠不代表整表不變〔推估〕。
  2. 要做到「與整表一樣可靠」就得重跑整表的每一場並逐場比雜湊——成本與重測相同，省不到時間。
  3. 「重新蓋章」是一條新的信任路徑：一旦被用在其實改了行為的改動上，就是把過期的表洗成新的，而且之後沒有任何訊號會發現。
- 結論：不建議。

### 6.4 建議（需 Owner 核准）

- **建議採 (b)**，但要 Owner 核准後才做；核准前一律維持 (a)。理由：(b) 不豁免任何會被載入的檔、不改任何對局結果，只移除「由不影響模擬的資料造成的過期」；同時消除 (a) 長期造成的「乾脆整檔豁免」壓力。
