# 自適應戰術執行系統（P1）— 設計與最小 Sprint

- 日期：2026-11-12
- 狀態：**只有設計，沒有改任何入侵模擬語意**；等 Owner Review
- 基礎：`moba-sim.v22` 候選的野區入侵 v2（`feature/moba-v21-sim-fixes`，`f1914fda`）
- 相關：`v22_候選_Buff入侵與Lag調查.md` 第 2 節（入侵 v2 的量測）

## 1. 現況與缺口

入侵 v2 現在的行為（`src/LogicEngine.js`）：

| 項目 | 現況 |
|---|---|
| 要不要入侵 | 開局擲一次骰（`invadeChance`；選入侵模板時 ≥ 0.7）。沒擲中就整場不入侵 |
| 誰去 | 固定打野；`invadeWithMid` 為真時中路**只走到入口**支援，不進去打 |
| 去哪 | 最近的敵方野怪營 |
| 何時放棄 | 血量 < 55%、身邊 14 內敵方英雄 ≥ 2、沒目標、輸掉競速、陣亡、撤退接手、90 秒窗到期 |
| 敵方反應 | **沒有**。敵方不知道被入侵，不會回防 |
| 量測結果（30 Seed） | 擲中 15 場全部走到並打到；搶到 10 場；入侵窗內英雄擊殺 0 次；失敗主要是被野怪打到血量不足 |

缺口有四個：

1. 人數固定 1 人，不看陣容與戰況。
2. 玩家選了入侵，仍有約三成整場不執行（骰子沒中），而且沒有任何理由紀錄。
3. 敵方不反應，所以沒有交戰，搶到率偏高（67～86%）。
4. 判斷寫死在入侵專用的函式裡，分推、團戰、物件控制無法共用。

## 2. 設計原則

1. **選擇＝意圖，不是結果。** 玩家選了某個戰術，系統保證「每個合理時機都會評估並盡量執行」，不保證成功。每一次不執行或中止都要有原因碼。
2. **決定性。** 評估只讀引擎狀態，不擲骰、不新增亂數消耗（沿用 v22 入侵 v2 的作法），Replay 才能重現。
3. **不另建引擎。** 意圖與傾向放 Tactical Director（查表）；執行沿用引擎現有的英雄狀態（入侵、撤退、集結）；玩家可選項走 Capability Registry。
4. **雙方同一套規則。** 進攻與回防用同一個評估函式，只是視角相反；用 `teamRelative` 路名框架，紅藍對稱。
5. **觀測與 Replay 契約分開。** 新的統計放獨立的觀測物件（比照 `invObs`），不動 `exec` 的形狀。

## 3. 共用決策契約：TacticalExecution.v1

四種戰術（入侵、分推、團戰、物件控制）共用同一個五步循環：

```
意圖（Director 給）→ 評估（引擎算）→ 編隊與承諾 → 執行（沿用現有狀態）→ 結束（完成／中止，記原因）
```

### 3.1 意圖（Intent）

由 Director 依玩家的戰術書、時期（前／中／後）提供，引擎只查表：

| 欄位 | 內容 |
|---|---|
| `kind` | `invade`｜`split`｜`teamfight`｜`objective` |
| `posture` | `auto`｜`conservative`｜`aggressive`｜`allIn`（玩家可選的傾向） |
| `window` | 這個意圖有效的時間範圍 |
| `target` | 目標提示（哪一側野區、哪一路、哪個物件）；可為空，交給評估選 |

### 3.2 評估（Assessment）

純函式，輸入是引擎當下狀態，輸出是「去不去、去幾個、誰去、去哪」。三組分數：

**(a) 每名隊員的可用度**（決定誰能抽身）

| 因素 | 讀什麼 |
|---|---|
| 血量與資源 | 目前血量比例、是否剛復活或正在回城 |
| 到場時間 | 目前位置到目標入口的路徑時間 |
| 兵線狀態 | 自己那一路的兵線位置：推過河道＝可離開；壓在自家塔下＝離開要付代價 |
| 對位壓力 | 對位敵人是否在線上、是否正在推塔 |
| 能力 | 選手的能力修正（現有的 `invadeAdj` 等）、英雄定位（刺客／坦克／法師）、等級與裝備相對對手 |

**(b) 目標價值**

| 因素 | 讀什麼 |
|---|---|
| 目標本身 | 野怪營是否存活、剩餘血量、是不是 Buff、重生時間 |
| 距離與路徑 | 入口到目標的路徑、撤退路線長度 |

**(c) 威脅**

| 因素 | 讀什麼 |
|---|---|
| 敵方到場時間 | 每名敵方英雄到目標的路徑時間（取代現在的「身邊 14 內 ≥ 2 人」） |
| 敵方戰力 | 可能到場者的血量、等級、控制技能 |
| 塔 | 目標是否在敵方塔射程附近 |

評估輸出「我方可到場戰力」對「敵方在同一時間內可到場戰力」的比值，以及人數方案。

### 3.3 編隊：1～4 人

候選順序：打野（一定是帶隊）→ 中路 → 輔助 → 靠近目標那一路的邊路。ADC 不參加（守線與吃兵）。

| 傾向 | 人數 | 出發門檻（我方對敵方的到場戰力比） | 中止門檻 |
|---|---|---|---|
| 保守 `conservative` | 1～2 | 高（明顯優勢才去） | 早（一有敵人接近就走） |
| 自動 `auto` | 1～3 | 中；人數依威脅調整 | 中 |
| 積極 `aggressive` | 2～3 | 低；願意付兵線代價 | 晚（願意先打一波） |
| 全力 `allIn` | 3～4 | 最低；忽略兵線代價 | 只在明顯輸掉交戰時走 |

- 門檻的實際數值**不在這份設計裡定**，由第 6 節的 Sprint 0 量出來。
- 人數不是固定值：同一個傾向下，敵方打野在另一側現身時減人，敵方多人靠近時加人或不去。
- 「自動」的意思是由 AI 在 1～3 人之間自己選，不是「隨機」。

### 3.4 執行與中止

執行沿用現有狀態：帶隊者用入侵 v2 的走位與打野怪邏輯；跟隊者新增「護送」行為（站在帶隊者與敵方來向之間，不打野怪、有敵人接近時交戰）。

中止原因碼（統一一張表，四種戰術共用）：

| 原因碼 | 意思 | 現況 |
|---|---|---|
| `hp` | 帶隊者血量不足 | 已有 |
| `outnumbered` | 敵方到場戰力超過門檻 | 已有（改用到場時間計算） |
| `no_target` | 沒有可打的目標 | 已有 |
| `lost_race` | 目標被對方先拿走 | 已有 |
| `killed` | 帶隊者陣亡 | 已有 |
| `retreat` | 全隊撤退邏輯接手 | 已有 |
| `window` | 意圖的時間窗結束 | 已有 |
| `ally_down` | 跟隊者陣亡，剩餘戰力低於門檻 | 新增 |
| `lane_emergency` | 隊員原本那一路的塔正在被拆 | 新增 |
| `objective_call` | 更高優先的物件（龍／巴龍）開打 | 新增 |
| `declined:<原因>` | 評估後決定不出發（威脅過高、沒人能抽身…） | 新增 |

`declined` 是這個設計的重點：玩家選了入侵但這場沒去，賽後要能看到「第 0:45 評估：敵方三人在河道，不出發」。

### 3.5 敵方回防（同一套評估，反向使用）

- 觸發：防守方的野怪營被攻擊，或入侵者進入防守方英雄／塔的偵測距離。⚠ 現有的戰爭迷霧只是畫面效果，引擎不知道有迷霧；這裡的「偵測」要在引擎裡新定義（距離判定），屬於語意變更。
- 防守方對「回防」這個意圖做同樣的評估：誰能抽身、到場時間、戰力比。回防人數同樣 1～4 人。
- 雙方同時入侵：兩邊各自獨立評估；在河道相遇時由現有的交戰判斷接手，不寫特例。
- 回防也有兵線代價，同樣記錄。

### 3.6 收益與代價的帳

每次執行結束記一筆觀測（不進 Replay 契約）：

| 欄位 | 內容 |
|---|---|
| 參與者、人數、傾向 | |
| 結果與原因碼 | |
| 搶到的野怪金錢／經驗 | |
| 交戰結果 | 擊殺、陣亡 |
| 兵線代價 | 參與者離線期間漏掉的小兵金錢／經驗、塔受到的傷害 |
| 敵方回防人數與對方的兵線代價 | |

有了這張帳，公平性才量得出來：入侵的淨收益＝搶到的＋擊殺−兵線代價−陣亡損失。

## 4. 延伸到其他戰術

| 戰術 | 意圖 | 評估重點 | 編隊 | 主要中止原因 |
|---|---|---|---|---|
| 入侵 | 敵方野區 | 到場戰力比、目標存活 | 1～4，打野帶隊 | `hp`、`outnumbered`、`lost_race` |
| 分推 | 某一路的塔 | 分推者單挑能力、敵方回防人數、我方另外四人能否牽制 | 1（＋1 護送） | `outnumbered`、`objective_call` |
| 團戰 | 集結點 | 雙方到場人數與戰力、大招冷卻 | 3～5 | `ally_down`、`declined` |
| 物件控制 | 龍／巴龍／塔 | 物件血量、雙方到場時間、打野懲戒 | 3～5 | `lost_race`、`outnumbered` |

現有的 `_objectiveUrgency`、`_objectiveTeamView`、團戰集結窗已經在做這類判斷的一部分。這個契約的目的是讓它們用同一組輸入、同一張原因碼表、同一種觀測紀錄；**不是**重寫它們。延伸的順序見第 6 節。

## 5. 玩家可調整的方式

戰術書新增一個維度（每個時期各一個）：**執行傾向**。

| 選項 | 給玩家看的說明 |
|---|---|
| 自動 | 由教練組依陣容與戰況決定人數與時機 |
| 保守 | 只在明顯有利時出手，一有危險就撤 |
| 積極 | 願意犧牲一些兵線，主動製造機會 |
| 全力 | 多人出動，接受較高風險 |

- 走現有流程：Capability Registry 新增一列（先是 `design`），通過真實性 gate（選項真的改變行為）後才轉 `live`、才出現在戰術書。這是 Owner 之前定的「不做假功能」規則。
- 第一版只接入侵；傾向對其他戰術還沒有作用之前，畫面要標明「目前只影響野區入侵」。
- 賽後報告顯示每次評估的結果與原因，讓玩家看得出「我選了積極，AI 做了什麼、為什麼沒做」。

## 6. 版本策略與最小 Sprint

### 需要新的模擬版本嗎

**需要。** 人數、出發判斷、回防都會改變比賽結果。建議：

- 新的可選規則集層 `tacticExecution: "adaptive.v1"`，只存在於新規則集 `career.v23`／`balanceTool.v23`（從 v22 逐欄衍生）。
- 新旗標 `mobaTacticExecV23`，預設 false，需要 v22 旗標也開才生效。
- v20、v21、v22 的規則集物件與已歸檔證據一個欄位都不動；v22 指紋 `c2b507e0cc723382` 保留為歷史憑證。
- 前提：**v22 要先由 Owner 決定去留**。如果 v22 不核准，這個設計要改成從 v21 衍生，入侵 v2 併進新版本。

### Sprint 切法

| Sprint | 內容 | 改語意嗎 | 產出 |
|---|---|---|---|
| **0　影子研究** | 只寫工具：在 v22 的對局裡，於每個決策時點從引擎外部算出第 3.2 節的三組分數，對照實際結果（搶到／血量中止）。用新的公開 Seed，紅藍各半、至少三種陣容 | **不改** | 每個因素與結果的關聯；四種傾向的門檻建議值；「如果用這套門檻，會出發幾次、幾人」的預估 |
| **1　自適應編隊** | 評估函式、1～4 人編隊、護送行為、`declined` 與新原因碼、觀測帳 | 改（v23 候選） | 執行率、人數分布、原因碼分布、兵線代價；回歸 gate |
| **2　敵方回防** | 回防意圖、雙方入侵 | 改（同一個 v23 候選，重新登記指紋） | 交戰次數、搶到率落點、淨收益 |
| **3　玩家傾向** | Registry 列、解析器、戰術書畫面、賽後原因顯示 | 改設定路徑，不改引擎規則 | 真實性 gate：四個選項行為可區分 |
| **4　延伸** | 物件控制接上同一個契約（最接近現有程式） | 改（另一個候選版本） | 另案規劃 |

建議先只核准 **Sprint 0**：不改語意、不動任何候選證據，約一個工作段可以完成，而且門檻數值有了量測依據之後，Sprint 1 的範圍才定得準。

## 7. 驗收標準（草案，數值待 Sprint 0 校準）

| # | 標準 | 怎麼量 |
|---|---|---|
| 1 | 層不存在時，v20／v21／v22 的結果逐位元相同 | 既有黃金與 `check_match_setup_3a`；v22 的 41 條 gate |
| 2 | 選了入侵的對局，**每一場**都至少有一次評估紀錄；「出發」或「`declined` 加原因」二擇一，不允許沒有紀錄 | 新 Seed，紅藍各半 |
| 3 | 選「自動」以上時，至少一次實際走到敵方野區的對局比例達到目標值 | 目標值由 Owner 定（建議 ≥ 80%） |
| 4 | 四種傾向的人數分布可區分（保守的平均人數 < 自動 < 積極 < 全力） | 真實性 gate |
| 5 | 1、2、3、4 人的情況都實際出現過，且不是由骰子決定 | 同一 Seed 重跑結果相同；改陣容或戰況後人數會變 |
| 6 | 有回防之後，搶到率落在目標區間 | 區間由 Owner 定（v22 無回防時是 67～86%） |

| 9 | 選入侵模板對勝率的影響在 Owner 核准的範圍內 | 相對於標準模板的勝率差，新 Seed |
| 10 | 所有原因碼都至少被單元測試觸發一次 | 新 gate |
| 11 | 不新增亂數消耗；同一 Seed 重跑逐位元相同 | 新 gate |

## 8. 風險

| 風險 | 說明 | 對策 |
|---|---|---|
| 雪球 | 多人入侵成功 → 經濟領先 → 之後更容易成功 | 觀測帳記淨收益；驗收 #9 設勝率上限 |
| 兵線崩盤 | 抽太多人導致塔被拆 | `lane_emergency` 中止；全力傾向也保留 ADC 守線 |
| 資訊公平 | 評估用的是引擎的完整資訊；防守方是否只能用視野內資訊 | 需要 Owner 決定（見下） |
| 計算成本 | 每名英雄每刻算路徑時間 | 只在決策時點算（不是每刻）；沿用現有導航的距離查詢；Sprint 0 一併量模擬每刻耗時 |
| 與既有判斷衝突 | 團戰集結、撤退、Gank 都會搶同一名英雄 | 明訂優先序：撤退 > 物件召集 > 進行中的執行 > 新的出發 |
| 範圍膨脹 | 四種戰術一次做完 | 第一個候選版本只做入侵 |

## 9. 需要 Owner 決定的事

1. v22 候選（Buff＋入侵 v2）要不要核准為這個設計的基礎。
2. 先只核准 Sprint 0（影子研究，不改語意），還是直接核准到 Sprint 1。
3. 防守方的資訊：用完整資訊（簡單、與現有 AI 一致）還是只用視野內資訊（較真實，但入侵會更容易成功）。
4. 驗收 #3、#6、#9 的目標值。
5. ADC 永遠不參加入侵（設計如此）是否同意；若要 5 人全員入侵，需要另外處理兵線全空的情況。
6. 傾向是每個時期各選一次，還是整場一個。
