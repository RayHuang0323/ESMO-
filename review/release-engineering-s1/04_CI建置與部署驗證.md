## E2：純文件 push 不重新部署

### 為什麼不用 `paths-ignore`

1. 它只看這次 push 帶了哪些檔，**看不到上一次部署失敗**。上一個產品 push 的部署失敗（例如 Pages 500）之後，接著推一個純文件 commit，就會被跳過，產品永遠不會上線，也沒有人發現。
2. 它只看路徑和副檔名。`public/**/*.md` 會被複製進 dist；用 `?raw` 或 `import.meta.glob` 匯入的 `.md` 會進 bundle。

### 做法（`tools/ci/deploy_decision.mjs`＋新的 `decide` job）

- 用 GitHub deployments API 找出「最後一次**成功**的 Pages 部署」的 SHA，拿它和 HEAD 比較。
- 只有在兩者之間的每一列都是白名單文件（mode 100644），而且產品原始碼、建置設定、public、package、.github 都沒有引用它們時，才輸出 `deploy=false`。
- 以下情況一律 `deploy=true`：手動觸發（`workflow_dispatch`）、API 失敗、沒有權杖、找不到最後部署、最後部署不在歷史裡或不是祖先、diff 讀不懂、判斷時發生例外。
- `build` 的條件是 `!cancelled() && needs.decide.outputs.deploy != 'false'`：decide 失敗或沒有輸出時照常 build。
- `deploy` 的條件是 `!cancelled() && needs.build.result == 'success'`。審查發現預設的 `success()` 會連帶看 decide 的結果，已修正。
- build 之後加了兩步：整棵依賴樹檢查（不符就讓部署失敗）、印出 `DIST_HASH`。

### 限制與風險

- 本機沒有 YAML 解析器（沒有為此新增依賴），workflow 語法只做了人工檢查和規則測試。**第一次真實執行時需要 Owner 在 Actions 頁面確認**。
- **Branch protection／必要檢查**：這台電腦沒有權杖，查不到設定。依 GitHub 文件，被跳過的 job 對必要檢查視為通過；若之後設了「必須通過 build」，需要確認這一點。
- 跳過部署時，main 的 SHA 和正式站的建置來源 SHA 會不同。發布報告要寫「正式站建置來源＝最後成功部署的 SHA」，驗證正式站時比對 bundle 雜湊。
- 如果 Owner 不想讓這個改動上線，可以只 revert `cf6ef2f1` 和 `62c84db7` 裡 `deploy.yml` 的部分；其他工具不依賴它。
