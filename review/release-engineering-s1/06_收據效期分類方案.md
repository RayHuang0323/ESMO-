# Release Engineering S1｜06 收據效期分類方案（待 Owner 核准，未實施）

- ⚠ 正式效期**仍是 24 小時**（`DEFAULT_MAX_AGE_HOURS = 24`，本輪沒有改）。本文件只是提案。
- 本輪已完成的部分是唯讀工具 `tools/release_gate_plan.mjs`（`status`、`plan`），以及在收據裡記錄瀏覽器版本。
- 測試：`node tools/check_release_gate_plan.mjs`，19/19。

## 一、C1＋C2 實測：效期問題出在哪裡

| 項目 | 數字（來源：`plan` 讀 93655403 的真實收據） |
|---|---|
| 10 個 gate 本身的耗時合計 | 約 185 分鐘（3.1 小時） |
| 第一張到最後一張收據的實際跨度 | 07:01Z → 16:01Z，**9 小時** |
| 多出來的約 6 小時 | 休眠、等 Owner 決定、WebKit 低記憶體崩潰補跑、browser gate 跨休眠重跑、P2v2 等接電 |
| 照實際順序的剩餘窗口 | 21.36 小時（只算 gate 耗時） |
| 照建議順序（最長的先跑） | 21.66 小時，只多 0.3 小時 |

**結論**：調整順序的效益很小，**真正的成本是中間的等待與重跑**。所以：
1. 長測試要支援 checkpoint 續跑（Phase D）。
2. 收據過期時只重跑過期的那一張；現行 assert 本來就是逐張驗。
3. 效期依證據的性質分級，而不是一律 24 小時。

### 更正

上一輪 TD-62 方案寫「長時間的 Gate 排在最後跑」，這是**錯的**。依序執行時，所有收據的共同窗口取決於**第一個完成的**收據，跨度＝總時長 − 第一個 gate 的時長。所以應該**最長的排第一**。`plan` 會用實際歷史耗時算出建議順序。

## 二、分類提案

| 分類 | 例 | 建議效期 | 立即失效的條件 |
|---|---|---|---|
| 純邏輯與決定性 | moba、det、platform、active | 72 小時 | tree、依賴摘要、Node 主版本任一不同（收據裡都有，現行 assert 已檢查） |
| Golden 與版本隔離 | v21a、golden | 72 小時 | 同上，加上 fixture 或指紋常數改變（屬於 tree） |
| Production Build | production、build | 72 小時 | 同上，加上 VITE_* 建置環境（收據的 `bundle.buildEnv`） |
| 瀏覽器功能 | browser、四引擎 | **24 小時（不變）** | 瀏覽器版本改變（Chrome 會自動更新；收據現在記錄 `env.browser.chrome`） |
| 效能與記憶體 | P1、P2v2 | **24 小時（不變）** | 瀏覽器版本、電源狀態、機器負載；契約規定的完整實驗單位 |
| 正式站 Production Smoke | prod smoke | **不可沿用** | 只代表當下的正式站；任何部署都使它失效 |

### 理由

- 純邏輯類的結果只取決於 tree、依賴和 Node 主版本，這三項收據裡都有，時間本身不會讓它失效。
- 瀏覽器和效能類會受到自動更新與機器狀態影響，所以維持 24 小時。

## 三、需要 Owner 決定的事

1. 是否採用分級效期。若採用，需要另開一輪工具 Sprint：
   - assert 依收據的 `category` 套用不同上限；舊收據沒有 category 時一律 24 小時。
   - 瀏覽器類收據的版本必須與現在相同。
   - 加上反向測試。
2. 若不採用：維持 24 小時。工具照樣可以用 `status` 預警即將到期的收據，用 `plan` 排出最佳順序。

## 四、現在就能用的工具

```
node tools/release_gate_plan.mjs status --repo <worktree> --target-sha <sha> --require-gate … [--warn-hours 6]
node tools/release_gate_plan.mjs plan   --repo <worktree> --require-gate … [--est <gate>=<分鐘>]
```

`status` 會列出每個 gate 的狀態（PASS／EXPIRED／NOT_RUN／FAIL／INVALID）、來源（直接或 docs-carry）、到期時間、剩餘時數、瀏覽器是否已更新，以及整體發布窗口。
