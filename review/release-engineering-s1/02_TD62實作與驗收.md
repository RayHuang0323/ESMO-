## 怎麼用

```
# 1. 來源 B 的 production gate 必須記錄 bundle 雜湊（新規定；舊收據沒有，不能被沿用）
node tools/release_gate.mjs run --repo <B worktree> --target-sha <B> --gate <prod gate> --cmd "<build 指令>" --record-bundle dist

# 2. 在文件 commit D 的乾淨 worktree 上產生沿用收據
node tools/release_gate.mjs carry --repo <D worktree> --base-sha <B> --target-sha <D> --require-gate g1 --require-gate g2 ...

# 3. 照常 assert；D 沒有直接收據的 gate 才會改看沿用收據，並標示「沿用自 B」
node tools/release_gate.mjs assert --repo <D worktree> --target-sha <D> --require-gate g1 ...
```

## 其他規則

- 目標 SHA 上若有**直接收據**（即使是 FAIL），一律以直接收據為準，沿用不能蓋掉。有測試。
- `assert --require-gate docs-carry` 本身不會被當成 gate PASS。
- 沿用收據本身被改（digest 不符）⇒ assert FAIL。

## 實測發現（影響未來怎麼用）

1. C1＋C2 的 gate 是透過 repo **外**的 `run.mjs` 執行的，工具無法判定會跑到什麼 ⇒ 全部被保守判定為必須直接重跑。**要讓 gate 能被沿用，`--cmd` 必須直接呼叫 repo 內的工具。**
2. 交接文件是測試輸入：`check_cs_season_contract`、`check_home_team_contract` 會讀 `docs/ai/跨模型交接流程.md`。所以只要改了交接文件，跑到這兩支的 gate 就必須直接重跑；這正是預期的行為。
3. 判斷規則刻意偏保守。代價是「會碰 docs 目錄」的 gate（例如契約檢查）在任何 docs 變更時都要重跑。這是**不放寬驗收**的取捨。
