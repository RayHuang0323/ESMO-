## 1. Ban/Pick：分路摘要常駐 ＋ 頭像位置標示

### 根因不是「面板沒做」

摘要面板 Milestone I 就存在，而且本來就會隨選角即時重算。真正的問題是**版面順序**
與**自動跳頁**：

| 症狀 | 根因 |
|---|---|
| 選的時候看不到會被排到哪一路 | 面板排在 260px 高的選角捲動格**下面** ⇒ 輪到你選人時被推出畫面外 |
| 選完只閃現不到 1 秒 | `done` 後 `setTimeout(..., 1200)` 自動跳到戰術頁 |
| 還沒選就完全沒東西 | 面板被 `picks.blue.length > 0` 閘住 |

### 修法

1. 面板移到選角格**之上**，移除 picks 數量的閘門（尚未選角顯示「等待選角」）。
2. **不再自動跳頁**，改成明確的「確認出戰配置 →」按鈕。要看多久看多久。
3. 已選英雄頭像**下方**常駐位置標示（不疊在臉上、不遮名稱）；低適性或衝突時
   加 ⚠ 並在下方列出一行說明（例：`⚠ 混沌術士 → 上路：適性低`）。
4. 新增「陣容需求」：`已有 上路·中路 ｜ 尚缺 打野·下路·輔助`，下一手該補什麼一眼看得出來。
5. 摘要多一欄「被壓制」：用本檔既有的 `archCounterScore`（AI 選角本來就在算）
   比對對手已選英雄，門檻 2 分以下不顯示以免變成雜訊。

### 單一來源（Ray 明確要求「不可兩套判定」）

頭像位置碼、陣容需求、下方摘要**全部從 `draftPlan.assignment` 推導**——
`laneByHero` 與 `compNeeds` 兩個 useMemo 就是把同一份 assignment 轉成索引，
**沒有第二次計算**。

驗證方式不是看程式碼長相，而是**逐一比對兩處的輸出**：
瀏覽器驗收 §5d（選角途中）與 §9c（選完）都把頭像上的位置碼與摘要的中文路名
做映射比對，任何一格不同就紅。

## 3. 隊伍面板：兩個召喚師技能並排

原本兩格是**上下疊**在頭像旁的窄欄、14px 見方，手機上第二格幾乎讀不出來
（Ray 回報「只看得到第一個」）。

改成並排、放大到 16px、三個分支（有技能／reserved／無資料）**等大**，
整欄 `flexShrink: 0` ⇒ 不擠壓名稱、血條或狀態標籤。

**實測（瀏覽器量到的真實幾何，不是宣稱）**：
兩格 18×18、`y` 相同 `x` 不同（確實並排）、血條仍有 **128px** 可讀寬度、
兩格都是真技能（`flash` / `teleport`，不是 reserved 佔位）。

詳細面板（`BattleHeroSheet`）維持完整名稱、即時冷卻；
方格 tooltip 另外帶「本場已用 N 次」。

## 4. 快速完成戰鬥：改為單一 feature flag

按鈕本來就在（`isDebugMode()` 閘門）。問題是那道閘門的語意是
「現在是不是測試模式」，不是「這個開發工具還要不要留」——兩件事混在一起，
正式上線前得回頭翻每一個使用點才知道要拿掉什麼。

新增 `src/featureFlags.js`，兩道閘門並存：**測試模式 且 `devFastForward` 為真**。

| 項目 | 內容 |
|---|---|
| 開關位置 | `src/featureFlags.js` → `FEATURE_FLAGS.devFastForward`（單一位置，改 `false` 即整個關閉） |
| 用途 | 驗收與手測時不必等 20–30 分鐘模擬跑完 |
| 移除時機 | 正式上線前，且驗收腳本改用其他方式推進比賽之後，連功能本體與旗標一起刪 |

## 6. 驗收腳本踩坑（第五、六次，都不是產品問題）

這一輪最花時間的不是功能，是**讓「技能事件命名正確」這條驗收穩定下來**：

| 嘗試 | 結果 | 為什麼 |
|---|---|---|
| 在現場戰鬥取樣戰報 | 桌機 0 筆、手機 2 筆（同一份程式碼） | 戰報只留最近 11 筆，前幾分鐘幾乎沒有技能事件（第一顆懲戒約 60–90 模擬秒） |
| 改到 Replay 播放後取樣 | 桌機 0 筆、手機 2 筆 | 結果取決於取樣窗剛好落在哪一段 |
| **逐格拖時間軸掃過整場（41 個點）** | **桌機 13 種、手機 18 種** | 完全決定性，整場都掃得到 |

最終資料同時是「戰報命名正確」的鐵證——舊碼把所有技能都寫成「懲戒」，
而現在抓到的分佈是：

```
懲戒 → 只在 B2/R2（打野）　點燃 → 中路　治療 → 下路　傳送 → 上路　幽魂 → R1
```

每一筆都通過「這個席位真的帶著這個技能」的比對。

**教訓（延續 I-close、J）：驗收腳本不要靠取樣運氣，能 seek 就 seek、能列舉就列舉。**

另外，本輪 verifier 自己也踩了兩次關鍵字掃描（頭像 testid 是條件式寫法、
方格尺寸的正則沒容忍空白）——都是我自己的斷言 bug，已修並在教訓裡登記。
