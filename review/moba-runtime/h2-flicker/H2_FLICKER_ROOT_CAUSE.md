# H.2-flicker — Runtime 動態物件閃爍：根因分析與修正

日期：2026-07-29｜狀態：**已找到根因並修正，但尚未取得真實 Android 裝置的肉眼確認**
⇒ 依指示**不宣稱已修復**、**未 push**、**未部署**。

## 0. 先更正上一輪的錯誤結論

H.2-close 曾回報「閃爍已修」。**那個結論不成立**，判準本身就是錯的：
當時是每 **600 毫秒**取樣一次 `visible` 欄位，而閃爍是**單幀或數幀**的消失重現——
取樣頻率比事件本身慢一個數量級，幾乎不可能抓到。用它得出「沒有閃爍」等於沒驗。
本輪一律改成**逐幀**統計（由頁面自己在每個 rAF 累計，工具只讀彙總）。

## 1. 真正的根因：**深度緩衝精度不足 ⇒ 共面貼花 z-fighting**

透視深度的解析度：`Δz ≈ z²(far − near) / (far · near · 2^bits)`

| 條件 | Δz（視線距離 175） | 場景需要分開的高度差 |
|---|---|---|
| 舊值 near=1 / far=4000，**24-bit**（桌機） | 0.0018 | 地面鋪層間距 0.02–0.04｜選取環 0.35｜塔環 0.11｜目標環 0.09 |
| 舊值 near=1 / far=4000，**16-bit**（Android 常見） | **0.4672** | 同上 ⇒ **比所有間距都大** |

也就是說：在 16-bit 深度的裝置上，**地面鋪層、岩塊投影、選取環、塔環全部塌進同一個
深度桶**，逐幀在彼此之間搶贏 ⇒ 畫面上就是「一閃一閃、瞬間消失再出現」。
桌機拿到 24-bit，同一份程式碼怎麼看都正常——**這正是「桌機沒事、真機在閃」的成因**，
也是為什麼 scene graph 的 `visible` / key / mount 全部正常也照樣會閃：
**它是每像素的深度比較結果在跳，不是邏輯狀態在跳。**

### 1.1 可控重現（不是推論）

把相機 `near` 暫時降到 0.01（等效在 24-bit 桌機上模擬 16-bit 的精度崩潰）：

| 量測 | 正常設定 | 降低精度（重現） |
|---|---|---|
| 逐幀 scene graph（消失／NaN／重掛） | 全部 0 | **仍然全部 0** |
| 畫面像素振盪（靜止相機） | 0.036% | **4.59%（128×）** |

⇒ 證實兩件事：(a) 這個病灶用 scene graph 永遠驗不到；(b) 它確實由深度精度造成。
熱區圖 `heatmaps/01_repro_低深度精度_閃爍熱區.png` 顯示閃的是**岩塊地面投影
（`rock_shade`）等共面貼花**與**英雄選取環**——正是「幾乎與地面同高」的那些東西。

### 1.2 還有一個讓修正無效的坑

`RuntimeCamera` 的每幀迴圈裡寫死了 `camera.near = 1; camera.far = 4000;`，
把 Canvas 的相機設定整個蓋掉 ⇒ **改 `CAM.near/far` 完全不會生效**
（診斷探針讀回來仍是 1/4000）。這一行不修，上面的分析改了也是白改。

## 2. 修正內容

| # | 修正 | 檔案 |
|---|---|---|
| 1 | 相機 `near 1→35`、`far 4000→1000`（far/near 4000→28.6）⇒ 16-bit 下 Δz 從 0.467 降到 **0.0129**，低於最小層距 0.02 | `MobaRuntimeView3D.jsx` |
| 2 | 移除每幀硬寫 `camera.near=1/far=4000` 的覆蓋，改讀 `CAM` | `MobaRuntimeView3D.jsx` |
| 3 | 地面貼花（英雄選取環、陣亡標記、塔環、大型目標環）改用 **polygonOffset**——單位是**深度緩衝的最小可解析差**，與位元深度無關，是貼花的標準解法。⚠ 刻意**不**關 `depthTest`（關掉會讓環穿透牆與塔） | `MobaRuntimeHeroes.jsx`、`MobaRuntimeStructures.jsx` |
| 4 | 內插退路不再跳到 snapshot 位置，改**維持上一幀已驗證的位置** | `MobaRuntimeView3D.jsx` |

### 2.1 關於第 4 項：這是我自己在 H.2-close 引入的缺陷

H.2-close 為了避免內插切過牆角，加了「內插點不可走時退回 snapshot 位置」。
但 snapshot 位置就是這段內插的**終點**：`a` 逐幀由 0 增到 1，只要中段有一小截落在
不可走區，那幾幀就會被丟到終點、下一幀又回到中途 ⇒ 位置序列變成
「前進 → 跳到終點 → 退回」，肉眼就是英雄在抖。
改成維持上一幀後位置保持單調，而上一幀本來就通過過可走判定 ⇒ 仍不會穿牆。

## 5. 關於像素級指標：**只當診斷，不當通過門檻**（誠實說明）

我試著用「靜止相機下逐像素比對」當硬性門檻，但**做不到可靠**，原因如下，
所以不拿它宣稱通過：

- **刻意的動畫**會被算進去：塔冠每幀旋轉並上下浮動、英雄持續移動。
  相鄰兩幀差異圖（`heatmaps/04_...png`）顯示逐幀變化幾乎**全部**落在這兩者身上。
- **HUD**：計時器每秒跳、LIVE 指示閃、戰報捲動。實測最大熱點在畫面左上角 `y=0`
  的 HUD 邊緣，根本不是 3D 場景。
- **錄影本身**：JPEG 量化會隨鄰近內容變動而改變，靜態區域也會出現數十階跳動。

已嘗試：遮蔽 HUD（DOM bounding rect）、遮蔽會動的物件（英雄與塔冠的投影位置，
本次遮掉 38–66%）、提高錄影品質到 95、加上振幅（≥26 階）與頻率（10 幀內 ≥4 次）條件。
殘餘仍有數個百分點 ⇒ 不足以當判準。**真正的把關交給 §3 §4 的逐幀統計與深度精度門檻，
肉眼確認交給真實 Android 裝置。**

對照組數據仍保留（同一套指標、同一組條件）：
降低深度精度時 0.1059%，修正後 0.0063–0.0336% ⇒ 相對關係與根因一致。
