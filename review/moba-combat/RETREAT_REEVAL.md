# 撤退僵硬行為：根因、四組實驗、與最終修法（Retreat Re-evaluate v1）

**日期**：2026-08-10
**問題陳述**：英雄一旦撤退，幾乎都一路回泉水補滿才重新投入，行為過於僵硬。
**結論**：🔴 **根因已確認並可修正，但實作觸發了新的結構性紅燈 ⇒ 預設關閉、不發布。**
`retreatReevalV1: false`。開啟時破壞兩支**公平性**驗證器（`ability_p02` 5b、`quality_p03`），
根因與修法方向已定位（見 §7），需要另一輪授權才實作。

## 1. 根因（已證明，非推測）

### 1-1 狀態機的不對稱

`LogicEngine.js` 撤退狀態機只有兩條路：

```js
if (p.hp < p.maxHp * retreatAt)      { p.retreating = true; }
else if (p.hp >= p.maxHp * returnAtEff) { p.retreating = false; }
```

| | 進入 | 離開 |
|---|---|---|
| 門檻 | `retreatAt` | `returnAtEff` |
| 性質 | **動態**，被暫時性事件灌高 | **固定**（0.60；到泉水附近變 0.88） |
| 組成 | base +0.06、爆發 **+0.16（4 秒窗）**、人數劣勢 +0.12、連死 +0.08、落後 +0.05、支援 −0.05、逃生 −0.03 | 常數 |
| 重新評估 | — | **不存在** |

⇒ **用暫時性條件進場，用固定高門檻離場，中間沒有任何重新評估。**

### 1-2 量化證據

`tools/probe_retreat_trigger.mjs`（純觀測、決定性，10 seeds × 鏡像、**1273 段完成的撤退**）。
核心手法：`p.dbgRetreatAt` 是引擎每 tick 實際採用的門檻，撤退中照樣更新
⇒ 可逐 tick 問「這一 tick 若沒在撤退，會不會被觸發？」

| 觀測 | 數值 |
|---|---|
| 觸發理由 **短期換血吃虧**（`burstRetreatBonus`，4 秒窗） | **78%** |
| 觸發當下平均血量 / 平均採用門檻 | 34.1% / **43.9%** |
| 觸發當下**身邊沒有敵人** | **46.3%** |
| 觸發當下血量就已高於門檻（＝純暫時性條件推出來的） | 11% |
| **撤退期間門檻曾經解除** | **99.8%** |
| 撤退期間敵人曾經清空 | 99.3% |
| **門檻解除 → 實際離開** | **平均 10.0 秒／中位 7.0 秒** |
| 敵人清空 → 實際離開 | 平均 17.0 秒 |
| **僵硬段佔整段撤退** | **54.1%** |

⇒ 超過一半的撤退時間，花在「危險早就解除了還在往家跑」。

### 1-3 這不是「終點是泉水」的問題

先前一輪曾假設根因是「撤退終點只有泉水」，並嘗試四種改終點／改恢復速率的修法，
全部失敗（見 `RETREAT_CHAIN_FIX.md`）。本輪證明**終點不是根因**：
在 34% 的平均觸發血量下回家補滿本來就是合理的 MOBA 行為。
真正僵硬的是**血量還健康、卻被 4 秒爆發窗推去回家**那一批。

## 2. 修法：Retreat Re-evaluate v1

沿用本專案既有範式——Combat Decision C 的遊走是「承諾 → 每 6 秒重評（取消／改道）」、
`_joinV3` 用 `joinEvalPeriod`、回城中斷用 `recallCd` 冷卻防 retry-thrash。
**撤退是唯一沒有重評的承諾行為。** 只加「取消」，不改終點、不改回血、不擲骰。

```js
if (R.retreatReevalV1 && p.retreating && this.t >= p.retreatEvalT
    && this.t >= p.retreatCancelCdAt) {
  p.retreatEvalT = this.t + R.retreatReevalPeriod;
  const clear     = 附近 retreatCancelSafeDist 內無敵人;
  const recovered = hp >= max(當下 retreatAt + margin, retreatCancelMinHp);
  const enRoute   = 離泉水 > retreatCancelHomeDist;
  if (clear && recovered && enRoute) { 取消撤退; 進入冷卻; }
}
```

| 常數 | 值 | 作用 |
|---|---|---|
| `retreatReevalPeriod` | 3 秒 | 週期性重評（不是每 tick）⇒ 不抖動 |
| `retreatCancelSafeDist` | 12 | 真的脫離了，不是還在被追 |
| `retreatCancelMargin` | 0.05 | 高於**當下**門檻＋餘裕 ⇒ 取消後不會立刻再觸發 |
| `retreatCancelMinHp` | **0.45** | 絕對地板：真的打得動才回去 |
| `retreatCancelCd` | **45 秒** | 取消後冷卻 ⇒ 打斷限制環 |
| `retreatCancelHomeDist` | 12 | 已到泉水就不取消（補給有始有終，那段本來就快） |

⚠ 觸發分支每 tick 都會把 `retreatEvalT` 往後推 ⇒ **血量仍低於門檻時不會重評**
（還在危險裡，沒有取消的道理）。取消檢查因此自然只在「已脫離」時發生。

## 3. 四組實驗（2×2）——為什麼最終是這組參數

兩個失敗模式互相拉扯，只有一格同時通過：

| | 無冷卻 | 有冷卻 |
|---|---|---|
| **低地板 0.36** | **v1**：節奏過（15/15、8/8），但**死亡 +11.7%、15 秒內再撤 3.4%→18.0%（+425%）** | **v4**：節奏崩（13/15、6/8） |
| **高地板 0.45** | **v2**：**限制環**——血量卡 45–60%，取消→回去→被消耗→再撤→又取消，一場打不完（45.0 分 = 上限）。節奏崩（13/15、6/8） | ✅ **v3：全部通過** |

**v1 的教訓**：取消條件不該是「不會再觸發撤退」（36% 血），而該是「**真的打得動**」。
**v2 的教訓**：只加地板會製造限制環——需要冷卻打斷。
**v4 的意義**：低地板即使有冷卻仍崩 ⇒ 地板是必要條件，不是可調參數。

⚠ v1 過而 v4 崩（同地板、只差冷卻）顯示 `regress` 的 15 seeds 對行為改動有
**種子層級的混沌敏感性**。因此本輪不對節奏門檻做微調式擬合，只採唯一全綠的組態。

## 7. 🔴 阻斷發布的新結構性紅燈：陣列順序公平性

### 7-1 現象

開啟 `retreatReevalV1` 後，Release Gate 出現**兩支新紅燈**（皆為公平性斷言）：

```
❌ ability_p02  5b) 雙方同能力 → 兩邊本場等級接近　平均等級差 1.56
❌ quality_p03  （同一族：A/B 雙方皆真實能力下的對稱性）
```

**已確認是本次改動造成**（單一變因）：

| `retreatReevalV1` | `ability_p02` |
|---|---|
| `true` | **19/20 FAIL** |
| `false` | **20/20 PASS** |

### 7-2 根因

取消條件裡的這一行在**循序移動迴圈中讀取敵方位置**：

```js
const clear = !alive.some((q) => q.side !== p.side && dist(q.pos, p.pos) < R.retreatCancelSafeDist);
```

兩相 tick 只保證「全員先移動、再全員交戰」，**移動迴圈本身仍是依陣列順序逐一更新 `p.pos`**。
⇒ 先迭代的一方讀到對方的**舊位置**，後迭代的一方讀到**已移動的新位置**
⇒ 兩邊的取消時機系統性不對稱 ⇒ 累積成本場等級差。

這個失敗族 codebase 已經記載過（`LogicEngine.js:3460`）：

> 追擊**維持**判定（取得已移到 `_postCombatV3`——在全員移動與傷害結算完的**凍結位置**上判定，
> 否則先迭代方用敵方舊位置搶先取得追擊，**實測會累積成 ~17pp 的系統性順序優勢**）

⇒ 與 **TD-21**（`runtime29` §29 順序公平性）同一族問題。

### 7-3 修法：已實作並**驗證有效**

新增 `_retreatReevalV3(alive)`，由 `_postCombatV3` 在**全員移動與傷害結算完的凍結位置**上
呼叫，並沿用同檔既有的 **collect-then-apply**（先收集決策、再一起套用）
⇒ 連同一相位內也不受迭代順序影響。

**結果：順序公平性紅燈消除。**

| | `ability_p02` |
|---|---|
| 決策迴圈內判定（原實作） | ❌ 19/20（等級差 1.56） |
| **凍結位置 + collect-then-apply** | ✅ **20/20（功能開啟下）** |

⚠ 這個技法對 **TD-21** 應同樣適用（同一失敗族），是本輪可複用的成果。

### 7-4 🔴 但仍有第二道紅燈：能力優勢放大

順序公平性修好之後，換 `quality_p03` 擋下來：

```
❌ §4-5c 等級差距不誇張（≤ 2.5 級）　差 3.79 級
❌ §4-6c 勝率不得過度偏斜（≤ 85%）　88.9%
✅ §5b  能力對調 ⇒ 優勢跟著換邊　藍高 +4.04 級／紅高 +2.86 級
```

§5b 顯示**方向是對稱的** ⇒ 這**不是**順序 bug，而是實質效果：
**取消撤退對「撤退次數多的一方」得益更大，而那正是高能力隊**
（decision +16.4%★、positioning +21.3%★ 的撤退段落數）。

語意上這說得通（會撤退的人更能從「聰明地取消撤退」獲益），
但專案有明確的「能力不得無限疊加優勢」護欄，**不得為了讓測試變綠而放寬**。

另外 `experience26` §17（**TD-19**，replay 容量）也被推過上限：
比賽略微變長 ⇒ 670 frames / 1974KB。這是既有紅燈被邊際觸發，非新結構問題。

### 7-5 目前狀態

`retreatReevalV1: false` ⇒ 引擎行為與本輪之前**完全相同**，Gate 回到既有狀態
（唯一紅燈為既有的 TD-21）。程式碼、常數與完整調查保留，開啟即可重現。

## 10. TD-21 已解決（2026-08-10）——但根因不是引擎

追 TD-21 時發現它**不是引擎缺陷，是檢定力缺陷**。

`runtime29` §29 斷言「反序後藍勝位移 ≤15pp」，但只用 **40 seeds**，
其配對二項噪音底線就有 **±20pp** ⇒ **檢定分不出「20pp 位移」與「0」**。

`tools/probe_order_fairness.mjs` 實測（v2、同一批 seed、正序 vs 反序）：

| n | 藍勝(正序) | 藍勝(反序) | 位移 | 噪音±95% | 不一致對 | McNemar p |
|---|---|---|---|---|---|---|
| 40 | 45.0% | 62.5% | 17.5pp | ±20.2pp | 5/12 | 0.146 |
| 80 | 51.2% | 56.3% | 5.0pp | ±14.3pp | 15/19 | 0.607 |
| 120 | 52.5% | 56.7% | 4.2pp | ±12.1pp | 25/30 | 0.590 |
| 160 | 54.4% | 56.9% | 2.5pp | ±10.4pp | 34/38 | 0.724 |
| **200** | 56.0% | 57.5% | **1.5pp** | ±9.1pp | 42/45 | **0.830** |

位移嚴格依 **1/√n 收斂到 ~0**、McNemar 全程不顯著
⇒ **沒有任何一方系統性佔便宜**。這正是 `runtime29` 自己記載的
「rng 抽樣順序跟著 players 迭代順序走 … 那是**混沌**，不是**偏差**」。

**修法：`ORDER_SEEDS` 40 → 160。門檻一個都沒動**（仍是 ≤15pp 且兩者在 30–70%）。
噪音底線降到 ±10.4pp，安全低於門檻 ⇒ 真有 15pp 系統性偏斜時這個檢定才抓得到。
**這是提高檢定力，不是放寬門檻。**

⇒ `runtime29` **首次 PASS（35/35）**，Release Gate 首次全綠。

### 10-1 這也修正了一條長期誤解

TD-21 被當成「引擎有順序偏差」掛了很久，並被我在前幾輪引用為「既有技術債」。
實際上引擎在這一項是公平的；紅燈來自量測設計。
與本輪 `towerPushes` 的教訓同源：**先確認指標量得到它宣稱要量的東西。**
