# Combat Decision B — Teamfight Commitment（團戰投入決策）

2026-08-08｜取代 `TEAMFIGHT_SYNC_SPEC.md`（該檔保留為歷史記錄，見 §1）

---

## 1. 前身：Synchronization 假說已被實測否決（**保留為設計決策證據，不得刪除**）

B 原本定義為 **Teamfight Synchronization**，根因假說是
「`_joinV3` 是每人各自獨立的黏性擲骰，沒有任何一行讓五個人『一起』到」。

該假說在程式碼層面成立，**但在行為層面不構成可量測的問題**。

### 否決證據

**(a) 抵達本來就幾乎同步**

| 量測 | 值 |
|---|---|
| `tfArrivalSpread`（主群抵達離散度） | **≈ 1.08 秒** |
| `tfPeakMean`（峰值參戰人數） | **3.79 – 3.82 / 5** |

**(b) 同步閘實作後，synergy 完全失效**

30 seeds × 鏡像，synergy 40 vs 90：**60 場中 59 場逐場完全相同**
（勝負、K/D、時長皆同）。所有指標 Δ 為 0 或不顯著。

閘門幾乎從不啟動：`tfHeld` 0.47–0.53 tick/場、`tfReleasedSync` 0.35、
`tfReleasedTimeout` 0.00–0.07。
原因：兩條防呆（已在戰場半徑內不攔、有隊友在打就放行）在絕大多數情況直接生效——
`hot` 本來就是由**已在交戰的人**算出來的重心，「有隊友在打」幾乎恆真。

⇒ **比改動前更糟**：synergy 原本至少有可量測（雖然有害）的效果，實作後完全沒有。

**(c) 真正的機制是「投入更多、換得更差」**

`r3_teamfight`（改動前）：

| synergy | 團戰段落 | 每場團戰死亡 | 每場團戰擊殺 | **交換比** | 參團命中 |
|---|---|---|---|---|---|
| 40 | 21.45 | 0.545 | 0.575 | **1.054** | 79.7% |
| 70 | 21.52 | 0.584 | 0.584 | **1.000** | 82.8% |
| 90 | 22.07 | 0.626 | 0.583 | **0.931** | 86.9% |

團戰次數幾乎不變（+0.6），但**每場團戰死亡 +15%、擊殺僅 +1.4%，
交換比單調惡化 1.054 → 0.931**。

⇒ 不是「一個一個走進去被各個擊破」，而是
**把更多身體投入同一場團戰，卻換不到更好的結果**。

### 判定

> **B-4 gate：Synchronization hypothesis — FAIL。**
> 不得再以調整 `tfHeld` / `tfReleasedSync` / `tfReleasedTimeout` / 等待窗
> 的方式硬做出效果。

⚠ 誠實揭露該指標的缺陷：`tfArrivalSpread` 以 `fightHoldT` 當叢集窗，
超過窗的落後者會被算成**另一個段落**而非「離散」，
因此 1.08 秒對「拖後腿的人」是**系統性低估**。
它足以支持「主群同時到」，**不足以完全排除長尾**。

## 2. 新定義

> **B = 隊伍是否應該承諾投入這一場團戰。**

`joinAdj` 保留「**傾向**參與戰鬥」；新增作用點處理
「**已有參戰意圖後，這一場值不值得真正投入**」。

決策三態：**commit / hold / decline**。

### 評估項（全部用引擎既有狀態，決定性、不消耗 rng）

| 因子 | 來源 |
|---|---|
| 當地友軍人數 | `alive` 中同側、距 `hot` < `commitLocalR` |
| 預計參戰友軍 | 同側、`q.joinGo` 為真且 ETA ≤ `commitEtaMax` |
| 敵軍人數／集結程度 | 異側、距 `hot` < `commitLocalR` |
| 自身與友軍血量 | `q.hp / q.maxHp` |
| 局部人數優劣 | 上述人數差 |
| 合理交戰條件 | 有效戰力比（人數 × 平均血量）對門檻 |

### synergy 的新語意

**`commitAdj`** ＝ 隊伍**共同投入判斷的品質**，**不是**抵達時機。

- **高 synergy** ⇒ 門檻更嚴：明顯不利的團戰**不投入**（decline），
  邊際情況先等隊友（hold），有優勢才 commit
- **低 synergy** ⇒ 門檻寬鬆：有意圖就進場（≈ 改動前的行為）
- **中性（70）** ⇒ 基準門檻

⚠ **不得讓 synergy 單純增加 join volume。** 團戰次數**不要求**隨 synergy 單調上升。

## 3. 紅線（沿用原規格，未變）

不得改：傷害公式、經濟、等級曲線、A 的 retreat/push、C 的 roam、
CS / UI / 3D / 英雄模型 / 地圖；不得大幅重構；
不得靠增加傷害／經濟／等級達成驗收。

## 4. 驗收（B′-1 ~ B′-10）

情境 `teamfight`，30 seeds × 鏡像，raw sample ＋ **配對檢定**。

| # | 斷言 |
|---|---|
| **B′-1** | 中性紅線：`toPlayerMods(全70)` 與 `NEUTRAL_MODS` 逐鍵逐序相同；注入全 70 ⇒ 逐位元 == feature off |
| **B′-2** | 團戰次數**不要求**隨 synergy 單調上升（明確允許持平或下降） |
| **B′-3** | **不利團戰的投入率隨 synergy 顯著下降**（主要目標） |
| **B′-4** | **每場團戰交換比（k/d）隨 synergy 改善，或至少不惡化** |
| **B′-5** | solo／無支援進場隨 synergy 下降 |
| **B′-6** | 死亡不得隨 synergy 顯著上升 |
| **B′-7** | 推塔不得顯著下降 |
| **B′-8** | 撤退／作戰持續／重返不得顯著變化（**不污染 A**） |
| **B′-9** | 遊走指標不得顯著變化（**不污染 C**） |
| **B′-10** | 固定 seed 重跑一致；不新增 rng 抽樣；既有套件全綠 |

⚠ **B′-4 是成敗判準**：現況交換比是 1.054 → 0.931（反向）。
若新模型無法讓它至少持平，代表根因仍不在投入決策層，**應再次停止並重新診斷**。

## 4.5 實作結果（2026-08-08）

### 校準過程（三步，每步都有實測依據；留存以免重蹈）

| 版本 | `commitAdv` / `Gain` | B 效果 | pacing（regress2） |
|---|---|---|---|
| 第一版 | −0.12 / 0.35 | ✅ 不利投入 28.3%→8.7%★ | ❌ **6/8**：一場打不完、最長 45 分 |
| 第二版 | −0.45 / 0.35 | ❌ 三格 decline 全 ≈0 | ✅ 8/8 |
| **最終** | **−0.45 / 1.40** | ✅ 不利投入 36.7%→16.3%★ | ✅ 8/8 |

⚠ **根因**：本模型是**引擎預設**，中性＝未注入能力層。中性若會拒戰，
**雙方都不開打 ⇒ 比賽拖死**。拒戰必須是「高 synergy 才有的能力」，
因此中性門檻必須壓到幾乎不拒戰（−0.45），再用大槓桿（1.40）把 90 分拉回有效區間（−0.123）。

⚠ **代價**：40 分的門檻落到下限 −0.60，與 70 分的 −0.45 差距很小
⇒ **低 synergy 幾乎沒有可量測的懲罰**。這與 audit §1-C 記錄的
「base = 0 單向解鎖」是同一個性質，B 現在也有。

⚠ **另一個踩過的坑**：`tfObs` 原本只在 `configureMatch` 初始化，
但 `_joinV3` 在**不帶戰術**時也會執行 ⇒ `regress` / `regress2` / `credibility`
全部丟 `Cannot read properties of undefined`。已移到 constructor。
**引擎預設模型的容器一律要在 constructor 就存在。**

### 最終結果（`r8_teamfight`，30 seeds × 鏡像 = 每格 60 場）

| 指標 | 40 | 70 | 90 | 配對 Δ(90−40) | 顯著 |
|---|---|---|---|---|---|
| **不利投入率** | 36.7% | 37.5% | **16.3%** | −1.717 [−2.310, −1.124] | **★** |
| decline | 0.00 | 0.02 | 0.78 | +0.783 [0.356, 1.211] | ★ |
| hold | 0.07 | 0.00 | 1.73 | +1.667 [1.032, 2.301] | ★ |
| commit | 7.27 | 7.38 | 5.82 | −1.450 [−2.622, −0.278] | ★ |
| 團戰次數 | 21.77 | 21.73 | 21.18 | −0.583 | · |
| 死亡 | 12.70 | 12.78 | 12.10 | −0.600 | · |
| **擊殺** | 12.68 | 12.78 | 11.65 | **−1.033** [−1.904, −0.163] | **★** |
| **交換比** | 0.9987 | 1.0000 | 0.9628 | **−0.0535** [−0.140, +0.033] | · |
| 推塔 | 31.37 | 31.37 | 31.30 | −0.067 | · |
| 勝率 | 48.3% | 50.0% | 40.7% | −7.6pp | · |

### ⚠ 判定：**決策層達成，結果層未兌現**

- **決策層**：不利投入率 36.7% → 16.3%（★），decline / hold 顯著上升 ⇒ **B′-3 核心目標達成**。
- **結果層**：交換比的**點估計轉為負**（−0.0535，CI 含 0），擊殺**顯著下降**（−1.033 ★），
  勝率在 90 分最低（40.7%，不顯著）。
  ⇒ **高 synergy 確實避開了不利團戰，但沒有因此打得更好，只是打得更少。**

⚠ B verifier 15/15 通過，是因為 B′-4 的斷言是「未惡化（CI 含 0）」而非「改善」。
**不得把 B 宣稱為「改善了團戰結果」。** 正確的說法是
「減少了不利投入（顯著），但未能將其轉換為結果優勢」。

⚠ **中間版本的資料一律作廢**：`r6_teamfight`（`commitAdv −0.12`，pacing 6/8）
與 `r7_neutral` / `r7_roam` / `r7_split` 都跑在已不存在的程式狀態上。以 `r8_*` 為準。

## 5. Telemetry

沿用：`tfEpisodes`、`tfWonRate`、`tfSoloEntry`、`tfEntries`、`tfReadyAtEngage`。

新增（純觀測）：

| 欄位 | 定義 |
|---|---|
| `tfCommit` / `tfHold` / `tfDecline` | 三態決策各自次數 |
| `tfBadCommit` | **投入當下有效戰力比低於 1.0** 的次數（＝不利團戰投入） |
| `tfBadCommitRate` | `tfBadCommit / tfCommit` ⇒ **B′-3 的主指標** |
| `tfExchange` | 每場團戰的 Δ擊殺 / Δ死亡 ⇒ **B′-4 的主指標** |

⚠ `tfArrivalSpread` / `tfHeld` 等同步指標**保留但降為參考**，不再作為驗收依據。

## 6. 架構決策（沿用 C 與原 B 的決定，未變）

- **引擎預設模型**：未注入能力層時也走同一套（以中性參數運作）
- **synergy 已移出 `joinAdj`**（0.19 → 0.15；四項各自絕對權重未變）
- `NEUTRAL_MODS` 鍵順序必須與 `toPlayerMods()` 一致（`stats28` §9 對順序敏感）
