# 量測方法警語

---

## 🔴🔴 第一原則（2026-08-09）：**summary counter ≠ gameplay outcome**

**在把任何 `exec` / 彙總計數器當成「效果」之前，先讀它的遞增條件。**

這條原則是踩到坑之後才寫的。`exec[side].towerPushes` 被當成「推進強度」用了整整一輪，
所有「撤退越多推得越少」的結論都建立在它上面。它的真身是（`LogicEngine.js:2389`）：

```js
if (K && this.t - S.pushTick > 10) { S.pushTick = this.t; this.exec[p.side].towerPushes++; }
```

- `S = this._tac[p.side]` ⇒ **隊伍層級**，不是個人層級
- **每 10 秒最多 +1**（節流）⇒ 上限 ≈ `場長秒數 / 10`（23 分鐘的比賽約 134，實測約 29 ⇒ 責任週期 22%）

⇒ 它量的是「**有多少個 10 秒窗口，這隊至少有一個人碰到塔**」——一個
**責任週期 / presence** 指標。五人猛拆與一人慢磨，計數完全相同。

### 後果：撤退變多會壓低計數器，但不代表推塔輸出下降

撤退變多 ⇒ 同時站在塔邊的人變少 ⇒ 某些 10 秒窗口沒人碰塔 ⇒ 計數器掉。
但那五個人各自的 `p.twrDmg` 總和**未必**下降。實測（12 seeds、standard）三項全部分歧：

| 素質 | `towerPushes`（計數器） | **`twrDmg`（真實輸出）** |
|---|---|---|
| decision | −5.9% · | **+7.9% ·（方向相反）** |
| positioning | **−7.3% ★** | −3.0% ·（不顯著） |
| clutch | **+20.2% ★** | +5.2% ·（不顯著） |

**只有計數器達到顯著，真實推塔傷害一項都沒有。**

### 強制規則

1. **推進強度的主 KPI 是 `p.twrDmg`**（個人推塔傷害，`LogicEngine.js:122/2387`），
   輔以「推掉的塔數」與「主堡傷害」。
2. `towerPushes` **降級為 presence / 節奏診斷指標**。引用它時必須寫成
   「塔邊責任週期」或同義的名字，**不得**寫成「推塔」「推進」。
3. 任何 `exec.*` 計數器在首次使用前，必須在報告裡註明三件事：
   **層級（個人/隊伍）、遞增條件、有沒有節流或上限**。
4. 同類已知陷阱：`splitPushActions`（8 秒節流、隊伍層級）、
   `dragonContests` / `baronContests`（只在 `tacticOn` 時計、門檻是「至少 1 人到場」
   而非「集結」）、`invadeKills`（實測 319 次入侵 0 擊殺 ⇒ 有計數但無後果）。

### 工程規則 2：長 verifier 一律走 verify runner，禁止直接巢狀 fan-out

與上一條同源——**「看起來像失敗」不等於「失敗」**。

- `check_moba_runtime29` 直接跑會展開 **63 個子行程** ⇒ **跑不完**；
  `check_moba_stats28` 直接跑約 **87 分鐘**。
- 這些腳本的 `ck()` 是 `A.push([n, !!c])`，**累積到最後才一次印出**
  ⇒ 執行中 log 是 0 bytes **屬正常**，不得用 stdout byte 數判斷是否卡住。
- 舊逾時值會把還在正常跑的子驗證器砍掉，回報成 `exit=-1` ＋空 stdout，
  **看起來像斷言失敗**（`check_moba_runtime29.mjs:428` 已記錄此誤判）。

**正確跑法**：`node tools/verify.mjs --only=<id>` / `--resume` / `--list`。
runner 對每個子行程設 `ESMO_VERIFY_FLAT=1`，讓 fan-out 腳本跳過巢狀子驗證
（那些子項目 runner 已各跑一次）；被跳過的標成 **SKIP 且排除在分母外**。
每段跑完即寫 `tools/.verify-state.json`，可 `--resume` 續跑。

**實測對照（2026-08-09）**：

| verifier | 直接跑 | 走 runner（FLAT） |
|---|---|---|
| `experience26` | 逾時（>10 分無輸出） | **7 秒　29/29 PASS** |
| `stats28` | 約 87 分鐘 | **226 秒　21/21 PASS** |
| `runtime29` | 跑不完（63 子行程） | **47 秒　34/35 FAIL（TD-21）** |

⚠ 長驗證的回報**必須保存完整 log 與 checkpoint**，
不得只記最後一行 assertion count；被 timeout／中止／0 stdout 的一律標
**NOT RUN 或 TIMEOUT，不得標 PASS**。

### 這條原則的一般形式

> **計數器是為了「診斷」寫的，不是為了「衡量效果」寫的。**
> 節流、隊伍層級聚合、飽和上限——每一個都會讓計數器與真實產出脫鉤，
> 而脫鉤時**計數器往往仍然單調且顯著**，看起來像是很乾淨的證據。
> 判斷方法只有一個：找出對應的**連續型真實產出欄位**，兩者一起量，看會不會分歧。

## 🔴 最重要（2026-08-09）：「中性情境」不是正式遊戲的條件

**這是本檔目前最會誤導人的一點，先讀這節再讀其他任何結論。**

`LogicEngine._neutralKnobs()`（`:284`）與正式對局實際使用的 knobs 差在三個欄位：

| knob | `_neutralKnobs()` | 正式 `STANDARD_OPP_TACTIC` | 各戰術預設範圍 |
|---|---|---|---|
| `roamRate` | **0** | **0.3** | 0.15 – 0.7 |
| `invadeChance` | **0** | **0.1** | 0.1 – 0.35 |
| `splitPush` | **0** | **0.1** | 0.05 – 0.85 |

正式流程：`useLocalServer.js:191` → `configureMatch({ blue: toEngineTactic(opts.tactic),
red: toEngineTactic(STANDARD_OPP_TACTIC) })`。**每一場真實對局都走這條**，
`_neutralKnobs()` 只在「某一側傳 null」時才會被用到（`LogicEngine.js:298`）。

⇒ 中性情境是實驗室條件，**不是遊戲裡會出現的狀態**。

### 這三個 0 關掉了六個作用點

| 作用點 | 權重 | 被哪個 0 關掉 |
|---|---|---|
| `roamSightAdj` | mapAware +0.350 | `roamRate = 0` |
| `roamInfoAdj` | comms +0.360 | `roamRate = 0` |
| `roamGateAdj` | decision +0.120 | `roamRate = 0` |
| `roamFollowAdj` | leadership +0.120 | `roamRate = 0` |
| `invadeAdj` | courage +0.080、mapAware +0.060 | `invadeChance = 0` |
| `splitAdj` | adaptability +0.080、decision +0.060、courage +0.050、focus +0.040 | `splitPush = 0` |

`roamInfoAdj` (0.36) 與 `roamSightAdj` (0.35) 是**全表最大的兩個權重**，
在中性情境下完全不執行。

### ⇒ 解讀規則（強制）

1. **中性情境量到「沒有差異」，對這六個作用點而言不代表「素質沒用」**，
   只代表**實驗條件把作用點關掉了**。`leadership` 尤其嚴重：它在 `STAT_MAP`
   裡唯一的條目就是 `roamFollowAdj`，中性情境下個人層作用點**一次都沒執行**
   （`r2_objective` / `r10_objective` 量到的效果全部來自 team-level 的
   `TEAM_LED_OBJ` / `TEAM_LED_JOIN`，那是另一條路徑）。
2. **五個專屬情境不是「人工極端案例」**，它們比中性情境**更接近**真實遊戲。
3. **但專屬情境的 knobs 仍偏離真實值**：invade 用 `invadeChance 0.5`
   （真實預設 0.1、最激進預設 0.35）、roam 用 `roamRate 0.5`（真實預設 0.3）。
   ⇒ 方向與接線正確性可信，**效果幅度一律不可直接搬去校準權重**。
4. `splitAdj` 即使在 `standard` 情境也**不生效**：`splitPush 0.1` 但
   `splitLane: null`，引擎註明「有 splitLane 才生效」。只有 `lanePlan.top === "split"`
   的分推戰術會打開它 ⇒ `splitAdj` 是**戰術限定**作用點。

### 已新增 `standard` 情境（2026-08-09）

`measure_stat_sensitivity.mjs` 的 `knobsFor` 新增 `case "standard"`，
**逐鍵照抄** `toEngineTactic(STANDARD_OPP_TACTIC)` 的輸出，已用程式斷言驗證
逐鍵相同（`tacticId` 除外）。`r10_standard.*` 是 16 項素質在**真實對局條件**下
唯一有代表性的基準，**最終分類以它為主依據**，r9gen 降為「關掉三個 knob 的對照組」。

⚠ 這一節不作廢任何既有數字 —— r9gen 與五情境的數值本身都正確、交叉驗證全過。
作廢的是「中性情境代表遊戲」這個**解讀前提**。

## 樣本量警語

| 指標類型 | 每場事件數 | 需要的 seeds |
|---|---|---|
| 逐 tick 累積（補刀、空揮、撤退、集火） | 數百～數千 | 8–30 足夠 |
| 每場數次（Gank、越塔） | 1–30 | 30 以上 |
| **每場一次擲骰（入侵）** | **1** | **100 以上** |
| **勝率** | 1（勝負） | **30 起，仍有 ±18pp 誤差** |

### 比例類指標的精度（不綁特定 seed 數）

每格場數 `n = seeds × 2`（藍紅鏡像）。對勝率、入侵率這類**每場一次**的比例指標：

```
單格 95% CI ≈ ±1.96 × sqrt(0.25 / n)
兩格相減   ≈ ±1.96 × sqrt(0.5 / n)      （≈ 單格的 1.41 倍）
```

| seeds | n（每格） | 單格 ±95% CI | 兩格相減 ± |
|---|---|---|---|
| 8 | 16 | ±24.5pp | ±34.6pp（**完全不可用**） |
| 30 | 60 | ±12.6pp | ±17.9pp（僅供旁證） |
| 100 | 200 | ±6.9pp | ±9.8pp（可辨識 ≥10pp 的效果） |

⚠ 逐 tick 累積的指標（補刀、空揮、撤退、集火）事件數是每場數百～數千，
精度遠高於上表，**不適用**這條公式；上表只管「每場一次」的指標。

# 觀測 proxy 的地位（先定義，再解讀）

以下指標**不是引擎的一級概念**，是量測工具用純取樣算出來的代理值
（只讀狀態、不改行為、不消耗 rng）。**不得**寫進正式契約、不得當成引擎的
成功／失敗語意、不得單獨拿來當調權依據。

| proxy | 定義 | 已知偏差 |
|---|---|---|
| `roamEpisodes` | 由 `exec.supportRoams` 增量偵測的遊走段落 | 恆等於引擎 `roams`（設計上） |
| `roamEngaged` | 段落窗內該輔助自己 `atkTicks` 有增加 | 只認「自己動手」，站場沒輸出者不算 |
| `roamPaid` | 段落窗（8 秒＋5 秒尾窗）內該側 K+A 有增加 | **偏寬**：隊友在別處拿的人頭也會算進去 ⇒ 是成功率的**上界** |
| `roamMissed` | `roamEpisodes − roamPaid` | 同上，是下界 |
| `objRallies` | 目標生成後，該側坑內（半徑 9）人數首次達 3 | 半徑取自引擎結算傷害的同一個值 |
| `objRallyDelay` | 生成 → 首次達 3 人的秒數 | **條件平均**：分母只含有集結的生成，沒集結的不計入 |
| `objHeadMean` | 目標存活期間坑內該側平均人數 | 含 0 人的 tick |
| `objRollGoRate` | `_objJoinV3` 真正擲骰時回傳 true 的比例 | 只統計會擲骰的 3 人（打野／輔助在擲骰前無條件 true） |
| `objKills` | `o.killerTeam === 受測方` | **不是 proxy**，引擎原生歸屬 |

⚠ 段落偵測**不可**用 `p.state === "遊走"`：`stOv` 只在對線分支寫進 `p.state`
（`LogicEngine.js:3415` / `:3499`），一開走就接上戰鬥的段落會被戰鬥狀態覆蓋 ⇒
系統性漏掉**成功**的案例（實測接戰率被壓到 10%，真值 21%）。

### 決策層：接線正確，但**被情境本身壓縮到 43%**

`p.dbgRetreatAt`（`LogicEngine.js:3170`）＝該 tick 實際採用的門檻，直接取樣：

| 韌性 | 實測門檻均值 | 裸值理論 |
|---|---|---|

`repeatDeathRetreatBonus 0.08`、`burstRetreatBonus 0.16`，每一層都是
`Math.min(0.50 / 0.55 / 0.62, …)`。40 分側（裸值 0.44）加上 base 0.06 剛好撞到
`Math.min(0.50)` ⇒ **能力差異被上限吃掉**；90 分側（0.4067 + 0.06 = 0.4667）沒撞到。

⇒ **comeback 情境（`retreatAt` 0.42）把門檻推進飽和區，反而壓縮了它想放大的那個素質。**
情境設計與作用點飽和區衝突，這是情境設計問題，不是接線問題。

### 判定：**接線正確但效果偏弱**（B）

> 門檻層可驗證、方向正確，但幅度被情境的飽和區壓到 43%，
> 行為層量不出可信的反應。
>
> **不是權重大小問題，也不是結構問題**——是**情境設計**把作用點推進了飽和區。
> 要重測應改用 `retreatAt` 較低（例如中性 0.25）但仍逆風的 knob 組合，
> 讓門檻遠離 `Math.min` 上限。本輪不改。
