# 撤退收益鏈：根因、四次修正嘗試、以及為什麼全部失敗

**日期**：2026-08-09
**狀態**：🔴 **未修好。根因已確認並量化；四個修正變體都無法在不破壞既有節奏門檻的前提下成立。**
**目前引擎狀態**：`retreatHoldV1: false`（預設關閉）⇒ 行為與本輪改動前**逐位元相同**（見 §4-1）。

---

## 1. 問題陳述

`STAT_IMPACT_FINAL_R10.md` §2 證明「撤退 → 存活 → 再投入 → 推進」這條收益鏈是斷的：

```
真實對局條件（r10_standard，12 項素質）
  r(Δ死亡, Δ推塔)        = +0.865  [0.579, 0.962] ★
  r(Δ撤退, Δ推塔)        = −0.830  [−0.951, −0.488] ★
  r(Δ撤退, Δ推塔/作戰分)  = −0.835  [−0.953, −0.502] ★
```

死得多的素質推得多；撤得多的素質推得少，**而且用實際在場時間正規化之後仍然如此**。

---

## 2. 根因（已確認）

### 2-1 撤退只有一個終點：泉水

`LogicEngine.js:3471`：

```js
if (p.retreating) {
  tgt = FOUNTAIN[p.side];        // ← 唯一終點
```

整條生命週期裡**缺少「退到安全位置就地恢復」這一段**。
`disengage → safety reached → recovery → re-evaluate → re-engage` 全部塌縮成
「傳送回家 → 補到接近全滿 → 走一整趟回來」。

### 2-2 引擎的回血經濟讓「回家」嚴格支配「就地恢復」

`matchProgression.js` 的 `regen` 契約：

| 情境 | 速率 | 從 30% 恢復所需時間 |
|---|---|---|
| 脫戰（野外） | **0.75%/秒**（且受傷後 7 秒才啟動） | 到 60% 要 **40 秒** |
| 泉水 | **10%/秒** | 到 88% 只要 **5.8 秒** |

差 13 倍，而且回城可以**傳送**過去（`recallChannelT: 6`）。
⇒ 沒有任何情況下「留在野外恢復」是划算的。這就是為什麼撤退行為會塌縮成回家。

### 2-3 量化證據（decision=90、standard 條件、20 場、決定性）

工具：`tools/probe_retreat_lifecycle.mjs`（純觀測，不擲骰、不改狀態）

| 生命週期階段 | 實測 |
|---|---|
| 【1 觸發】起始血量 | 34.3% |
| 【2 脫離】回城使用率 | **98.2%** |
| 【2 脫離】**撤到泉水的比例** | **95.7%** |
| 【3 恢復】段落時長 / 結束血量 | 18.2 秒 / **94.2%** |
| 【4 歸位】結束時離最近敵塔 | **172.8** |
| 【5 再投入】結束 → 首次攻擊 | 33.8 秒 |
| 【6 推進】**結束 → 首次推塔** | **47.5 秒**（**64.5%** 到下次撤退前根本沒再推到塔） |
| 【8 往返】撤退開始 → 再次推塔的完整成本 | **65.7 秒** |
| 【7 反覆】15 秒內再次撤退 | 4.0%（⇒ **不是**反覆退進的問題） |

### 2-4 為什麼會讓 `推塔/作戰分` 下降 —— 一部分是指標假象

`fightUptime = 1 − retreatingTicks / aliveTicks`（`measure_stat_sensitivity.mjs:361`）
在玩家於泉水回滿、`retreating = false` 的**那一刻**就停止計為撤退。
但後面 30–50 秒的**走回路程**被算成「在場」。

直接量測（同一支探針）：

| | decision 40 | decision 70 | decision 90 |
|---|---|---|---|
| `fightUptime` 認定在場 | 82.9% | 81.1% | 80.4% |
| 其中站在自家泉水 30 單位內 | 6.6% | 6.8% | **7.1%** |
| **扣掉後真實在場** | 76.4% | 74.2% | **73.3%** |

⇒ 分母被永遠不可能產生推塔的移動時間灌水。

### 2-5 這個缺陷 codebase 自己描述過

`LogicEngine.js:1662-1665`（Milestone F 的註解）：

> 當時的觀察是「團隊天賦單投 = 負回報」，因為勝負來自主堡血量（靠兵線與推塔），
> 而打贏團戰之後所有人只是進入 DISENGAGE、走回自家塔、再重新對線
> ⇒ **打得多不會變成推進**。

Milestone F 用「勝方開一個主動權窗」修好了**團戰勝利**那條路徑。
**血量撤退這條路徑從來沒修。**

## 3. 四次修正嘗試（全部保留在程式碼裡，flag 關閉）

實作：`retreatHoldV1` / `retreatHoldHp` / `retreatHoldSafeDist` / `retreatHoldRegenPctPerSec`
（`matchProgression.js`）＋ `LogicEngine.js` 的撤退分支與回血段。
**全程未動任何 stat 權重、未改傷害、未改 XP、未改英雄/技能、未擲骰。**

| # | 改動 | 結果 |
|---|---|---|
| 1 | 撤退目標改為**自家前線塔**（`frontTower`，與 DISENGAGE 同一位置來源） | 幾乎沒被用到 —— 門檻 0.34 高於撤退**觸發**血量 34.5% ⇒ 一開始就判定「非回家不可」。撤到泉水 95.7% → 只降到 74.4% |

## 4. 為什麼停止，而不是嘗試第五個變體

1. **四次修正，每一次都在別的地方冒出新問題** —— 這是架構問題的特徵，不是假說失敗。
2. **開始對雜訊調參**：兩次只差一個安全檢查的執行，decision@90 推塔從 30.42 變成 27.83（−8.5%）。
   6 seeds（12 場/格）的雜訊已經和要追的效果同級。
3. **量測本身推翻了修法方向**：問題不在「在哪裡恢復」，而在**總恢復時間**。
   換地點只是把移動時間重新標記成撤退時間——讓 `推塔/作戰分` 這個指標變誠實
   （§2-4 的分母灌水被移除），但沒有真的把「活下來」換成推進。
   這也解釋了為什麼撤退時間會上升而推進沒有回來。

### 4-1 目前狀態是安全的（已驗證，非推論）

`retreatHoldV1: false`，並以**實測**確認等價（不是靠讀程式碼推論）：

```
flag OFF 重跑 r10_standard 的 decision 三格
  decision 三格 × 全欄位比對: 222 個｜相異 0
  中性基準比對: 74 個｜相異 0
```

⚠ 先前用 `git stash` 做的等價比對是**錯的**——`git stash` 會把檔案還原到 HEAD，
而 HEAD 不含本 worktree 未提交的 B/C 改動 ⇒ 那次比到的差異是 B/C 造成的，與本次改動無關。
該次比對已作廢，以上表為準。

## 5. 三條可能的路（需要決策，本輪不執行）

### A. 接受「總恢復時間」是設計常數，改修指標定義
撤退本來就該有代價。目前 `推塔/作戰分` 的下降有一部分是 §2-4 的指標假象
（走回路程被算成在場）。把 `fightUptime` 改成扣掉「在自家後場且非撤退」的時間，
指標就誠實了，而引擎不動。
**成本最低，但不改變任何遊戲體驗。**

### B. 沿用 Milestone F 的「主動權窗」機制（建議）
成功脫離（撤退了但沒死成）也開一個窗，把**存活**轉成地圖收益——
就像 F 把**團戰勝利**轉成推塔/目標窗那樣。
這是唯一直接接上「活下來 → 推進」這個斷點的作法，
而且這個 codebase 已經用同一個模式成功修過同類問題（`_resolveFightV3`）。
**工作量較大，但方向正確且有前例。**

### C. 縮短總恢復週期（動 regen 或 returnAt）
血量半徑很大：換血、追擊、塔下壓力、擊殺價值全部連動
（`regen` 契約的註解本身就是為了修這些才寫的）。
**不建議在沒有明確授權前碰。**

### 6-1 探針自身修掉的兩個量測 bug（避免日後重蹈）

1. `post.delete(p.id)` 在記錄「再次撤退」**之前**執行 ⇒ 「反覆退進」恆為 0.0%。
2. `lastDamagedAt` 由 **tick 尾端**寫入（`LogicEngine.js:3919`），而回血速率在 tick 中段決定。
   探針在 `e.tick()` 回傳後採樣 ⇒「同一 tick 內先回血、後被打」會被誤判成違規。
   斷言已改為只認 `since > 0` 的情況。
