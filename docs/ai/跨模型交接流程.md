# 跨模型交接流程

> Claude Code token 不足時，如何安全交接給 Codex（或其他模型）。
> 前置：雙方都先讀 `AGENTS.md`。Codex 專用規則見 `docs/ai/CODEX使用規範.md`。

## 1. Claude token 不足前（交接方）

Claude 應該：

- **停止新增大改**（不要開新的大範圍重構）。
- 跑 `git status --short`、`git diff --stat`。
- 回報：**已完成 / 未完成**清單。
- 標記**未驗證項**（尤其手機 UX / FPS / 視覺 —— Node 證不了的）。
- **不自行亂 commit**；工作區未收尾就照實說明，交給使用者決定。

## 2. 交接給 Codex 前（使用者 / Claude 提供）

- **交接清單指向 `docs/README.md`**（新模型由此決定選讀哪些文件，不重讀完整歷史）。
- 目前 Sprint 目標與範圍
- 最新 commit hash
- `git status` 現況
- 已跑哪些 verifier、結果
- 失敗 / 紅燈項目
- **不可修改區域**（別人正在改的、或高風險契約）
- **只提供任務必要文件**——不要求新模型重新讀完整歷史 Sprint 紀錄。

## 3. Codex 接手流程（接手方）

Codex 應：

- 先讀 `AGENTS.md`、再讀 handoff（00 / 05 / 06 / 08）。
- 先看 `git status` / `git diff`，掌握現況。
- **不重跑全專案 Audit**（浪費 token；handoff 已有現況）。
- **不重寫已完成部分**。
- 先修 **blocking issue**。
- 必要時**先寫 verifier** 再改實作（讓改動有安全網）。

## 4. Codex 完成後（交還）

Codex 回報：

- 修改檔案清單
- 根因（若修 bug）
- 已驗證項（含 exit code / 輸出形狀）
- 未驗證項
- 是否 commit / push
- 下一步 / 交還 Claude 或使用者

## 5. 衝突處理（Codex 發現 Claude 已改一半）

**絕對不要自作主張覆蓋別人的工作。** 若發現工作區已有未完成改動：

- **不 `git reset`**
- **不 `git checkout` 覆蓋**
- **不 `git pull` 覆蓋**
- **不刪未追蹤檔**（`git clean` 禁用）
- 先**回報狀態**（列出未 commit 的檔案與內容摘要）
- **等使用者確認**再動。

## 6. 遇到 verifier 紅燈

- 先判斷：是**這次改動造成**，還是**既有已紅**（見 `CLAUDE.md` 的「已失效 verifier」清單）。
- 若是本次造成 → 修好再繼續，不可刪 verifier 或改斷言硬過。
- 若是斷言本身壞掉（跟不上合法重構）→ 改斷言，**並在 `05_Sprint紀錄.md` 說明原因與證據**。
- 判不出來 → 回報，不硬提交。

## 7. 遇到不確定需求

- **不猜、不擴大範圍**。
- 列出不確定點與可選方案，回報使用者。
- 在得到答覆前，只做範圍明確、可逆的部分。
- **若文件之間有衝突**：依 `docs/README.md` §五 的優先順序初判，並**列出衝突點交由 owner 或使用者裁決**，不自行選較舊文件。

## 10. Competition Release Gate（2026-08-19 起）

```
node tools/check_competition_release_gate.mjs            # 全跑
node tools/check_competition_release_gate.mjs --list     # 區段清單
node tools/check_competition_release_gate.mjs --only=q6,build
```

**Claude、Codex、任何人都用同一支入口。**
它不取代各 verifier，只是把「這一塊改了就必須全綠」的集合固定下來。

### 何時必跑

動到下列任一處，**merge / deploy 前必須全綠**：

- `src/platform/competition/**`（seasonState、seasonStateV2、seasonSealingV2、
  circuitPoints、asiaFinals、asiaCircuit、playoffs、honors）
- `src/platform/profileStore.js` 的 Competition 相關動作
  （`competitionView`、fixture lifecycle、sealing、rollover、`activeCompetitionEvent`）
- `src/screens/manage/CompetitionScreen.jsx` 與 `seasonRecap/**`
- `src/platform/contracts/competition.js`
- `review/fixtures/competition/**`（動到 fixture 等於動到所有 gate 的基準）

### 包含的區段（10）

`v2_runtime`（SeasonState v2 runtime compatibility）／`v2_active_focus`／`v2_sealing_m2`／
`circuit_points`／`multi_event`／`career_final`／`asia_finals`／`team_honors`／
`q6`／`build`

### 行為

- **不會在第一個 FAIL 就中止**——全部跑完，一次看到完整故障面
- 每段除了 exit code 還檢查**輸出形狀**（寫死通過數）。
  `exit 0` 但沒印出預期的通過行**一樣算 FAIL**——腳本提早 return 會被抓到
- 每段完整 stdout/stderr 寫到系統 temp 的獨立 log，另寫 `summary.json`（含耗時與失敗原因）
- browser 段逐支檢查自己實際使用的 Vite／CDP port；若 gate 沒自行收乾淨，runner 只回收
  該段新產生的 listener，且該段仍判 FAIL
- 結束前再檢查全部 12 個 browser LISTENING port，確認沒有本次新增的殘留
- 最後輸出 `passed X/Y` / `failed X/Y`，任一 FAIL ⇒ exit 非 0

⚠ **新增斷言時必須同步更新 `GATES` 內的 `shape` 通過數。**
那是刻意的摩擦：讓「斷言變多了」變成一個要被看見的決定。

## 11. Team Development / 天賦系統 版本保護（2026-08-20 起）

### 為什麼需要這一節

2026-08，正式站部署了較舊的 main 之後，首頁**又出現舊的「天賦」磚與舊天賦樹**，
而較新的「戰隊發展」整套 UI 一直好好地活在 branch 上。當時 `npm run build` 全綠、
既有 verifier 全綠——因為**沒有任何一支在問「首頁的主要投資入口現在是哪一個」**。

這不是功能缺陷，是**版本降級**：用較舊的 base 工作、或拿舊 main 當 recovery base，
就會靜默地把新版產品換回舊版，而所有既有 gate 都不會有感覺。

### 契約（動到下列任何一項，merge / deploy 前都必須回來看這一節）

- `src/screens/DashboardScreen.jsx`（首頁入口磚與 `NAV`）
- `src/screens/manage/TeamDevelopmentScreen.jsx`
- `src/screens/manage/PlayerTalentScreen.jsx`
- `talentPick` route
- `src/platform/profileStore.js` 的 `teamDevelopment`
- `PROFILE_SCHEMA_VERSION`

1. **新版正式產品名稱是「戰隊發展」（Team Development）。**
   首頁主要長期投資入口磚必須是「戰隊發展」，`NAV.development → "teamDevelopment"`。

2. **「天賦」只可作 legacy compatibility。**
   `PlayerTalentScreen` 與 `talentPick` 路由**保留**給舊存檔與選手詳情流程，
   但**不得再成為首頁主要入口磚**，除非有新的產品決策（要有明確決策紀錄，
   不是某次 recovery 的副作用）。

3. **`TeamDevelopmentScreen` 是新版 UI baseline。**
   4 分類 / 20 節點（每類 5 項）、Lv.0–3、prerequisite、下一級效果說明、
   規劃中（planned/future）狀態、GSAP ＋ `prefers-reduced-motion`。

4. **`65e3506`（P0.6A）是 UI Recovery evidence，不是完整產品恢復。**
   它**只**恢復 UI / presentation / fixture / docs，
   **沒有**動 `profileStore.js`、沒有 teamDevelopment persistence、沒有 R60 gameplay consumer。
   實測佐證：該樹 `PROFILE_SCHEMA_VERSION = 9`、profileStore 內 `teamDevelopment` 出現 0 次、
   `TeamDevelopmentScreen` 還加了 `typeof purchase !== "function"` 防護才不會炸，
   且它自己帶的 `check_team_development_v1.mjs` 在該樹上跑到第 17 條
   「profileStore migration 與 write hook」就 FAIL。

   > **「P0.6A UI Recovery」≠「完整 R59–R62 product recovery」。**
   > 未來任何 AI 都不得把兩者混為一談。完整版在
   > `release/moba-combat-closure`（`PROFILE_SCHEMA_VERSION = 10`、
   > profileStore 有 `teamDevelopment` 與 `purchaseTeamDevelopment`、
   > BanPick / Tactic / CsTactic / Roster / Recruit 五個 consumer 都已接線）。

5. **Claude / Codex 不得因為使用較舊 main 或 recovery base，
   把 Team Development UI 默默降回舊 Talent UI。**
   若某次工作的 base 不含戰隊發展，那是 base 的問題，**不是**把首頁改回「天賦」的理由。

### 驗證

```
node tools/check_team_development_recovery.mjs
node tools/check_team_development_recovery.mjs --root=<另一棵 worktree>
```

⚠ 這支**刻意分三段輸出**，因為它們是三件不同的事：

| 段 | 意義 | 影響 exit code |
|---|---|---|
| `UI Recovery Contract` | 上面 1–3、5 的契約。`VIOLATED` = 降級 | ✅ 是 |
| `Persistence Integration` | R59 / R59.1，路線圖項目 | ❌ 否，只回報現況 |
| `Gameplay Consumers` | R60，路線圖項目 | ❌ 否，只回報現況 |

後兩段**永遠不會被印成 PASS**，只會是 `INTEGRATED` / `NOT YET INTEGRATED`。
讓已知未完成的路線圖項目把 gate 染紅，只會訓練人忽略紅燈；
但把它們算成 PASS，就會讓「UI 恢復了」被讀成「R59–R62 完成了」——這正是要防的誤讀。

Home Command Center 只回答「現在最需要處理什麼」，應提供：
