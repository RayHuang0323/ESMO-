# 03 開發規範

## 基本原則

- 小步修改。
- 不大幅重構。
- 不為了方便重寫 UI。
- 不建立第二套資料來源。
- 不破壞已驗證的 Battle Balance。
- 優先可維護、可擴充、可讓 AI 接手。

## 禁止修改項目

除非任務明確允許，禁止修改：

- `src/LogicEngine.js`
- Battle Balance
- BattleResult 結構
- HeroProgress 計算規則
- SeasonStore 統計規則
- battleStore 核心資料流
- Router 主架構

## 禁止新增

- 第二套 Hero Database
- 第二套 Store
- 第二套 BattleResult
- 第二套統計邏輯
- 假資料覆蓋真資料

## Store 新欄位規則

新增 Store 欄位時，必須向下相容 localStorage。

陣列欄位要使用：

```js
Array.isArray(saved.items) ? saved.items : DEFAULT.items
```

UI 讀陣列時，使用：

```js
items ?? []
```

避免黑畫面。

## Hero 資料規則

`src/data/heroDatabase.js` 是唯一英雄資料來源。

不可另建第二套 Hero image database、skill database 或 stats database。

如需圖片，應整合到同一份 heroDatabase 或建立由 heroDatabase 引用的單一資源 map，並清楚說明。

## BattleResult 規則

BattleResult 是唯一戰鬥結果來源。

Result / HeroProgress / Season / Dashboard 不得重新統計 KDA、MVP、勝負、EXP、戰績。

## UI 呈現原則（2026-08-04 起，適用所有新功能）

新功能上 UI 時，**優先做成圖形化、好操作的介面**，可以有克制的特效，
**但不得影響功能邏輯**。

- 預設用視覺化形式（圖表／進度條／圖示／色彩化狀態／預測條），而不是純數字或表格。
- 狀態顏色要配文字，不可只靠顏色辨識。
- **畫面顯示的數字必須來自邏輯用的同一份計算**，不可為了顯示另算一套
  （＝上面「不建立第二套資料來源」的延伸；範例見 Milestone N 的 `buildWeekLines`
  同時服務結算、預覽與預測）。
- 特效不得擋互動、不得延遲狀態更新、不得改 state 形狀或 Store 寫入。
- 不覆蓋 Legacy Experience 規格與手機優先原則——資訊密度與流程仍以
  `02_Legacy_Recovery_規格.md` 為準；特效不得讓 320px 溢出或掉幀。

跨模型完整版見 `AGENTS.md` §UI 呈現原則。

### Motion Policy（2026-09-02 起）

**「ESMO 避免動畫」這條舊共識已作廢。** 動態預設**允許**，判準是
「這個動態有沒有在傳達狀態變化」：有就做，沒有就不要做。

- 允許：進場 stagger、狀態／分頁切換轉場、進度與數值變化、可領取的低頻 pulse、
  hover／press 回饋、領取解鎖的一次性回饋、hero 的極慢環境漂移。
- 禁止：長駐重粒子、無意義的永久動畫、擋住互動或延後 state 更新、手機掉幀、
  把動畫旗標寫進 Store schema 或存檔。
- **必須支援 `prefers-reduced-motion: reduce`**：呈現完成狀態、拿掉位移與閃爍，
  但顏色與文字狀態全部保留。

完整規則（含建議時長表與實作參考）見 `AGENTS.md` §Motion Policy；
視覺語言與 token 見 `docs/design/ESMO_Design_System_v1.md` §5。

## 驗證要求

每次修改後至少確認：

- esbuild 或 build 通過。
- Contract 檔零改變，除非任務允許。
- 20 seed 回歸不變，若任務不應影響戰鬥。
- UI 流程本機驗證。
- Legacy Diff Checklist。
