## 已查證：`requeueMatch()` 清掉 `settlements` **不會**造成重複結算（2026-08-12）

**結論：不可重現。** 只做 audit ＋ 最小重現，**沒有改任何程式**。

### 風險前提確實成立

`requeueMatch()` 會整個換掉 `matchmaking`，`matchmaking.settlements`（O7 結算帳本）
確實歸零——實測 `settlements` 從 1 筆變 0 筆。**但重送同一份 MatchResult 什麼都不會多發。**

### 擋住的是哪一層

`settlements` 只是**第二道**防線。真正的冪等在這兩處，而 `requeueMatch` **碰不到**：

| 防線 | 位置 | requeue 會清掉嗎 |
|---|---|---|
| `matchmaking.settlements`（O7，key＝`settlementIdOf(resultId)`） | `matchmaking` 之下 | **會** |
| **`processedMatchTransactions`（S25，key＝`transactionId`）** | **profileStore 頂層** | **不會** |
| `growthLog` 條目 id `${transactionId}:${playerId}` | 存在選手身上 | 不會 |

**關鍵是 `transactionId` 具決定性**（不含時間戳、不含亂數）：

```
makeTransactionId(mode, matchId) = `${mode}:${matchId}:progress-v1`
mobaMatchId(br)                  = fnv1a(winner|duration|score|gold|towers|mvp|每位選手 KDA…)
```

⇒ 同一場比賽永遠推導出同一個 `transactionId`
⇒ `applyProgressToState` 命中 `processedMatchTransactions` ⇒ 回既有 receipt、`nextState: null`、**不入帳**。

### 實測證據

- 情境 A（賽程路徑）與 B（票券路徑）：結算 → `requeueMatch` → 重送同一份結果，
  錢／粉絲／聲望／XP／天賦點／`stats`／成長紀錄／賽程賽果**差異全部為空 `{}`**，
  receipt 為 `ok=true, alreadyApplied=true`。
- 情境 C（反證）：把 `settlements` **與** `processedMatchTransactions`
  **兩層一起清掉**再重送 ⇒ `funds 1530000 → 1860000`、`fans +173`、`xpTotal +285`
  ⇒ 證明擋住的就是這兩層，不是別的巧合。**只丟 `settlements` 那一層，S25 仍然擋得住。**

### 順帶記錄（無害但要知道）

`requeueMatch()` 是**先清空 `matchmaking`、再呼叫 `enqueueMatch`**，
所以**即使 requeue 失敗**（實測拿到 `ok=false` 的情境），
`lastResult` / `settlements` / `lastSettlementError` 一樣被丟掉。
獎勵安全由 S25 那層守住沒問題，但 **O7 的衝突偵測記憶（`lastResult`）會消失**
——「同一場送不同勝負」這種偵測在 requeue 之後會失憶。目前沒有已知玩家路徑會觸發。

## 技術債（既有）：舊賽果重送可能寫進**別的** fixture

**與上面的 requeue 無關**——做過對照組，**不呼叫 `requeueMatch` 也一模一樣重現**。

### 現象

一份**已結算過**的舊 `BattleResult` 若再次被送進 `reportMatchResult()`，
而當下手上有**另一場賽程的 active session**（例如已經進到下一場賽程的 launched 狀態）
⇒ **那一場還沒打的賽程會被判 `completed`，並寫進舊比分**。

```
outcomes 7 → 8 ; fx2.status: launched → completed ; fundsChanged: false
receipt: ok=true, viaSession=true, alreadySettled=true
```

### 成因

`reportMatchResult()` 用**當下 session** 鑄出新的 `MatchResult`（**新的 resultId**），
再由 `fixtureIdOfSession(session)` 決定寫進哪一場 ⇒ 舊結果被綁到新賽程上。
`settlements` 帳本擋不住，因為 resultId 是新的（所以帳本在不在都一樣）。

### 影響範圍

- **不會**重複發錢／粉絲／經驗／天賦點／能力成長／成長紀錄（S25 那層仍然擋住，
  `alreadySettled=true`）。**只有賽程狀態被污染。**
- **玩家目前沒有正常 UI 路徑可以觸發**：`useBattleFeed` 只在
  `snap.over && !bs.result` 時送出**當場**結果，一場只送一次；
  要重現得像 audit 腳本那樣直接拿舊物件呼叫結算邊界。
  ⇒ 定位為**縱深防禦缺口**，不是線上災情。

### 最小修法候選（**尚未實作**）

`profileStore.reportMatchResult()` 目前是：

```js
if (receipt?.ok && isFixtureSession(session)) get()._writeFixtureResultFromMatch(...)
```

`receipt.ok` 在 `alreadySettled` 時**仍然是 true**。改成：

```js
if (receipt?.ok && !receipt.alreadySettled && isFixtureSession(session))
```

首次結算照寫，重送就不再碰賽程。**一行。**

## 【P0・已修，長期釘住】players 陣列順序決定勝負

**這是正確性缺陷，不是平衡問題**：模擬結果曾取決於資料結構的擺放順序。
自 Sprint 04 起就存在，被「塔會瞬間融化」的粗暴節奏掩蓋。

實測（40 seeds，v1 = 缺陷版規則集）：把 `players` 陣列反轉，
**藍方勝率 55% → 6.7%**（位移 48 個百分點）。五個根因：

| # | 根因 | v2 修法 |
|---|---|---|
| ① | 傷害立即套用 ⇒ 先被迭代者先出手，被秒殺者連還手機會都沒有 | `simultaneousCombat`：傷害累積 → 一起套用 → 才判定死亡 |
| ② | 移動與交戰同一迴圈 ⇒ 先動的人用敵人**舊位置**判定接戰 | `twoPhaseTick`：全員先移動 → 再全員交戰 |
| ③ | `alive.find` ⇒ 一律集火「索引最小」的敵人 | `nearestTarget`：打**最近**的敵人 |
| ④ | 熱點取「陣列第一個」交戰者的鄰域 ⇒ 永遠繞著藍方長 | `symmetricHot`：取最密集鄰域、並列時 centroid |
| ⑤ | 小兵對戰只迭代藍方 ⇒ 紅兵被集火、系統性先死 | `symmetricMinionCombat`：雙方各自出手、同時結算 |
| ⑥ | `PITS.baron {33,32}` 不在雙方基地中垂線上 ⇒ 紅方近 2.45 單位 | 移到 `{33,34}`（差 0.20），連同 `OBSTACLES[0]` 水池 |

**長期防線**：`check_moba_runtime29` §24–29 的**正序／反序 invariant**
（傷害同時結算 / 小兵雙方迭代 / 最近目標選取 / 地圖對稱 / 整場勝率位移），
每一條都同時跑 v1 對照 —— **v1 的系統性翻轉必須被測出來**，否則測試等於沒檢定力。

⚠ **殘留（P1）**：v2 反轉陣列後**逐 seed 勝方仍可能改變**——rng 抽樣順序跟著 players
迭代順序走（特效骰、無戰術時的參戰骰）。那是**混沌**不是**偏差**（已證明無系統性
陣營優勢）。要做到「反轉後逐位元相同」需改 **per-player rng 流**（seed + player id 派生）；
會改變所有 v2 數值 ⇒ 需重新校準並重跑全部 verifier，**不在 29A 範圍**。

⚠ **殘留（P1）**：**換命時的擊殺 XP 歸屬仍看陣列順序**。`pendingHits` 先結算的那位攻擊者
拿得到擊殺 XP；後結算的那位此時已被標記 `dead` ⇒ `_addXp` 的 `p.dead` 守衛讓他拿不到。
實測同一換命場景：正序 b1 升 Lv2、反序改成 r1 升 Lv2。**不影響勝負**（雙方各記 1 殺，
`runtime29` §24 已驗），影響的是單一次換命的 XP。修法是讓 `_resolveKill` 的 XP 發放不受
攻擊者當下死活影響 —— 會改變所有 v2 數值 ⇒ 需重新校準並重跑全部 verifier，不在 29A 範圍。

⚠ **殘留（P1）**：`LANES` 折線、`WALLS`、`BUSHES` 仍不是精確 180° 鏡像
（例：藍方泉水到下路線頭 7.8 單位、紅方到另一端 11.2 單位，差 3.4）。
已修的是引擎機制真正依賴的部分（基地/泉水、塔與主堡路線參數、小兵出生、雙坑等距）。

### 3. 同一天 + 同一份名單 ⇒ 同一場比賽

### 11. 一天多場的疲勞／體力規則 ✅ 已定案（2026-08-13），**不需要改現有機制**

排程器不得因當天已有玩家賽事就禁止安排第二場。

|---|---|---|
| `matchEnergyCost` | 12 | 第一場後 ~95 → ~83 |
| `streakEnergyStep` | 3 | 同日第二場扣 15 ⇒ ~68 |
| `unfitBelow`（不可出賽門檻） | **15** | ~68 遠高於門檻 ⇒ **`exhausted` 擋不到第二場** |
| `injury.base` / `perStreak` | 0.02 / +0.02 | 第二場每人約 4% 受傷率 |

### 5. `mobaMatchId` 碰撞率實測（2026-08-13，上線前的依據）

工具：`tools/measure_moba_matchid_collisions.mjs`（10,000 個不同 seed，11 分片，
耗時 5,239 秒）。

| 項目 | 數值 |
|---|---|
| 成功終局場數 | 9,995 |
| unique matchId / unique 投影 | 9,995 / 9,995 |
| 投影碰撞（②） | **0** |
| 雜湊碰撞（③） | **0** |
| **true collision（②＋③）** | **0** |
| 碰撞率 | 0.0000%（0 / 9,995） |
| 決定性對照（同 seed 重跑） | 100 相同 / 0 不同 |

**這個數字證明了什麼**：投影本身鑑別力很強 —— 9,995 場不同對戰，被雜湊的欄位
（勝方／時長／比分／雙方經濟／推塔／MVP／十位選手 K/D/A/gold/dmg）沒有任何兩場
完全相同。②是換雜湊擋不掉、真正危險的那一類，實測為 0。

⚠ **沒證明什麼**：一萬場對 32-bit 雜湊碰撞幾乎沒有檢定力 —— 生日問題下期望碰撞數
只有 **0.0116**，「觀察到 0」本來就是預期值，無法區分「雜湊沒問題」與「稍差」。
要對 ③ 有檢定力得跑十萬～百萬量級。

**真正的曝險是每個存檔、不是每萬場**：誤拒需要新一場的 matchId 撞到該存檔裡
**任何一場已入帳**的舊 matchId。存檔 100 場 ≈ 2.3e-8；500 場 ≈ 1.2e-7；
2,000 場 ≈ 4.7e-7。以 0 事件 / 9,995 樣本的 95% 上界（rule of three）計，
每場 < 0.03%，而實際曝險比該上界小數個數量級。

⇒ 上線決策依據：誤拒**可觀測且可恢復**（`lastSettlementError` 有中文原因落盤），
錯寫**靜默且不可逆**（FixtureOutcome 依 D11 不可變）。兩者不對稱，故採 fail-closed。

## 既有缺口：房間空窗期可以切去另一場賽程（2026-08-21 M2 實測發現，非本輪造成）

**影響評估：不構成規避敗場的漏洞。**
留在 `launched` 的那一場會把日曆擋住（`advanceDay` 回
`stoppedBy.code = "player_fixture"`），玩家必須回去打完或明確棄權才能繼續，

**仍然該修的理由**：兩場同時 `launched` 是自相矛盾的狀態，畫面上也可能同時
出現兩個「進行中」。修法應是把守衛從「有沒有場次」放寬到「有沒有**未收尾的
賽程對戰**」（房間也算），並在切換時明確要求先取消前一場。

⚠ **不在 M2 修**：那會改到 MOBA 共用的進場守衛，屬於獨立的行為變更，
需要自己的驗證與瀏覽器實測。M2 的範圍是把 CS 接上既有鏈路，不是重寫進場規則。
`tools/check_cs_season_m2.mjs` 已把「有進行中的**場次**時別的賽程會被擋」
與「中離擋住日曆」兩條釘住，修這個缺口時不得讓它們轉紅。

## CS Season M3-2 之後的待辦與風險（2026-08-22）

`series_incomplete`。理由是一場 `MatchResult.v1` 只代表一張地圖，結算不了一個 series。

⇒ **玩家若打進四強，目前只能棄權或讓它逾期補判。**

這是自覺的取捨（不猜、不編一張沒打的地圖），但它是**產品缺口，不是設計終點**。
M4 要做的是跨三張地圖的 series 流程：地圖結果累計住在 MatchSession /
ActiveMatch，**不進 SeasonState**（規格 D4）。做出來之後那兩道要一起拿掉，
`check_cs_series.mjs` §8 的兩條斷言也要跟著改寫成「series 走得完」。

### ② 中途存檔的 Major 場次不會補上 matchFormat

`ensureCsMajor` 只在**建立**對戰表時掛 `matchFormat`。若有一份存檔的 Major
在 M3-1 與 M3-2 之間就已經排好（fixture 的 `matchFormat` 是 null），
它會**繼續走 BO1 投影**，比分是 `1:0`。

⚠ 目前**沒有這種存檔**：CS Major 是 M3-1 才有的東西，兩個 commit 都沒有部署過，
所以這是理論缺口，不是現存資料問題。但如果日後要在 Major 已存在的狀態下改
`matchFormat`，需要一支 migration —— 不能只靠 `ensureCsMajor` 的冪等，
因為它對「已經有這一場」的判斷是看 `playoffKey` 存不存在，不看 matchFormat。

### ③ BO3 的 veto 仍是裝飾

`veto: null` 是明文寫的，不是忘了填。引擎現役地圖只有三張（`CS_MAPS`），
三張池下 ban 一張、剩兩張選一張，沒有博弈可言。要做真正的 veto，
前置是把引擎地圖池擴到 7 張 —— **那是另一條工作線，不綁在 CS Season MVP 裡**。

## CS Season M4-A 之後的待辦與風險（2026-08-22）

### ① ⚠ 中離後重新進場會把 series 洗回 0:0（**既有機制，M4-A 讓它更值錢**）

玩家中離（`abandonMatchSession`）之後賽程仍是 `launched`，
而 `startFixtureMatch` 對 `launched` 的賽程允許重新簽發（`allowRelaunch`）。
重新簽發會開一個**新的 sessionId** ⇒ `createMatchSession` 會建一個**全新的 series**。

⇒ **輸掉第一張地圖之後中離、再重新進場，可以把 0:1 洗掉重打。**

⚠ 這條路在 BO1 時代就存在（中離→重新進場→重打），M4-A 沒有新增它；
但 series 讓它值錢得多：以前只能重擲一場，現在能重擲一個已經落後的 BO3。

**沒有在本輪修的理由**：修法會動到 `startFixtureMatch` 的重新進場規則，
那是 MOBA / CS 共用的路徑，且 `check_cs_season_m2.mjs` 有兩條斷言釘著它
（房間逾時之後必須能重新進場）。這是獨立的行為變更，需要自己的驗證。

**修的方向**（給下一個人）：series 的進度不該跟著 session 死。可以把
「這個 fixture 已經打到幾比幾」掛在 **fixtureAssignment** 上（它跨 session 存活），
重新簽發時沿用而不是重建。⚠ **不得**改放進 SeasonState —— 規格 D4 擋的就是那個。

### ② 三張地圖共用同一個引擎 seed

`csConfig.seed` 取自 `matchmaking.launch.seed`，整個 series 三張圖都是同一個。
目前不構成問題（三張是**不同地圖**，引擎輸入不同 ⇒ 結果不同），
但「同一個 seed 打三場」在語義上是可疑的，日後若地圖池變大或出現同圖重賽會浮現。

修法很小：由 `session.seed` 與 `series.nextMapIndex` 派生逐圖 seed。
⚠ 注意 `MatchResult` 的 `seed_mismatch` 驗證讀的是 `session.seed`，
不是 csConfig 的那一個 ⇒ 改 csConfig 的 seed 不會破壞結果驗證。

### ③ M4-A 沒有做 Recap UI（本輪明確不做）

Major 仍然沒有賽事頁、沒有對戰表畫面、沒有 series 比分的視覺呈現。
玩家看得到的只有：收件匣兩封信、以及打完一張圖之後自動回到選圖。
`activeSeriesView()` 已經備好給畫面用（含 `score` / `maps` / `nextMapKey` /
`label`），**不含任何 map runtime 細節**。

### ④ M3-3 未做：CS 冠軍沒進 honors、CS 仍一毛錢都不發

與 M3-1 / M3-2 的紀錄相同，沒有變化。
