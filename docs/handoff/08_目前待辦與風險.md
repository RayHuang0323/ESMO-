## 🔴 工程規則（2026-08-09 新增，跨 AI 適用）

### 規則 1：`exec` summary counter 只作診斷，不得當 gameplay outcome KPI

`exec[side].towerPushes` 曾被當成「推進強度」用了整整一輪，所有
「撤退越多推得越少」的結論都建立在它上面。它的真身是**隊伍層級、
每 10 秒最多 +1** 的責任週期計數器（`LogicEngine.js:2389`），上限 ≈ 場長秒數/10。

用真實推塔傷害 `p.twrDmg` 在 30 seeds 重測：責任週期計數器 **8/8 全部顯著**，
真實推塔傷害 **只有 2/8 顯著**，decision 甚至方向相反（計數器 −10.8%★ vs 真實 +3.5%·）。

- **推進強度一律用 `p.twrDmg` ＋ 推掉的塔數 ＋ 主堡傷害。**
- 使用任何 `exec.*` 前，必須註明：**層級（個人/隊伍）、遞增條件、有無節流或上限**。
- 同類已知陷阱：`splitPushActions`（8 秒節流）、`dragonContests`/`baronContests`
  （門檻只是「有人到場」）、`invadeKills`（實測 319 次入侵 0 擊殺）。

詳見 `review/moba-combat/METHOD_CAVEAT.md` 與 `STAT_IMPACT_FINAL_R10.md` §7。

## J-close Hotfix 2（已完成，未 push）

報告：`review/moba-runtime/j-close-hotfix2/J_CLOSE_HOTFIX2_REPORT.md`；
rollback `j-close-hotfix2-baseline` → `bcd9b3f`。

**修的是 Hotfix 1 造成的阻斷回歸**：Ban/Pick 整頁**沒有任何捲動軸**，
第六列以後的英雄永遠碰不到。根因是 BanPick 根元素只寫 `minHeight:100%`、

修法：根元素 `height:100%` ＋ flex column，英雄格 `flex:1 + minHeight:0 +
overflow-y:auto` 成為全頁唯一捲動區。另新增搜尋框、換篩選/關鍵字回頂部、
細捲軸＋底部漸層提示、手勢位移就吃掉 click（滑動不誤選）。
同時移除 Ban/Pick 的兩處「誰克制誰」呈現（`archCounterScore` 與 AI 行為未動）。

驗證：新增 `shot_banpick_hotfix2` **252/252**（六尺寸 × 版面/捲動/手勢/克制移除
＋ 六尺寸各一次完整流程）、`check_moba_milestone_j_close` **35/35**、

| # | 根因 | v2 修法 |
|---|---|---|
| ① | 傷害立即套用 ⇒ 先被迭代者先出手，被秒殺者連還手機會都沒有 | `simultaneousCombat`：傷害累積 → 一起套用 → 才判定死亡 |
| ② | 移動與交戰同一迴圈 ⇒ 先動的人用敵人**舊位置**判定接戰 | `twoPhaseTick`：全員先移動 → 再全員交戰 |
| ③ | `alive.find` ⇒ 一律集火「索引最小」的敵人 | `nearestTarget`：打**最近**的敵人 |
| ④ | 熱點取「陣列第一個」交戰者的鄰域 ⇒ 永遠繞著藍方長 | `symmetricHot`：取最密集鄰域、並列時 centroid |
| ⑤ | 小兵對戰只迭代藍方 ⇒ 紅兵被集火、系統性先死 | `symmetricMinionCombat`：雙方各自出手、同時結算 |
| ⑥ | `PITS.baron {33,32}` 不在雙方基地中垂線上 ⇒ 紅方近 2.45 單位 | 移到 `{33,34}`（差 0.20），連同 `OBSTACLES[0]` 水池 |

**長期防線**：`check_moba_runtime29` §24–29 的**正序／反序 invariant**
（傷害同時結算 / 小兵雙方迭代 / 最近目標選取 / 地圖對稱 / 整場勝率位移），
每一條都同時跑 v1 對照 —— **v1 的系統性翻轉必須被測出來**，否則測試等於沒檢定力。

⚠ **殘留（P1）**：v2 反轉陣列後**逐 seed 勝方仍可能改變**——rng 抽樣順序跟著 players
迭代順序走（特效骰、無戰術時的參戰骰）。那是**混沌**不是**偏差**（已證明無系統性
陣營優勢）。要做到「反轉後逐位元相同」需改 **per-player rng 流**（seed + player id 派生）；
會改變所有 v2 數值 ⇒ 需重新校準並重跑全部 verifier，**不在 29A 範圍**。

⚠ **殘留（P1）**：**換命時的擊殺 XP 歸屬仍看陣列順序**。`pendingHits` 先結算的那位攻擊者
拿得到擊殺 XP；後結算的那位此時已被標記 `dead` ⇒ `_addXp` 的 `p.dead` 守衛讓他拿不到。
實測同一換命場景：正序 b1 升 Lv2、反序改成 r1 升 Lv2。**不影響勝負**（雙方各記 1 殺，
`runtime29` §24 已驗），影響的是單一次換命的 XP。修法是讓 `_resolveKill` 的 XP 發放不受
攻擊者當下死活影響 —— 會改變所有 v2 數值 ⇒ 需重新校準並重跑全部 verifier，不在 29A 範圍。

⚠ **殘留（P1）**：`LANES` 折線、`WALLS`、`BUSHES` 仍不是精確 180° 鏡像
（例：藍方泉水到下路線頭 7.8 單位、紅方到另一端 11.2 單位，差 3.4）。
已修的是引擎機制真正依賴的部分（基地/泉水、塔與主堡路線參數、小兵出生、雙坑等距）。
