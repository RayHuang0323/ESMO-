- `GameView` 只掛載 `MobaRuntimeView3D`，不再讀／寫 map presentation preference，
  也不提供 legacy 切換按鈕。
- 權威資料流維持
  `LogicEngine snapshot → mobaRuntimeMapAdapter → Runtime renderers`；renderer 不回寫
  HP、target、勝負或位置。
- v3 tower snapshot 可附 `targetId/targetKind/lockShots`；tower FX 的 source／target

  snapshot.pos 畫巡遊／追擊／回營。Replay contract 未升版，舊 compact frame 仍以

- 英雄、小兵、建築與營地血條都由各 Runtime renderer 採 camera-facing 黑底槽與

### S29A：模擬規則集 / 時間 / 畫質（三條互不干擾的軸）

```
simTime          引擎世界時間。每 tick 固定推進 DT_SIM = 0.5 模擬秒。
                 ⇒ 與真實時間、瀏覽器 FPS、playbackRate **全部無關**。
playbackRate     只改「兩次 tick 之間的真實毫秒數」（tickMs = 500 / rate）。
                 dt 恆定 ⇒ **1×/2×/4× 不可能改變模擬結果**。
presentationTime 真實牆鐘。rAF 只用它算子幀進度 subT（0→1）供渲染內插。
                 渲染 FPS **不影響世界移動速度**（S29 §11 紅線）。
quality preset   battle/quality.js（low/medium/high）。只影響「怎麼畫」
                 （dpr / 後製 / 陰影 / FX 上限 / 光源），**絕不改變模擬結果**。
```

### MOBA 引擎的兩個注入層（S24 戰術 / S28 選手能力）

`LogicEngine` 有兩個**嚴格附加**的注入口。共同規則：**不呼叫 = 舊行為逐位元不變**；
knobs / mods 的形狀一律由**呼叫端**準備（引擎不 import 契約、不認得能力鍵名）；
只改「行為傾向 / 門檻 / 機率 / 節奏 / 路線」，**沒有任何傷害、勝率、金錢係數**。

| | S24 戰術層 | S28 選手能力層 |
|---|---|---|
| 開關 | `tacticOn` | `playerStatsOn` |
| 入口 | `configureMatch({blue,red,meta})` | `configurePlayers({blue,red,meta})` |
| 資料來源 | TacticScreen → `MobaTacticConfig.toEngineTactic` | profileStore.players → `getPlayerDerivedStats` → `mobaRosterAdapter.buildPlayerStatSlots` → `mobaPlayerStats.toEnginePlayerMods` |
| 對位 | side（blue/red） | **playerId**（`b1`–`b5`；非名字、非索引） |
| rng | 獨立 `rng2` 流（不污染主 `rng`） | **不新增任何抽樣**，只平移既有抽樣的門檻 |
| 中性 | `_neutralKnobs()` = 舊常數 | 能力全 70 分 ⇒ mods 全 0 / 倍率 1 |
| 證據 | `snapshot.tacticExec` | `snapshot.playerStatsExec`（每人撤退/團戰/目標計數） |

**呼叫順序**：`configurePlayers` 必須在 `configureMatch` **之前**——開局野區入侵在
`configureMatch` 當下擲骰，需要打野的 `invadeAdj`。唯一計算點在 `useLocalServer.start()`。

能力 → 引擎的 9 個作用點與 16 項能力映射表：見 `docs/design/MOBA選手能力注入.md`。
（`power` / `tough` **不受選手能力影響**——它直接乘進傷害式，注入即 damage multiplier。）

## 經營時間軸與財務閉環（Milestone N，2026-08-04）

### 時間只有一份

`meta.days` 是**唯一**的時間計數。week / season 一律由
`platform/economy/timeline.js` 的 `deriveTime(days)` 導出，不另存第二份。
`DAYS_PER_WEEK = 7`、`WEEKS_PER_SEASON = 12`；累計週次跨賽季不重置，
因此可以直接當週結算的全域唯一冪等鍵。

### 唯一時鐘

`profileStore.advanceDay(n)` 是**唯一**推進時間的入口：
每天結算訓練，跨過週結尾則以 `settleWeekInState` 結算那一週。
`advanceTrainingDay()` 保留為 `advanceDay(1)` 的別名。

畫面與其他 Store 動作**不得**自己加減 `finance.funds`——
與 S25 賽後結算（`applyMatchProgress` 是唯一發獎點）同一條紅線。

### 純邏輯 / Store 分層

沿用 S25 `progress/applyMatchProgress.js` 的手法：

```
platform/economy/timeline.js          純函式：日→週→賽季
platform/economy/weeklySettlement.js  純 reducer：settleWeekInState / advanceDaysInState
platform/economy/units.js             WAN 換算常數
profileStore                          薄包裝：一次 set()，另負責 inbox 通知
```

純模組不 import React / zustand / localStorage ⇒ `tools/check_finance_n.mjs`
可以直接在 Node 測。`WAN` 定義搬到 `units.js`，profileStore re-export，
避免純模組反向 import Store 造成循環。

### 冪等與帳本

- 冪等鍵 = 累計週次；`economy.settledWeeks[week]` 存 receipt。
- 同一週再次結算 → 完全不寫入，回傳既有 receipt 並標記 `alreadySettled`。
- 交易 id 由「週次 + 分類」決定性推導（`w12-salary`），不用 `Date.now()`。
- 不變式：本週交易金額加總 = receipt.net = 資金實際變化。驗證器逐項斷言。

### 收支的唯一計算

`buildWeekLines(state)` 同時服務結算與畫面預覽（`currentWeekPreview()`）⇒
Dashboard 與 FinanceScreen 顯示的數字，就是週結算會用的那一份，畫面不另算一套。

薪資唯一來源是 `players[].salary`（週薪・萬，Legacy 規格）；
`finance.weeklyCost` 定義為**不含薪資**的營運支出，兩者不重複計算。

## 經濟平衡層（Milestone N2，2026-08-04）

### 費率只有一份

`platform/economy/economyConfig.js` 是**唯一**設定來源：薪資公式、贊助拆分比例、
戰績取樣、三種情境、警告門檻。週結算不再讀 `finance.weeklyIncome` / `weeklyCost` /
`players[].salary` 這些 Legacy 種子值——`check_finance_n2.mjs` 有斷言擋住
（把種子值改成荒謬數字，結算結果不得改變）。

```
economy/economyConfig.js   費率與情境（唯一設定來源）
economy/salary.js          薪資由能力推導（overall / lv / potential）
economy/weeklySettlement.js 週結算（讀 config，不含任何 magic number）
economy/forecast.js        未來現金預測（唯讀，沿用 buildWeekLines）
```

### 一份計算，三個出口

`buildWeekLines(state, opts)` 同時服務：

1. **週結算**（`settleWeekInState`）
2. **本週預覽**（`currentWeekPreview` → Dashboard / FinanceScreen）
3. **現金預測**（`forecastWeeks` → Dashboard 未來四週）

⇒ 畫面顯示的數字就是結算會用的數字。驗證器有一條專門的斷言：
**預測與實際跑三週的結果必須一致**（實測 130.7 萬 vs 130.7 萬）。

### 賽事獎金的歸屬（避免雙重入帳）

| 收入 | 發放點 |
|---|---|
| 贊助固定收入 | 週結算 |
| 贊助績效獎金 | 週結算（依近期戰績縮放） |
| **賽事獎金** | **S25 `applyMatchProgress` 賽後入帳** |

週結算**不發**賽事獎金；現金預測則以帳本裡 `cat === "prize"` 的真實紀錄估未來收入。
這條界線不能模糊，否則同一筆錢會入帳兩次。

## 招募與養成閉環（Milestone O，2026-08-04）

### 招募的唯一寫入點

```
contracts/recruitment.js      RecruitmentTransaction.v1（契約 + 驗證 + 冪等鍵）
recruit/applyRecruitment.js   純 reducer：applyRecruitmentToState(state, tx)
profileStore.signProspect()   薄包裝：建單 → 套用 → save() → 收件匣
```

畫面與其他 Store 動作**不得**自己 push 進 `players[]` 或動 `finance.funds`
——與 S25 賽後結算、Milestone N 週結算同一條紅線。

### 冪等鍵與伺服器接管

冪等鍵 = `recruit:<poolSeed>:<prospectId>:v1`，由新秀池識別與池內編號決定性推導。
本機目前的 poolSeed 是 `RecruitScreen` 的 seed；**日後由伺服器發池時換成伺服器的
池 id 即可，交易單形狀不變**。交易單自帶簽約當下的選手快照，
所以伺服器改了新秀池演算法之後，既有合約仍能原樣重播。

### 三道保護

| 保護 | 判準 | receipt.reason |
|---|---|---|
| 名額 | `players.length >= ROSTER_CAP`（15） | `roster_full` |
| 餘額 | `finance.funds < 簽約金` | `insufficient_funds` |
| 重複 | `recruitment.signed[txId]` 已存在 | `alreadySigned: true` |

三者都是**完全不寫入**（`nextState === null`），不會產生半套狀態。

### 決定性

選手 id = `r<poolSeed>-<prospectId>`；士氣由 potential 推導（72–92）。
**沒有 `Math.random()`、沒有 `Date.now()`** ⇒ 同一張交易單重播逐欄相同。
這是日後由伺服器發放／重播的前提，驗證器有對應斷言。

### 資料歸屬（不建立第二套）

- 選手：唯一存放處仍是 `profileStore.players[]`，交易單只是入隊憑證。
- 資金：唯一來源仍是 `finance.funds`，招募扣款進既有交易帳本（`cat: "recruit"`）。
- 週薪：仍由 `economy/salary.js` 依能力推導；`players[].salary` 是身價／轉會欄位。
- 養成：沿用既有訓練系統（`assignTraining` → `advanceDay` → `applyCourse`），
  招募進來的選手不需要任何特殊處理。

## 名單分層與出賽陣容（Milestone O1，2026-08-04）

### 三層名單

`active`（一隊）／`bench`（替補）可出賽；`unlisted`（未登錄）不可。
存在 `players[].rosterTier`；舊存檔由 Legacy `status` 推導（主力→一隊，其餘→替補）。
把人設為未登錄時，`setRosterTier` 會一併把他從兩份陣容移除。

### 兩份陣容，一份選手

```
profileStore.players[]        選手唯一來源（不得有第二套）
profileStore.lineup   b1–b5   MOBA 出賽陣容（Milestone E）
profileStore.csLineup f1–f5   CS 出賽陣容（Milestone O1）
```

CS 之前沒有陣容：拿 `status === "主力"` 的前五個，誰上場看陣列順序。
現在 `toFpsRoster(players, csLineup)` 依陣容取人，缺人回 `null`。

### 出賽閘門

`squadCheck(mode)` → `validateSquad()`，回傳**可顯示的中文理由**：

| code | 意義 | 層級 |
|---|---|---|
| `empty_seat` | 該席位沒有人 | 阻擋 |
| `unknown_player` | 指到不存在的選手 | 阻擋 |
| `duplicate_player` | 同一人佔兩席 | 阻擋 |
| `ineligible` | 未登錄名單 | 阻擋 |
| `role_mismatch` | 定位與席位不符 | 警告（`strictRole` 時阻擋） |

畫面**不自己判規則**，只顯示 `check.errors[].message`。

### 提交契約（伺服器不信任前端數值）

`squadSubmission(mode)` 產生的提交單只有 `{schema, mode, seats, submittedAt}`——
**只有 playerId 與席位，沒有任何能力／戰力／等級**。
`validateSquadSubmission()` 會拒絕夾帶 `stats/power/tough/lv/rating` 的提交單。
日後連線時，伺服器拿 playerId 自行查詢真實數值即可，客戶端說什麼都不影響結算。

### 結果回寫

`mobaProgressAdapter` 以 `seatPlayers(lineup, players)` 解析出**實際出賽的人**，
`playerProgress[].playerId` 寫的是那個人的 id，不是席位 id；
CS 走 `_gid`。席位換成替補時，XP 就寫給替補。驗證器有對應斷言。

## 疲勞・狀態・受傷（Milestone O2，2026-08-04）

### 掛在既有的單一結算入口

出賽損耗**不是**另一條寫入路徑：它掛在 S25 的 `applyProgressToState` 裡，
與經驗、等級、天賦點在同一個迴圈、同一個 `nextState`。

```
BattleResult / CsMatchResult
   → adapter（依實際陣容產生 playerProgress[].playerId）
   → applyProgressToState   ← XP／等級／天賦點／**出賽損耗** 一次寫完
   → profileStore.set()
```

因此三件事自動成立：
1. **只有實際出賽的人**被套用——替補與未登錄根本不在 `playerProgress` 裡。
2. 沿用既有的 `transactionId` 冪等 ⇒ 不會重複扣體力或重複發經驗。
3. receipt 逐人回報 `condition`（扣了多少、連續第幾場、是否受傷）可稽核。

### 決定性（伺服器可重算）

受傷判定由 `deterministicRoll("${transactionId}:${playerId}")` 推導，
傷停天數用第二個雜湊 `:days`。**沒有 `Math.random()`、沒有時鐘。**
伺服器拿同一張交易單重算會得到逐位元相同的結果 ⇒
客戶端提交的成長／狀態數值一律不必信任（`5e` 斷言：交易單宣稱 Lv99 也無效，
一律以 Store 現值重算）。

### 恢復由統一時鐘驅動

`profileStore.advanceDay(n)` 每一天對每位選手呼叫 `applyDailyRecovery`：
傷停 −1 天、沒排訓練的人 +8 體力、隔天沒出賽就把連續出賽計數歸零。
有排訓練的人不在這裡回體力（避免與 `applyCourse` 雙算）。

### 不可出賽的判定只有一處

`matchFitness(player)` → `{ok, code, message}`（`injured` / `exhausted`）。
`matchSquad.validateSquad` 直接引用它，**不重寫規則**；
`autoFillSquad` 也用它過濾。畫面只顯示 message。

## 出賽申請契約（Milestone O3，2026-08-04）

### 三層契約的分工

```
MatchLineup.v1  (E)   席位 ↔ 選手的映射規則
MatchSquad.v1   (O1)  這份陣容合法嗎 + 要提交什麼（只有映射）
MatchEntryRequest.v1 (O3)  一次出賽申請：身分 + 編制 + 隊伍版本 + 決定性識別 + 快照
```

O3 建立在 O1 之上，**不重寫規則**：資格判定仍走 `validateSquad`，
不可出賽仍走 O2 的 `matchFitness`。

### 只送身分，不送數值

申請單欄位固定為
`{schema, squadSchema, transactionId, mode, teamId, teamName, rosterVersion, squad, submittedAt}`，
`squad` 每列只有 `{seat, playerId, role, seatRole, tier}`。

`validateMatchEntryRequest` **遞迴掃描**整張單，命中 `FORBIDDEN_VALUE_KEYS`
（stats/power/tough/rating/lv/level/xp/energy/morale/condition/damage/dmg/derived/ovr/score）
即拒絕。伺服器一律以 playerId 自行查詢真實資料。

### 隊伍版本（偵測名單漂移）

`rosterVersionOf(players, seats, mode)` = 雜湊（成員 id + 分層 + 席位指派）。
**刻意不含能力數值**：練功、升級、受傷不會讓已送出的申請失效，
但換人、改分層、改陣容會 ⇒ 伺服器能分辨「名單真的變了」與「只是練了功」。

### 決定性識別

`entry:<mode>:<rosterVersion>:<seatsHash>:s<season>w<week>d<day>`
⇒ 同陣容同日重送＝同一個 id（伺服器天然去重）；換人或換天＝不同場次。
`transactionId` 必須可由內容重算，竄改會被驗證擋下。

### 畫面

`src/screens/common/MatchEntryPanel.jsx` 是 MOBA 與 CS 賽前頁**共用**的面板，
資料全部來自 `profileStore.matchEntry(mode)`——畫面不自己判規則、不自己算數字。

## 配對票券（Milestone O4，2026-08-04）

### 四層契約的分工

```
MatchLineup.v1        (E)   席位 ↔ 選手
MatchSquad.v1         (O1)  陣容合法嗎
MatchEntryRequest.v1  (O3)  一次出賽申請（身分＋編制＋隊伍版本＋決定性識別）
MatchmakingTicket.v1  (O4)  一次排隊（狀態機）
MatchAssignment.v1    (O4)  配對結果（只能由 gateway 簽發）
```

每一層都**不重寫下一層的規則**：O4 的資格判定仍走 O3 → O1 → O2。

### 狀態機是唯一權威

```
idle → validating → queued → matched
                 ↘        ↘ cancelled / rejected
```

轉移表寫在 `contracts/matchmaking.js`，`transitionTicket` 是唯一入口。
畫面與 Store **不得自己判斷**某個狀態能不能變成另一個狀態。
`canEnterMatch(ticket)` 是「能不能進對戰」的唯一判定——
**只有 matched 且帶合法指派單**才行，取消與拒絕一律擋下。

### 對手由誰決定

`MatchAssignment` 只能由 gateway 產生，並且契約會拒絕：
比賽結果（winner/result/score/rewards/mvp/kills/outcome）、
對手戰力數值（power/stats/rating/lv）、與票券不符、缺種子或缺簽發者。
⇒ 客戶端無法指定對手強弱、無法挑有利種子、無法宣稱結果。

### mock gateway 不是後端

`platform/matchmaking/mockGateway.js` 是**純函式**的決定性模擬：
等待秒數、對手、種子皆由 ticketId 雜湊推導。
它每次輪詢都會用**當下的名單**重新驗證資格 ⇒ 排隊中狀況改變會被拒絕。
接上真伺服器時只換這一支，票券契約與畫面不動。

## 比賽房間（Milestone O5，2026-08-04）

### 五層契約

```
MatchLineup.v1        (E)   席位 ↔ 選手
```

每層都不重寫下層規則。O5 的進場判定 `canEnterRoom` 建立在 O4 的
`validateAssignment` 之上。

### 進場的唯一判定

`canEnterRoom(room, ticket)` 要件（缺一不可）：

1. 房間狀態為 `confirmed` 且 `confirmations.us && confirmations.opponent`
2. 房間帶 `issuedBy`（gateway 簽發；自造房間拒絕）
3. `room.ticketId === ticket.ticketId`（**舊票券不可進新房間**）
4. `room.assignmentId === ticket.assignment.assignmentId`（指派單不可被抽換）

畫面只顯示 `blockedReason`，**不自己判規則**。

### 房間與票券的連動

`pollMatchRoom` 每次都先檢查票券：票券不是 `matched`、或 `ticketId` 對不上，
房間立刻轉 `cancelled`（原因「票券已失效，房間關閉」）。
⇒ 重新排隊會拿到新票券，舊房間自動作廢。

### 倒數

進入 `ready_check` 才開始倒數（`READY_SECONDS = 20`）。
`isExpired` / `remainingSeconds` 是唯一的時間判定，逾時後 `confirmSide` 一律拒絕。

## 比賽場次與進場（Milestone O6，2026-08-04）

### 六層契約

```
MatchLineup.v1        (E)   席位 ↔ 選手
MatchSquad.v1         (O1)  陣容合法嗎
MatchEntryRequest.v1  (O3)  一次出賽申請
MatchmakingTicket.v1  (O4)  一次排隊
MatchAssignment.v1    (O4)  配對結果（gateway 簽發）
MatchRoom.v1          (O5)  比賽房間與雙方確認
MatchSession.v1       (O6)  正式場次與一次性進場令牌
```

### 進場的最終把關

對戰入口的唯一許可是 `consumeLaunchToken(session, token, {room, ticket, now})`。
它會一次檢查：令牌正確且未使用、場次未逾期未取消、簽發者存在、
房間仍是 `confirmed` 且 id 相符、票券仍是同一張、指派單與 seed 未被竄改。

⇒ **重複進場、舊票券、竄改 seed、自造場次全部進不去**，且每一種都有中文原因。

### 為什麼場次要能在重整後恢復

需求明確要求「保留重新整理後恢復尚未開始之場次的能力，但不可重複建立比賽」。
因此：

- migration **不清掉** `created` 狀態的場次（票券 `matched`、房間 `confirmed`
  本來就會保留）。
- 防重複不靠清狀態，而靠 **`tokenUsed` 會被一起存下來** ——
  已啟動的場次重整後仍然是 `launched` / `tokenUsed: true`，再按也進不去。
- `sessionId` 由 roomId 推導 ⇒ 同一房間不可能產生第二場比賽。

### 啟動參數

`launchConfigOf(session)` → `{sessionId, mode, seed, opponentId, opponentName, issuedBy}`。
**沒有陣容、沒有能力、沒有比賽結果。** seed 是 gateway 在配對時決定的那一個。

⚠ 現況：`launch` 已存進 Store 供對戰入口讀取，但**尚未接到 LogicEngine 的種子**
（需要改 GameView / LoadingScreen 的參數傳遞，屬後續項）。

## 權威場次與單次結算（Milestone O7，2026-08-04）

### 七層契約

```
MatchLineup.v1        (E)   席位 ↔ 選手
MatchSquad.v1         (O1)  陣容合法嗎
MatchEntryRequest.v1  (O3)  一次出賽申請
MatchmakingTicket.v1  (O4)  一次排隊
MatchAssignment.v1    (O4)  配對結果（gateway 簽發）

MatchResult.v1        (O7)  比賽結果（綁定場次、防重送、防衝突）
```

### seed 的單一權威來源

```
gateway 配對 → assignment.seed
   → session.seed（O6）
   → launchConfig.seed（一次性令牌換得）
   → matchmaking.launch（Store）
   → GameView 讀 Store → start({ seed })
   → useLocalServer: (seed >>> 0) | 1 → new LogicEngine(seed)
```

**LogicEngine 不再自行產生隨機 seed**（有場次時）。
`GameView` 刻意不接受 props 傳 seed ⇒ 前端無法覆寫。
沒有場次時退回時鐘，並在 replay capture 標記 `seedSource: "local"`。

### 場次生命週期

```
created ──consumeLaunchToken──> launched ──completeSession──> completed
                                   │  └─abandonSession──> abandoned
                                   └─resumeSession（可多次，不再消耗令牌）
cancelled / expired 為另兩個終局
connection: connected ⇄ disconnected（正交，斷線仍可恢復）
```

⚠ `launched` **不是終局**——這是 O7 相對 O6 的語意變更，
`check_match_session_o6` 的兩條斷言已同步改為更嚴格的整組比對。

### 單次結算的分工

```
MatchResult.v1 驗證（來源／綁定／衝突）
   → settleMatchResultInState
        → applyProgressToState   ← S25 唯一發獎入口（錢／經驗／體力／傷勢）
        → 記錄 settlement receipt ＋ 追蹤鏈 ＋ 失敗原因
```

`settleMatchResult` **不自己加錢、加經驗、扣體力**。
冪等有兩層：結算帳本（`settlements[settlementId]`）與 S25 的 `transactionId`。
失敗時完全不寫入 ⇒ 重試安全，不會只完成一半。

### 追蹤鏈

`matchTrace()` 回傳
`ticketId → assignmentId → roomId → sessionId → matchId → resultId → settlementId`，
**不含 launchToken**。畫面上的追蹤區塊只在 `isDebugMode()` 顯示。

## 選手能力如何影響 MOBA（Milestone P0-2，2026-08-05）

### 紅線與繞法

S28 紅線：`dmgAmt = p.power * dt * ...` ⇒ **能力不得注入 `power`**。

但引擎的 `p.power = p.basePower * powerMultFor(p.mlv)`（`LogicEngine.js:628`）
——**戰力本來就由本場等級導出**。因此 P0-2 的注入點是：

```
選手能力 → xpRateScale（±6%）→ _addXp() → mlv 成長速度
                                        → powerMultFor(mlv) → power／maxHp
```

⇒ 能力**間接**影響戰力，但沒有任何一項係數乘進傷害式。

### 注入點只有一處

`LogicEngine._addXp(p, amt, drain)` 是所有經驗來源（小兵／野怪／擊殺／助攻／推塔）
的唯一入口，係數只套在那裡，且**只套在 `amt > 0`**——
`drain`（等級落後補正）不縮放，避免高能力選手連被扣都比較少的雙重優勢。

### 三層保護

1. **opt-in**：未 `configurePlayers` ⇒ `_mod` 回 null ⇒ 係數不存在 ⇒
   既有對局（regress / regress2 / 所有舊 fixture）逐值不變。
2. **硬限幅**：`SCALE_CLAMP.xpRateScale = [0.94, 1.06]`。
3. **中性即無效**：全 70 分 ⇒ ×1（沿用 S28 的 `u(70) = 0` 慣例）。

### 目前的能力 → 對戰影響全貌

| 模式 | 管道 | 影響 |
|---|---|---|
| CS | `fpsRoster` → 引擎短鍵 | 直接影響模擬 |
| MOBA | `toEnginePlayerMods` → 行為 mods | 撤退／gank／roam／分推／推線／參團 |
| MOBA | `xpRateScale` → `_addXp` → `mlv` | **本場成長速度 → 戰力（P0-2 新增）** |
| MOBA | `lastHitLoss` → `_awardMinionXp` | **補刀漏兵（P0-3 新增）** |
| MOBA | `attackWaste` → 傷害段前 | **該 tick 空揮（P0-3 新增）** |
| MOBA | `castMiss` → `_summonerSpellsV2` | **技能放空，冷卻照算（P0-3 新增）** |
| MOBA | `focusRate` → `_combatStep` 選敵 | **改打殘血目標（P0-3 新增）** |
| MOBA | `retreatLate` → 撤退門檻 | **該撤時撤太晚（P0-3 新增，決定性）** |

## Milestone P0-3：最小戰鬥品質層（2026-08-05）

P0-2 之後 MOBA 仍然沒有操作品質模型。P0-3 補上五個掛點（見上表），
把「能力高＝少犯錯」變成可觀測的行為，而**不是**把能力乘進傷害。

三個不變量，任何後續改動都不得破壞：

1. **中性（全 70）＝ 現行行為**。五項係數全為 0 ⇒ 不擲骰、不改分支。
   `tools/check_moba_quality_p03.mjs` §3a 逐位元證明。
2. **單向映射**。`ONESIDED_CLAMP` 決定方向：penalty 只罰低能力、bonus 只給高能力。
3. **獨立亂數流 `rng3`**（在 `configurePlayers` 建立）。
   ⚠ **不得改用 `rng2`**——那是戰術層的流，被多抽一次就會平移 Gank／遊走時機，
   等於能力層默默改動戰術層。

紅線（S28）仍然成立：`dmgAmt = p.power * dt * R.dmgK * ...` 沒有被能力碰過。
`attackWaste` 期望值上等同少量 DPS 損失，但它是**離散事件**而非傷害乘數——
這是自覺取捨，已在驗證器 §2 用原始碼斷言釘住。
