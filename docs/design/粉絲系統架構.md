# 粉絲系統架構（Fan System v1）

> 規劃日期：2026-08-23
> 基準：`main @ 564986f`
> 狀態：**規劃完成，未實作、未核准開工**。本輪只做 Audit + 設計質疑 + 架構規劃。
> 範圍：粉絲（fans）的資料歸屬、來源、與 Sponsor / Finance / Season / Match 的關係，以及 v1 的最小可行版本。

---

## 〇、一句話結論

**repo 裡已經有粉絲數、有公式、有門檻、有共用發放點與冪等帳本——缺的只有一個合理的種子值、來源權重、一條賽季來源。**

所以這件事的正確定位是**「接通既有設計」**，不是「新增一套系統」。

## 一、Audit：現況（2026-08-23 於 `main @ 564986f` 實查）

### 1.1 最重要的一個事實

| 項目 | 值 |
|---|---|
| 贊助商粉絲門檻 `SPONSORS[].reqFans` | 0 / 500 / 800 / 1500 / 2000 / 3000 |
| `profileStore` 預設 `meta.fans` | **128,000** |

> **粉絲門檻從開局第一秒就全部達標。**
> 「粉絲 → 解鎖更好的贊助」這條唯一的粉絲玩法，目前在 repo 裡是**死的**——
> 不是還沒做，是做了但被種子值蓋掉。真正在擋人的只有 `reqWins`（0/3/5/10/15/20 勝）。

### 1.2 已經存在哪些粉絲相關資料

| 資料 | 位置 | 狀態 | 說明 |
|---|---|---|---|
| `meta.fans` | `platform/profileStore.js:287` | **會動** | 唯一 canonical 粉絲數，種子 128,000 |
| `fanGain` 公式 | `platform/data/matchRecorder.js` | **會動** | 勝 `120 + margin×140 + streak×25`；敗 `15 + (1−margin)×30` |
| `teamRewardsFor()` | `progress/rewardFormulas.js` | **會動** | MOBA / CS **共用同一支**，差異只在各自 adapter 的 `marginF` |
| `meta.reputation` | `platform/profileStore.js:287` | **死的** | 種子 47，但入帳一律 `reputation: 0`（註解自承「無經驗證公式」） |
| `SPONSORS[].reqFans` | `data/playerModel.js:247-252` | **被種子蓋掉** | 見 1.1 |
| `fanCount` | `EsportsGame.jsx`（Legacy） | **平行實作** | `useState(2041)`，只活在 1.4MB 原型，與主幹無關 |
| `mode.audience` | `screens/DashboardScreen.jsx:674` | **假數字** | 寫死 `"2,041"` / `"訓練"` / `"賽季"`，不讀任何資料 |

### 1.3 分類

**只是 UI 顯示**
- Home Hero 與手機頁首的「N 支持者」（唯讀 `meta.fans`）
- 戰隊詳情頁的粉絲數字
- 賽後獎勵收據的「聲望 —」（永遠 0，所以誠實顯示破折號）
- 首頁三個模式磚的 `audience`——**完全寫死的假數字**

**真的會改變數值**（只有一條路徑，而且已經很乾淨）

```
賽果
  → rewardFormulas.teamRewardsFor()
  → contracts/matchProgressTransaction.js
  → progress/applyMatchProgress.js:192   ← 唯一發放點
  → 冪等：processedMatchTransactions[transactionId]
```

### 1.4 Sponsor 是否已經依賴粉絲

**程式碼上是，實際上不是。** `signSponsor(id, ctx)` 確實檢查 `ctx.fans >= sp.reqFans`，
但因為種子值遠超所有門檻，**粉絲對贊助的影響目前等於零**。

### 1.5 Match / Season 是否產生粉絲

| | 結果 |
|---|---|
| 單場比賽 | **會**——MOBA 與 CS 都會，走同一支公式、同一個發放點 |
| 賽季 | **完全不會**——`platform/competition/**`、`competitionAward.js`、`weeklySettlement.js`、`honors.js` 裡**一次 `fans` 都沒有出現**。冠軍、Major、亞洲總決賽對粉絲毫無影響 |

### 1.6 重複或半完成的舊設計

| 問題 | 性質 | 建議 |
|---|---|---|
| `reputation` 永遠 0 | 半成品，與粉絲功能重疊 | **移除或併入粉絲**，不要兩套聲望純量 |
| `reqFans` 被種子蓋掉 | 設計已寫但不生效 | 校準種子與門檻（v1 核心） |
| Legacy `fanCount` | 平行實作 | 不動（Legacy 是參考規格，不是執行路徑） |
| Mode card `audience` | 寫死假資料 | 接真值或拿掉，不要留假數字 |
| `meta.fans` 無 sanitize | 載入時只做 `{...DEFAULT.meta, ...saved.meta}` | 壞存檔會讓 `fans` 變成非數字並一路流下去 |

## 二、Grilling：對這個需求的質疑

以下每一題都先站在反對面。

### Q1 粉絲系統到底增加什麼玩法？

如果粉絲只餵贊助門檻，而門檻已經全部達標——增加的玩法是**零**。現在就是這個狀態。

> **裁決**：粉絲要有玩法，必須至少有一件「玩家想要、但粉絲不夠就拿不到」的東西。
> 目前 repo 裡唯一夠格的候選是**贊助合約**。

### Q2 與 Reputation / Sponsor / Finance 重複嗎？

**與 Reputation 直接重複。** `meta.reputation` 就是一個「戰隊聲望純量」，種子 47、從不變動、畫面顯示「—」。

與 Sponsor / Finance 不重複：粉絲是**資格與價碼**，錢是**結果**，是因果不是並列。

> **裁決**：做粉絲的**前提**是先處置 `reputation`——刪掉，或明確定義成別的東西。不能兩個都留著都不動。

### Q3 玩家為什麼會在意粉絲增加？

不會，除非它擋住某個門。經營遊戲裡玩家在意一個數字通常只有兩個理由：它**解鎖**東西，或它**會掉**。

> **裁決**：選「解鎖」，不要選「會掉」（理由見 Q9）。

### Q4 如果粉絲只是數字，會不會沒意義？

會，而且這正是目前的狀況。**首頁已經在顯示「12.8萬 支持者」，而那個數字完全沒有後果。**

> **裁決**：v1 的第一優先**不是**增加粉絲來源，是讓現有的粉絲數有後果。

### Q5 會不會形成雪球？

會，而且現有公式**刻意在助長**：`streak × 25`。接上贊助之後就是完整迴圈：
贏 → 粉絲 → 更好贊助 → 更多錢 → 更好選手 → 更容易贏。

但要誠實：這是經營遊戲本來就該有的正回饋。問題不是有沒有雪球，是雪球有沒有天花板。

> **裁決**：用三道天花板，不要用粉絲衰減：
> ① 贊助分級是**階梯不是線性**（到頂就到頂）
> ② 合約會到期，必須重新談
> ③ 粉絲**永遠不碰數值**（產品紅線）

### Q6 Practice 與正式 Season 應該給一樣多嗎？

**現在給的一模一樣。** 造成兩個問題：刷練習賽是最有效率的漲粉手段，而正式比賽**不特別**。

> **裁決**：必須分開，差距要明顯。**這是本案最有產品價值的單一改動**——
> 它讓「打正式賽季」第一次有了比賽果本身更多的意義。

### Q7 MOBA 與 CS 應該共用戰隊粉絲嗎？

**共用。** 理由不是省事，是**贊助只有一份**——拆成兩池粉絲就必須拆成兩池贊助。
而且 `teamRewardsFor()` 本來就是共用的，這條不用做任何事。

### Q8 現在要做 Player 個人人氣嗎？

**不要。沒有任何消費端。** 個人人氣要有意義，必須有轉會市場議價、個人贊助、或粉絲對特定選手的忠誠度——這三個現在都不存在。

### Q9 粉絲下降真的有必要嗎？

**反對做衰減。** 每日衰減會變成**雜務壓力**：玩家為了不掉數字而定期上線做無聊的事，那是留存機制不是經營樂趣。

但「只漲不跌」會讓它變成純計數器。解法不是讓粉絲掉，是**讓合約會到期**——
停滯的隊伍不會掉粉，但下一份合約談不到更好的價碼。**壓力來自機會成本，不是懲罰。**

> **裁決**：v1 **不做粉絲衰減**。

### Grilling 之後改變的三件事

1. 主要工作從「加系統」改成「接通既有設計 ＋ 校準數值」。
2. 先處置 `reputation` 變成**前置條件**，不是可選項。
3. 練習賽與正式賽的權重差異，從「細節」升格為**本案最主要的產品價值**。

## 三、三個方案

### A · 極簡版：把現有的修好

玩家會感覺到：開局粉絲是個小數字，好的贊助商簽不到；打贏比賽粉絲成長，某天終於解鎖更好的贊助。正式比賽給的粉絲明顯比練習賽多。

| 面向 | 評估 |
|---|---|
| 複雜度 | 幾乎為零——調種子值、加一個來源權重 |
| Sponsor 互動 | 門檻真的擋人（現況完全不擋） |
| Finance 互動 | 間接：簽到更好的贊助 → 週收入更高 |
| 雪球 | 輕微，贊助分級有天花板 |
| 開發成本 | **很低**，約半個 Sprint |
| 擴充性 | 好，之後加來源就是加權重表一列 |

### B · 推薦版：粉絲同時決定「能簽誰」與「值多少」★

玩家會感覺到：A 的一切，加上——同一家贊助商，粉絲多的時候談到的週收入更好。
冠軍、Major 會給一次明顯的粉絲跳躍。賽後看得到「+240 粉絲」，賽季成績單看得到「本季 +8,400」。

| 面向 | 評估 |
|---|---|
| 複雜度 | 低——一張分級表 ＋ 一個賽季入帳點 |
| Sponsor 互動 | **門檻 ＋ 價碼**，粉絲成為長期經營主軸 |
| Finance 互動 | 只透過贊助週收入，**不新增第四個金錢入口** |
| 雪球 | 可控：分級是階梯、合約會到期、粉絲不碰數值 |
| 開發成本 | **低—中**，約 1.5 個 Sprint |
| 擴充性 | 很好——品牌等級、個人人氣、Fan Shop 都能長在同一個數字上 |

### C · 稍微豐富版：B ＋ 品牌等級與期待值

玩家會感覺到：B 的一切，加上「地區 → 全國 → 國際」的品牌等級；等級越高，粉絲對成績的**期待**越高，大隊伍輸給小隊伍漲粉明顯變慢。

| 面向 | 評估 |
|---|---|
| 複雜度 | 中——多一層等級狀態與期待值計算 |
| 雪球 | **最好的一個**：期待值是天然的負回饋 |
| 開發成本 | 中，約 2.5–3 個 Sprint |
| 風險 | 期待值很難調到「有感但不惱人」，容易變成懲罰玩家 |

### 選 B

A 太薄——修好門檻之後，粉絲仍然只是一道一次性閘門。
C 的期待值需要一輪專門的數值校準，而 `economyConfig` 自己標著「待轉會與合約系統完成後再校正」，在浮動地基上疊期待值會兩邊都調不準。

**B 讓粉絲從「一道閘門」變成「一條持續有回報的曲線」，多出來的複雜度只有一張分級表。**
C 的品牌等級可以之後直接長在 B 上，不會白做。

## 四、Fan System v1 設計（方案 B）

原則：**不新增 Store、不新增金錢入口、不碰數值。**

| # | 問題 | 答案 |
|---|---|---|
| 1 | Canonical ownership | `meta.fans`（已經是）。寫入者只有兩個且都已有冪等帳本：`applyMatchProgress`（單場）與 `settleCompetitionAward`（賽季名次）。**不新增第三個** |
| 2 | fans 存哪裡 | 就存 `meta.fans`，不開新 Store／新切片。「最近變化」**用推導**（讀既有 `finance.transactions` / 收據帳本），不新增第二份 log。賽季成長需要起點 → 賽季建立時記一個 `fansAtSeasonStart` 快照（單一數字） |
| 3 | MatchResult 如何影響 | 沿用 `teamRewardsFor()`，**只多乘一個來源權重**。權重由 `origin.kind` 與賽事 tier 決定，不由畫面決定 |
| 4 | Practice vs Season | 建議起點（待實測校準）：練習／自由對戰 `×0.25`、聯賽賽程 `×1.0`、Major／季後賽 `×1.5`；冠軍與 Major 奪冠另給**一次性**大額（走賽季入帳點，不是單場） |
| 5 | MOBA vs CS 同公式 | **是，而且不用做任何事**——`teamRewardsFor()` 本來就共用，項目差異已由各自 adapter 的 `marginF` 表達 |
| 6 | Sponsor 如何讀 fans | 維持 `signSponsor(id, ctx)` 由呼叫端傳入真值（不在 Store 內重算）。新增：**價碼分級**——`weekly` 依粉絲級距乘係數（階梯，非線性） |
| 7 | Finance 是否受影響 | **只透過贊助週收入**。不新增 fans→money 直接路徑，金錢入口維持既有三個，`forecast` 不外推粉絲 |
| 8 | Home 呈現 | Club Status／戰隊快照加一列：**總粉絲 ＋ 本週變化**。**不做粉絲中心頁**。順便把模式磚寫死的 `audience` 接真值或移除 |
| 9 | Season Recap | 加一列「本季粉絲成長 +N」，用 `fansAtSeasonStart` 相減 |
| 10 | Save / migration | ① 加 **sanitize**（`fans` 必須是有限非負整數）——現在完全沒有；② **舊存檔怎麼辦是產品決策**，見風險 R2 |
| 11 | 不重複結算 | 不發明新機制：單場走 `processedMatchTransactions[transactionId]`，賽季走 `processedCompetitionAwards[finalStandingsId]`，兩個帳本都已存在且已被 verifier 守著 |
| 12 | 新 verifier | 要，一支 `check_fan_system.mjs` |

### 4.1 粉絲如何增加 / 是否減少

**增加**
- 單場勝負（既有公式 × 來源權重）
- 連勝加成（既有 `streak × 25`）
- 賽季名次結算（新增，走既有獎金入帳點）
- 冠軍 / Major 奪冠（一次性）

**減少**
- **v1 不做任何粉絲減少。** 壓力來自贊助合約會到期——停滯的隊伍不掉粉，但下一份合約談不到更好的價碼。

### 4.2 verifier 要守的六條

1. `meta.fans` 只有兩個寫入點，且都經過冪等帳本
2. 粉絲**不進入** `configurePlayers` / `configureMatch` / 任何 stats 路徑
3. 練習賽權重 **<** 聯賽權重 **<** Major 權重（順序，不是寫死的數字）
4. 同一場比賽重複結算不會重複加粉絲
5. 畫面只讀不算——Sponsor 的資格與價碼由 Store 出口提供
6. 壞存檔的 `fans` 會被 sanitize 成合法值

## 五、Match / Season / Sponsor / Finance 關係

```
來源                         入帳點（皆已有冪等帳本）        真相            去向
───────────────────────      ────────────────────────       ──────────      ─────────────────
練習／自由對戰 ×0.25   ┐
聯賽賽程       ×1.0    ├──→  applyMatchProgress        ┐
Major／季後賽  ×1.5    ┘     （transactionId）         │
                                                       ├──→  meta.fans ──→  Sponsor
賽季名次／冠軍（一次性）──→  settleCompetitionAward     ┘    （只漲不衰減）   ├ 能簽誰（門檻）
                             （finalStandingsId）                            └ 值多少（分級價碼）
                                                                                    │
                                                                                    ↓
                                                                              Finance
                                                                        （只有贊助週收入這一條）

                                   ✗ meta.fans ──╳──→ 選手數值 / 勝率 / Battle Engine
                                     產品紅線：粉絲永遠不得連到這裡（由 verifier 擋住）
```

**壓力來自哪裡**：合約會到期 ⇒ 停滯的隊伍不掉粉，但下一份談不到更好的價碼（機會成本，不是懲罰）。

## 七、現在不要做

**沒有消費端的**
- Player 個人人氣（沒有轉會議價／個人贊助）
- Fan Shop、周邊、票務
- 社群媒體模擬、貼文、輿論

**會踩紅線的**
- 粉絲加選手數值或勝率
- 粉絲直接換錢（第四個金錢入口）
- 每日粉絲流失
- 第二個 Store／第二套 progression

**時機未到的**
- 品牌等級與期待值（方案 C，等經濟參數穩定）
- MOBA / CS 分開的粉絲池
- 粉絲影響門票與場館收入

## 八、Sprint 拆分

有依賴順序。**F0 是前置，不做它後面全部會建在重複概念上。**

| | 內容 |
|---|---|
| **F0** | 處置 `reputation`（刪除或重新定義）＋ 補上 `meta.fans` 的載入 sanitize。**前置，不含任何玩法** |
| **F1** | 把粉絲門檻接通：校準種子值與 `reqFans`，加來源權重（練習 < 聯賽 < Major）。**交付後粉絲第一次有後果** |
| **F2** | 賽季粉絲入帳：名次與冠軍的一次性粉絲，走既有 `settleCompetitionAward` 冪等路徑；記 `fansAtSeasonStart` 快照 |
| **F3** | 贊助價碼分級：粉絲級距決定 `weekly` 係數（階梯，非線性）。方案 B 相對 A 的核心差異 |
| **F4** | UI 五個落點 ＋ 假 `audience` 清理，桌機與手機各驗一次 |
| **F5** | `check_fan_system.mjs`（六條斷言 ＋ mutation sentinel）。可與 F1 併，但不得晚於 F3 |

> 建議 F1 交付後**實際玩一段**再決定要不要做 F3。

## 九、風險

| # | 風險 | 說明與處置 |
|---|---|---|
| R1 | **數值校準沒有基準** | `economyConfig` 自己標著「待轉會與合約系統完成後再校正」。粉絲接上贊助會動到現金流平衡。**處置**：F1 只調粉絲側不動既有費率；重新校準列為 F3 之後的獨立一輪 |
| R2 | **舊存檔怎麼辦（產品決策）** | 現有存檔 `fans` = 128,000。若新門檻按小數字設計，舊存檔會直接全解鎖，等於老玩家跳過整個系統。三個選項：①只有新局套用新刻度（最安全，但老玩家體驗不到）②一次性 migration 換算刻度（有感，但改動老玩家存檔）③門檻改成相對值（不動存檔，但公式變複雜）。**這是產品取捨不是技術取捨，需 Ray 決定** |
| R3 | **雪球** | 贏→粉絲→贊助→錢→更強。**處置**：分級是階梯有天花板、合約會到期、粉絲不碰數值。若實測仍過強，先調階梯而不是加衰減 |
| R4 | **兩個矛盾的數字** | 首頁同時有真的「12.8萬 支持者」與寫死的「👁 2,041」。不處理會直接被玩家看到 |
| R5 | **`reputation` 沒處置就開工** | 會變成兩個聲望純量並存，日後每次都要解釋差別。**F0 必須先做** |
| R6 | **「有趣」無法用 verifier 驗** | gate 能守住不重複結算與不碰數值，但守不住「玩家有沒有感覺」。F1 交付後應該實際玩一段再決定 F3 |

## 十、GO / NO-GO

**GO —— 但先做 F0，且把它定位成「接通既有設計」而不是「新增系統」。**

理由：repo 裡已經有粉絲數、有公式、有門檻、有共用發放點與冪等帳本。缺的只有
**一個合理的種子值**、**來源權重**、**一條賽季來源**。以這麼低的成本換到
「贊助有追求、正式賽季比練習賽更有份量」，投報率很高。

但如果不先處置 `reputation`、不先決定舊存檔怎麼辦（R2），這件事會在半路變成一個誰都說不清楚的雙軌設計。
