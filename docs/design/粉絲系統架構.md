# 粉絲系統架構（Fan System v1）

> 規劃日期：2026-08-23
> 基準：`main @ 564986f`
> **狀態：✅ 產品核准（2026-08-23，Ray）。規格已依最終產品裁決更新，尚未開工。**
> 範圍：粉絲（fans）的資料歸屬、來源、與 Sponsor / Finance / Season / Match 的關係，以及 v1 的最小可行版本。

## 〇、一句話結論

**repo 裡已經有粉絲數、有公式、有門檻、有共用發放點與冪等帳本——缺的只有把門檻校準到正確的數量級、加上來源權重、補一條賽季來源。**

定位是**「接通既有設計」**，不是「新增第二套系統」。

## 〇之二、最終產品裁決（2026-08-23）

> 以下十一點是本案的**產品決策，優先於本文件其餘任何敘述**。
> 下方章節已全數依此改寫；若有殘留矛盾，以本節為準。

| # | 決策 | 影響 |
|---|---|---|
| 1 | **Fan System GO**，定位維持「接通既有設計」 | 不建立第二套 progression、第二個 Store |
| 2 | **保留約 128,000 的粉絲數量級**，不改成 500 / 1,000 小尺度 | 舊存檔**不做 fans 尺度 migration**；改為重新校準 `reqFans` 與 `fanGain` |
| 3 | **v1 不做 Sponsor 價碼倍率** | 原 F3 延後為 **Fan v1.1**；v1 粉絲只影響 **Sponsor 解鎖資格** |
| 4 | **fanGain 保留來源權重**（Practice < League < Major），但依 128k 尺度重新校準體感 | 給的是 calibration target，不是硬寫死的公式 |
| 5 | **`reputation` 不立即物理刪除** | 改為 product semantics deprecated；舊 save 欄位暫留，未來 schema cleanup 再刪 |
| 6 | **Home 不新增第四張 Club Status 粉絲卡** | 沿用既有支持者顯示，只加「本週變化」；維持 Home IA 去重成果 |
| 7 | **`mode.audience` 假數字直接移除**，不改接 `meta.fans` | Fans 與 Audience 語意不同，沒有 attendance system 就不冒充 |
| 8 | **不建立 Fan Center** | 只用 Home / Sponsor / Match Result / Season Recap / Team Overview |
| 9 | **v1 粉絲不下降**，不做每日 decay | 壓力來自合約到期的機會成本 |
| 10 | **Product redline 持續** | fans 永遠不得影響 player stats / match strength / win probability / battle engine |
| 11 | **Sprint 重新定義**（見 §八） | F0 → F1 → F5 基礎 → F2 → F4 → playtest → 再決定 F3 |

### 保留 128k 尺度的理由（記錄，避免日後被「順手改小」）

- 比較符合職業電競俱樂部的品牌感——12.8 萬支持者是一支真的職業隊，1,280 不是。
- 可以完全避開對現有 `fans: 128_000` 舊存檔做大規模 migration。

**這一個決策同時關掉了原規劃裡風險最高的一項（舊存檔 migration）。**
代價是 `reqFans` 與 `fanGain` 兩張表都要重新校準——那是純數值工作，沒有 schema 風險。

## 一、Audit：現況（2026-08-23 於 `main @ 564986f` 實查）

### 1.1 最重要的一個事實

| 項目 | 值 |
|---|---|
| 贊助商粉絲門檻 `SPONSORS[].reqFans` | 0 / 500 / 800 / 1500 / 2000 / 3000 |
| `profileStore` 預設 `meta.fans` | **128,000** |

> **粉絲門檻從開局第一秒就全部達標。**
> 「粉絲 → 解鎖更好的贊助」這條唯一的粉絲玩法，目前在 repo 裡是**死的**——
> 不是還沒做，是做了但被種子值蓋掉。真正在擋人的只有 `reqWins`（0/3/5/10/15/20 勝）。

**裁決 2 之後，修法不是把 fans 改小，而是把 `reqFans` 改大到同一個數量級。**

### 1.7 追加發現：`perk` 是純文案（本輪新查）

`SPONSORS[].perk` 寫著「訓練效果 +15%」「選手體力恢復 +10%」「選手士氣 +5」，
但全 repo 只有兩處讀它，**都是把字串印在畫面上**：

- `src/screens/manage/SponsorScreen.jsx:56`（目前贊助的「特殊加成」）
- `src/screens/manage/SponsorScreen.jsx:100`（簽約前的比較表）

**沒有任何邏輯讀 `perk`。** 兩個推論：

1. **對紅線是好消息**——不存在「fans → 解鎖贊助 → perk → 選手數值」這條間接路徑，
   紅線 10 在目前程式碼上是乾淨的，`check_fan_system` 的斷言可以直接寫死。
2. **對玩家是誠信問題**——粉絲一旦真的開始擋贊助，玩家會為了「訓練效果 +15%」去追一個
   **什麼都不會發生**的加成。這在 v1 之前不痛（因為所有贊助都已解鎖、沒人在追），
   **F1 之後會變成可見的謊**。列為技術債 TD-24，不在本案範圍內解，但 F4 UI 整合時要一併決定
   是「移除 perk 文案」還是「補上實作」。

### 1.8 追加發現：開局現金流對 `reqFans` 校準的硬約束（本輪新查）

`platform/economy/sponsors.js:23-29` 記著新手情境的算式：

```
支出 = 薪資 12.2 + 營運 5.5 = 17.7 萬／週
扶持期間（8 週）：戰績 50% 時淨額 ≈ −1.2 萬／週
扶持到期後：回到 −11.7 萬／週
```

也就是說 **玩家必須在 8 週內談到一份 `weekly` 夠大的正式贊助**，否則進入死亡螺旋。
市集裡 `weekly` 最低的兩檔是 `local`（6 萬）與 `redbull`（12 萬）。

> **硬約束（F1 必須遵守，不得「順手調高」）：**
> **`reqFans` 的第二階必須 ≤ 開局粉絲數（128,000）。**
> 若把 `redbull` 的門檻訂在 128k 以上，開局玩家只能簽 `local`（6 萬／週），
> 扶持到期後直接負向失控——那不是難度，是設計失誤。

下方 §4.1 的初始基準（第二階 = 100k）**已經滿足這條約束**，開局即可簽 `local` 與 `redbull`。

## 二、Grilling：對這個需求的質疑（規劃期記錄，已被裁決收斂）

以下每一題都先站在反對面。裁決後的結果已寫入 §四。

### Q1 粉絲系統到底增加什麼玩法？

如果粉絲只餵贊助門檻，而門檻已經全部達標——增加的玩法是**零**。現在就是這個狀態。

> **裁決**：粉絲要有玩法，必須至少有一件「玩家想要、但粉絲不夠就拿不到」的東西。
> repo 裡唯一夠格的候選是**贊助合約**。**v1 就只做這一件**（裁決 3）。

### Q2 與 Reputation / Sponsor / Finance 重複嗎？

**與 Reputation 直接重複。** `meta.reputation` 就是一個「戰隊聲望純量」，種子 47、從不變動、畫面顯示「—」。

與 Sponsor / Finance 不重複：粉絲是**資格**，錢是**結果**，是因果不是並列。

> **裁決 5**：不物理刪除，改為 deprecated 語意——不做大 migration / refactor，
> 但語意上收斂成單一概念。

### Q3 玩家為什麼會在意粉絲增加？

不會，除非它擋住某個門。經營遊戲裡玩家在意一個數字通常只有兩個理由：它**解鎖**東西，或它**會掉**。

> **裁決**：選「解鎖」，不選「會掉」（裁決 9）。

### Q4 如果粉絲只是數字，會不會沒意義？

會，而且這正是目前的狀況。**首頁已經在顯示「12.8萬 支持者」，而那個數字完全沒有後果。**

> **裁決**：v1 的第一優先**不是**增加粉絲來源，是讓現有的粉絲數有後果。

### Q5 會不會形成雪球？

會，而且現有公式**刻意在助長**：`streak × 25`。

但**裁決 3 把最強的一段雪球拆掉了**——v1 粉絲不影響贊助價碼，只影響資格。
資格是階梯而且有頂，所以 v1 的正回饋天生就撞得到天花板。

> **裁決**：v1 的天花板是「贊助分級是階梯 ＋ 合約會到期 ＋ 粉絲不碰數值」。
> 價碼倍率（真正會讓雪球連續放大的那一段）延後到 v1.1，等經濟參數校準完再談。

### Q6 Practice 與正式 Season 應該給一樣多嗎？

**現在給的一模一樣**——練習賽與聯賽賽程走同一支公式、同一個係數。
造成兩個問題：刷練習賽是最有效率的漲粉手段，而正式比賽**不特別**。

> **裁決 4**：必須分開，差距要明顯。**這是本案最有產品價值的單一改動**。

### Q7 MOBA 與 CS 應該共用戰隊粉絲嗎？

**共用。** 理由不是省事，是**贊助只有一份**——拆成兩池粉絲就必須拆成兩池贊助。
而且 `teamRewardsFor()` 本來就是共用的，這條不用做任何事。

### Q8 現在要做 Player 個人人氣嗎？

**不要。沒有任何消費端。** 個人人氣要有意義，必須有轉會市場議價、個人贊助、
或粉絲對特定選手的忠誠度——這三個現在都不存在。

### Q9 粉絲下降真的有必要嗎？

**反對做衰減。** 每日衰減會變成**雜務壓力**：玩家為了不掉數字而定期上線做無聊的事。

解法不是讓粉絲掉，是**讓合約會到期**——停滯的隊伍不會掉粉，但下一份合約談不到更好的條件。
**壓力來自機會成本，不是懲罰。**

> **裁決 9**：v1 不做粉絲衰減。

## 三、方案演進（記錄，說明 v1 為什麼長這樣）

規劃期提了三個方案，並推薦 B（粉絲同時決定「能簽誰」與「值多少」）。

**產品裁決把 B 切成兩段：**

| | 內容 | 落在 |
|---|---|---|
| B 的前半 | 粉絲決定**能簽誰**（eligibility） | **Fan v1** |
| B 的後半 | 粉絲決定**值多少**（`weekly` 價碼倍率） | **Fan v1.1**（裁決 3） |
| C | 品牌等級 ＋ 期待值 | 更後面，等經濟參數穩定 |

**切開的理由**：`economyConfig` 尚未完整校準（自帶「待轉會與合約系統完成後再校正」註記）。
把粉絲與現金流平衡同時綁死，會變成兩個都調不準。
**先讓粉絲擋門，看玩家有沒有感覺；有感覺再談價碼。**

C 的品牌等級之後可以直接長在 v1 上，不會白做。

## 四、Fan System v1 設計（依最終裁決）

原則：**不新增 Store、不新增金錢入口、不碰數值、不做 migration。**

| # | 問題 | 答案 |
|---|---|---|
| 1 | Canonical ownership | `meta.fans`（已經是）。寫入者只有兩個且都已有冪等帳本：`applyMatchProgress`（單場）與 `settleCompetitionAward`（賽季名次）。**不新增第三個** |
| 2 | fans 存哪裡 | 就存 `meta.fans`，不開新 Store／新切片。「本週變化」**用推導**（讀既有 `finance.transactions` / 收據帳本），不新增第二份 log。賽季成長需要起點 → 賽季建立時記一個 `fansAtSeasonStart` 快照（單一數字） |
| 3 | MatchResult 如何影響 | 沿用 `teamRewardsFor()`，**只多乘一個來源權重**。權重由 `origin.kind` 與賽事 tier 決定，不由畫面決定 |
| 4 | Practice vs Season | 順序不變式 **Practice < League < Major**；絕對值見 §4.2 calibration target |
| 5 | MOBA vs CS 同公式 | **是，而且不用做任何事**——`teamRewardsFor()` 本來就共用，項目差異已由各自 adapter 的 `marginF` 表達 |
| 6 | Sponsor 如何讀 fans | 維持 `signSponsor(id, ctx)` 由呼叫端傳入真值（不在 Store 內重算）。**v1 只做 eligibility，不做價碼倍率**（裁決 3） |
| 7 | Finance 是否受影響 | **只透過「簽到更好的贊助」這個間接結果**。不新增 fans→money 直接路徑，金錢入口維持既有三個，`forecast` 不外推粉絲 |
| 8 | Home 呈現 | **不新增第四張卡**（裁決 6）。沿用既有支持者顯示，只加本週變化：`12.8萬 支持者　+1,240 本週` |
| 9 | Season Recap | 加一列「本季粉絲成長 +N」，用 `fansAtSeasonStart` 相減 |
| 10 | Save / migration | **不做 fans 尺度 migration**（裁決 2）。只加 **sanitize**（`fans` 必須是有限非負整數）——現在完全沒有 |
| 11 | 不重複結算 | 不發明新機制：單場走 `processedMatchTransactions[transactionId]`，賽季走 `processedCompetitionAwards[finalStandingsId]`，兩個帳本都已存在且已被 verifier 守著 |
| 12 | 新 verifier | 要，一支 `check_fan_system.mjs`。**基礎 contract 斷言從 F1 同步開始**（裁決 11），不等到最後 |

### 4.1 `reqFans` 重新校準（**待校準區間，非最終 balance**）

裁決 2 保留 128k 尺度 ⇒ `reqFans` 必須跟著放大到同一個數量級。

**初始研究基準**（供 F1 起步，**不是最終值**）：

| 贊助商 | tier | `weekly`（萬） | 現行 `reqFans` | **初始研究基準** | 開局（128k）狀態 |
|---|---|---|---|---|---|
| `local` 在地網咖 | 入門 | 6 | 0 | **0** | ✅ 已解鎖 |
| `redbull` 紅牛運動 | 中級 | 12 | 500 | **100k** | ✅ 已解鎖 |
| `hyperx` HyperX 外設 | 中級 | 15 | 800 | **180k** | 🔒 差 52k |
| `vortex` Vortex 電競椅 | 頂級 | 20 | 1,500 | **300k** | 🔒 |
| `mamimoth` MAMIMOTH 能量飲 | 頂級 | 25 | 2,000 | **500k** | 🔒 |
| `crypto` 加密貨幣交易所 | 頂級 | 35 | 3,000 | **800k** | 🔒 |

> ⚠ `reqWins`（0/3/5/10/15/20）**本案不動**。它是另一道獨立閘門，繼續共同決定資格。
> ⚠ `SPONSORS` 陣列順序**不是**依 `reqFans` 排序（實際順序是
> mamimoth / vortex / hyperx / redbull / local / crypto）。任何依賴陣列順序的實作都是錯的，
> 要依 `reqFans` 自己排。

**初步合理性檢查**（算術，不是決策）：
開局 128k → 下一階 180k 需要 **+52k**。以聯賽勝場 ~1,200、一季 56 場、勝率 60% 估算，
單季比賽貢獻約 40k，加上賽季名次數千 ⇒ **約 1～1.5 個賽季解鎖一階**。節奏合理。

**但最頂階 800k 需要 +672k ⇒ 約 8–15 個賽季。**
這是整條階梯風險最高的一端（見風險 R7），F1 要特別看它，
可能需要把上緣壓低或讓後段賽季獎勵更陡。

### 4.2 `fanGain` 重新校準（**calibration target，不是硬寫死的公式**）

| 來源 | 目標體感 |
|---|---|
| 練習 / 自由對戰 | **數百** |
| 正式聯賽勝場 | **約 800–1,500** |
| Major / 大型賽 | **約 1,500–2,500** |
| Season placement | **數千** |
| Champion | **萬級明顯跳升** |

**與現行公式的落差**（供 F1 起步）：現行勝場是 `120 + margin×140 + streak×25` ⇒ 約 120–400。

- 練習 ≈ **維持現行量級**（數百）
- 聯賽 ≈ 現行的 **3–5 倍**
- Major ≈ 現行的 **5–8 倍**

順序不變式 **Practice < League < Major** 由 verifier 守；
**絕對數字由 F1 實測校準，不寫進 verifier**（否則每次調數值就要改 gate）。

### 4.3 粉絲如何增加 / 是否減少

**增加**
- 單場勝負（既有公式 × 來源權重）
- 連勝加成（既有 `streak × 25`，隨整體尺度一起校準）
- 賽季名次結算（新增，走既有 `settleCompetitionAward` 冪等路徑）
- Champion / Major 奪冠（一次性、萬級）

**減少**
- **v1 不做任何粉絲減少**（裁決 9）。壓力來自贊助合約會到期。

### 4.4 `reputation` 的處置（裁決 5，deprecated 而非刪除）

| 要做 | 不要做 |
|---|---|
| 標記為 product semantics **deprecated** | ❌ 物理刪除欄位 |
| 新功能**不得使用** | ❌ 為它做 schema migration |
| UI **不再顯示** | ❌ 為它做大 refactor |
| 新 settlement **不得寫入** | |
| 舊 save 相容欄位**暫留** | |
| 未來 schema cleanup 再物理刪除 | |

理由：物理刪除要動 save schema，而**本案的核心價值不在那裡**。
語意上收斂成單一概念，就足以避免「兩個聲望純量並存」的長期困惑。

### 4.5 verifier 要守的七條（`check_fan_system.mjs`）

1. `meta.fans` 只有兩個寫入點，且都經過冪等帳本
2. 粉絲**不進入** `configurePlayers` / `configureMatch` / 任何 stats 路徑（紅線 10）
3. 練習賽權重 **<** 聯賽權重 **<** Major 權重（**順序**，不是寫死的絕對數字）
4. 同一場比賽重複結算不會重複加粉絲
5. 畫面只讀不算——Sponsor 的資格判定由 Store 出口提供
6. 壞存檔的 `fans` 會被 sanitize 成合法值
7. **`reqFans` 第二階 ≤ 開局粉絲數**（§1.8 的硬約束，防止開局死亡螺旋）

> 裁決 11：第 1、2、4、6 條是 **contract 斷言**，從 **F1 同步開始**，不等 F5。
> 第 3、5、7 條可以在對應功能落地後再補。

## 十、GO / NO-GO

**✅ GO（2026-08-23 產品核准）。**

定位是**接通既有設計**，不是新增系統。

理由：repo 裡已經有粉絲數、有公式、有門檻、有共用發放點與冪等帳本。缺的只有
**把門檻校準到正確的數量級**、**來源權重**、**一條賽季來源**。
以這麼低的成本換到「贊助有追求、正式賽季比練習賽更有份量」，投報率很高。

裁決 2（保留 128k）與裁決 3（價碼倍率延後）各關掉了原規劃裡風險最高的一項：
**存檔 migration** 與 **現金流平衡耦合**。剩下的是純數值校準工作。
