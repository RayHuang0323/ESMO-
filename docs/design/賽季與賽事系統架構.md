# 賽季與賽事系統架構（Competition / Ranking / Shop）

> 規劃日期：2026-08-10
> 狀態：**規格已定案，未實作**。本文件是後續 Milestone 的唯一依據。
> 範圍：Competition Domain、Ranking、Shop Domain 的長期架構，以及 MOBA 常規賽 MVP。
> 本輪未寫任何程式、未 commit、未 push。

---

## 一、這份文件在回答什麼

ESMO 目前有完整的「一場比賽」管線，但沒有任何「賽季」結構。本文件定義三件事：

1. 賽事（聯賽／季後賽／國際賽／Major）如何長在既有管線之上，而不是旁邊。
2. 牌位／MMR／積分的資料形狀，以及它與賽事的關係。
3. 商店與經濟系統的責任邊界，特別是「付費不能變強」如何成為機器擋得住的規則。

**真實 LoL / CS 賽事僅作結構研究。** 不使用任何商標、隊名、選手名、賽事名或官方資料。

## 二、Audit：現有 vs 真的缺（2026-08-10 實查）

### 已經有、絕不重做

| 領域 | 現況 | 位置 |
|---|---|---|
| 時間軸 | `meta.days` 唯一計數，`deriveTime(days)` 導出 week/season，7 天/週、12 週/賽季（84 天）。`advanceDay()` 唯一時鐘 | `platform/economy/timeline.js` |
| 七層比賽契約 | Lineup → Squad → EntryRequest → Ticket/Assignment → Room → Session → Result。決定性冪等、只送身分不送數值、gateway 簽發、seed 單一權威鏈 | `platform/contracts/*` |
| 配對閘道 | 純函式 mock，接真伺服器只換這一支 | `matchmaking/mockGateway.js` |
| 發獎 | `applyMatchProgress` 是唯一單場發獎點；`settleMatchResult` 綁場次防重送 | `platform/progress/` |
| 經濟 | 費率單一來源、薪資由能力推導、贊助拆固定＋績效、四週現金預測、交易帳本冪等 | `platform/economy/` |
| 賽績 | `formLog` 已統一 MOBA + CS | `economy/formLog.js` |
| 多遊戲骨架 | `MATCH_FLOWS` 資料驅動，`GAME_TYPE.GAME3` 佔位已存在 | `router/matchFlows.js` |
| 選手模型 | 16 項能力、個性、士氣、位置適配、訓練課程 | `data/playerModel.js` |

### 真的是零

- **牌位 / MMR / 排名分**：全專案沒有任何一行。`meta.reputation` 永遠 0。
- **聯賽 / 賽程 / 季後賽 / 國際賽**：主幹零。
- **AI 對手隊伍實體**：紅方永遠中性能力，無 roster。
- **商店**：主幹零。
- **Competition / Tournament / Stage 契約**：零。

### 三個必須知道的陷阱

1. **`seasonStore` 不是賽季系統**，是戰績紀錄簿：只有 `history[]`（上限 50 場）與 blue/red 兩隊的推導統計，`resultKey` 是「勝方\|時長\|比分」四欄位。賽事系統**不得**往它身上長。
2. **Legacy `BracketModule` 是純假資料 UI**：積分榜用 `AI_TEAMS[].power / 160` 現算勝場，沒有真實賽程。可參考版面，不可參考資料流。
3. **Legacy `EquipModule` 含真實品牌名**（Razer / Logitech / Wooting…）。移植時必須全部換成自有品牌。

## 三、定位與四條紅線

```
Battle Engine    一場比賽怎麼打完                     ← 既有，賽事系統零修改
Match Pipeline   一場比賽怎麼開始與結算（七層契約）     ← 既有，僅擴充 origin
Competition      哪些比賽會發生、打完名次怎麼變         ← 新建
Ranking          隊伍在賽季中的位置                    ← 新建
Economy          錢怎麼進出                           ← 既有，新增賽事名次獎金入口
Shop             買什麼、擁有什麼、產生什麼效果         ← 新建（第二階段）
```

1. **Competition 不產生比賽結果。** 它只產生 Fixture、消費結果。
2. **Shop 不直接進 Battle Engine。** Effect 只能落在既有注入口（`configurePlayers` / `configureMatch`）或既有經營系統。
3. **錢的入口有三個，每個都有決定性冪等鍵**：`applyMatchProgress`（單場賽後）、`weeklySettlement`（週結）、`settleCompetitionAward`（賽事名次）。不得有第四個。
4. **不建第二套**選手／隊伍／時間資料。`meta.days` 仍是唯一時鐘，`players[]` 仍是唯一「被經營的選手」來源。

## 四、已定案決策（12 項）

| # | 決策 | 理由 |
|---|---|---|
| D1 | **兩條 ladder 並存、分開計分**：`career`（AI 聯賽生涯線）／`competitive`（線上競技線），互不換算 | 單機生涯與線上競技的平衡目標不同，合併會互相綁架 |
| D2 | **`RankingKey = (subjectType, subjectId, gameMode, ladderId)`**。MVP 值恆為 `("team", teamId, "moba", "career")` | `subjectType` 是 PlayerRanking 的擴充點——日後加 `"player"` 不改任何既有列 |
| D3 | **行事曆驅動**：賽季開始排定賽程，到日必須出賽或棄權判負。自由對戰另走排隊，不佔賽程 | 疲勞、傷停、輪替、資金壓力才有意義；與 O2 疲勞系統天然契合 |
| D4 | **Competition 採 Stage Graph 抽象**：賽事＝Stage 有向圖，邊是 Qualification | 共用的是賽制與晉級機制，不是「聯賽 vs Major」這種產品概念 |
| D5 | **AI vs AI 用決定性快速模擬**，不跑引擎 | 8 隊雙循環 56 場 × 20–30 分不可行 |
| D6 | **新增不可變 `team.id`**，`tag` / `name` 純顯示 | 現況拿 `team.tag`（"GSEAL"）當識別碼，改隊名會斷開所有歷史紀錄 |
| D7 | **`MatchOrigin.v1` 抽象 assignment 來源**，ticket 與 fixture 都合法。不造假 ticket、不建第二條進場流程 | 見 §6 |
| D8 | **新增 `settleCompetitionAward()`**，`cat: "prize"`（單場）與 `cat: "award"`（賽事名次）分開；`forecast` 不外推 award | 冠軍獎金不屬於任何一場比賽；一筆大額 award 會讓四週現金預測嚴重高估 |
| D9 | **AI 選手共用 `playerModel.js`，但存在 competition domain 的唯讀 roster**，不進 `profileStore.players[]` | `players[]` 的定義是「會被經營系統寫入的人」。AI 選手 MVP 唯讀，不符合。真正轉入玩家隊伍時才走既有 `signProspect` 建立可經營 instance |
| D10 | **雙貨幣**：`funds`（營運資金，只由比賽獎金／贊助／週結產生）／`tokens`（課金與活動）。**`tokens → funds` 永久禁止** | 若只有一種貨幣，課金＝買遊戲內資金＝繞過整個 Effect 層的 P2W |
| D11 | **賽果一經寫入即不可變**（儲存派）。`simulatorVersion` 是稽核欄位，不用於重算 | 模擬器升版不得讓三年前的冠軍換人 |
| D12 | **席位只做淺層參數化**（`SEATS_BY_MODE`），不做通用 roster engine | 沒有第三款遊戲的規格，硬抽會做出沒需求支撐的通用系統 |
| D13 | **聯賽固定 8 隊 = 玩家 + 7 支 AI**，雙循環 56 場。玩家打 14 場，AI 之間 42 場 | 賽程產生器需要確定的參賽數；Legacy `AI_TEAMS` 有 8 支，取 7 支或新設計皆可 |
| D14 | **新增不可變 `meta.seasonSeed`**，開新局時由 `startNewGame` 決定性產生；跨賽季以 `hash(seasonSeed + seasonNumber)` 派生 | 規格原本只說「seed 由賽季 seed 推導」卻沒定義它從哪來。若用 `Date.now()`，O 系列一路守住的決定性鏈當場斷掉 |
| D15 | **`advanceDay()` 遇玩家賽事日停止推進**，回傳擴充為 `{ daysAdvanced, stoppedBy }` | 見 §9「唯一時鐘的契約變更」。這是全案唯一會修改既有 verifier 斷言的地方 |
| D16 | **MVP 模擬器用 `teamStrength(roster)`** 把 16 項能力壓成單一實力值，再以 seed 產生賽果。與 LogicEngine 的勝率校準延後 | 讓 D9（共用 playerModel）真的成立，同時避免 MVP 就背上「模擬要像引擎」這種測不出來的判準 |
| D17 | **MVP 只做 debug 賽季快進**（沿用 `devFastForward` / TD-16 的路子，走完整結算路徑）。正式「模擬出賽」列第二階段第一優先 | 「代打成績算不算數」會牽動 Standings、獎金、贊助績效與線上競技線，不該在 MVP 匆促決定 |
| D18 | **Q1 驗收判準精確化為三條可執行判準**（見 §10） | 全套 `verify.mjs` 現況 16/18（TD-19／TD-21 既有紅燈），判準若寫「全綠」在數學上不可能達成 |

## 五、Competition Domain 資料模型

### 六個實體

| 實體 | 職責 | 關鍵欄位 |
|---|---|---|
| `Competition` | 一個賽事 | `id, gameMode, seasonId, organizerId, tier, prizeTable, stageIds[]` |
| `Stage` | 賽事內一個階段 | `id, competitionId, format, participants[], standingsRule, dayRange` |
| `Fixture` | 一場預定的對戰 | `id, stageId, round, day, sideA, sideB, matchFormat, status` |
| `Standing` | Stage 內的排名列（**推導，不儲存**） | `stageId, teamId, w, l, pts, tiebreakers[]` |
| `Qualification` | 晉級邊（MVP 零條） | `fromStageId, rule, toStageId \| toCompetitionId, slots` |
| `Circuit` | 跨賽事積分軌（第二階段） | `id, gameMode, seasonId, pointsTable, standings[]` |

`Stage.format` 四種：`round_robin` / `swiss` / `single_elim` / `double_elim`。**MVP 只實作 `round_robin`。**

### 項目差異收在哪裡

`competition/formats/moba.js` 與 `formats/cs.js` 持有 BO 制、換邊規則、Ban/Pick 順序、map veto、加時規則。**共用層不認得這些欄位**，只把它們原樣掛到 Fixture 上，傳給對應的賽前流程。

第三款遊戲若仍是 team-vs-team lineup 型態，接入成本＝一份 format 檔。**若不是（1v1 / BR / 非固定人數），仍需擴充 Contract——不宣稱零成本。**

### `FixtureOutcome.v1`

```js
{
  fixtureId, gameMode, seed, simulatorVersion, resultSource,
  winner, score, duration, highlights[]
}
```

- `resultSource: "engine"` — 玩家實打，另有完整 `BattleResult.v2`
- `resultSource: "simulated"` — AI vs AI，**刻意不產生 `BattleResult.v2`**

不產生 BattleResult 的理由：它有 10 人逐項 KDA／金錢／傷害，快速模擬編不出來，編了就是假資料。本專案已有「誠實佔位不編造」的先例（CS 補兵數顯示「—」、`reputation` 永遠 0）。

`simulateFixture(fixture, teams, seed)` 是純函式，seed 由 `fixtureId` 雜湊推導。無 `Math.random()`、無 `Date.now()`，與 O 系列契約同一手法。

這個形狀讓「玩家選擇模擬出賽（跳過實打）」成為天然可支援的功能，MVP 不做但不會擋住。

### 兩類 Analytics（重要）

| 類別 | 吃什麼 | 內容 |
|---|---|---|
| **Competition Analytics** | engine + simulated **一視同仁** | 勝敗、Standings、Qualification、Circuit Points、獎金、賽季歷史、升降級 |
| **Combat / Balance Analytics** | **只吃 engine** | KDA、場均擊殺、龍／巴龍、時長分布、引擎平衡校準、verifier 取樣 |

**AI 模擬結果是正式賽果**，該進聯賽的全部都進。被擋掉的只有「拿來反推引擎平衡」的那一類。

⚠ **現有問題**：`seasonData.js` 把兩類混在一起——`standings()` 是 Competition Analytics，`analytics()`（場均擊殺／龍／巴龍）是 Combat Analytics，同一支檔、同一份 `history`。接 Competition 時必須先拆開。

## 六、`MatchOrigin.v1`：Fixture 如何接上既有七層管線

### 問題

`createAssignment({ ticket, opponent, seed })` 簽名硬綁 ticket；`assignmentId = hash8(ticket.ticketId + seed)`；O5 `canEnterRoom` 要求 `room.ticketId === ticket.ticketId`。**賽事路徑沒有票券。**

### 解法：換名 + 放寬，不是語意變更

```js
MatchOrigin.v1 = { kind, originId, entryRequestId, rosterVersion, mode }

票券來源：{ kind: "ticket",  originId: ticket.ticketId,   ... }
賽事來源：{ kind: "fixture", originId: fixture.fixtureId, competitionId, stageId }
```

所有現在讀 `ticket.ticketId` 的地方改讀 `origin.originId`。**因為票券路徑的 `originId === ticketId`，現有 verifier 對票券路徑的每一條斷言都仍然字面成立**——不需要重新校準，只需要為 fixture 路徑加新斷言。

`MatchEntryRequest`（O3）兩條路徑都要——賽事出賽一樣要提交陣容、一樣要 `rosterVersion` ⇒ **O3 零改動**。

### 實測改動範圍

`ticketId` 全專案 23 處、7 個檔：

| 檔案 | 耦合點 |
|---|---|
| `contracts/matchmaking.js` | 7（ticketId 推導、assignmentId 推導、複製、mode、`ticket_mismatch`、`mode_mismatch`、`canEnterMatch`） |
| `contracts/matchRoom.js` | 4（guard、複製、mismatch、assignment 讀取） |
| `contracts/matchSession.js` | 6（guard、mismatch ×3、複製、rosterVersion） |
| `matchmaking/mockGateway.js`、`profileStore.js`、`progress/settleMatchResult.js`、`screens/common/MatchQueuePanel.jsx` | 各 1–2 |

需加新斷言的 verifier 六支：`check_matchmaking_o4`、`check_match_room_o5`、`check_match_session_o6`、`check_authoritative_o7`、`check_result_flow_o71`、`check_match_entry_o3`。

**約等於一個 Milestone O 級別的工作量。**

### 兩條路徑

```
排隊：EntryRequest → Ticket(狀態機) → mockGateway         → Assignment(origin: ticket)
賽事：EntryRequest →                  competitionGateway  → Assignment(origin: fixture)
                                                              ↓ 以下完全共用
                                            Room → Session → Launch → MatchResult
```

`origin` 只有 id 與模式，**沒有任何數值** ⇒ 不違反 `validateAssignment` 現有的「拒絕對手戰力數值」斷言。

## 七、Ranking

```js
RankingKey = { subjectType: "team", subjectId: teamId, gameMode, ladderId }
ladderId ∈ { "career", "competitive" }
```

三種計分機制共存於同一張表：

| 機制 | ladder | 形狀 | 階段 |
|---|---|---|---|
| League Standing | career | 勝敗、積分、賽季末升降級 | MVP（僅 Standings，無 ladder 表） |
| Circuit Points | career | 名次 → 積分累加 → Major 配額 | 第二階段 |
| MMR → 牌位 | competitive | Elo，映射 tier / division / LP | 第二階段 |

### Standings：進行中推導、結算後凍結

- **賽季進行中**：Standings 是對 `FixtureOutcome[]` 的**純推導**。儲存它等於製造第二份真相，與 outcomes 不一致時沒人說得出聽誰的。
- **賽季結束**：snapshot 一次成不可變的 `FinalStandings`。

理由：升降級、名次獎金、歷史紀錄需要「當時判定的結果」，而 tiebreaker 規則日後可能修正——修正 tiebreaker 不該讓三年前的冠軍換人。與 D11 邏輯一致。

## 八、Shop Domain（設計凍結，第二階段實作）

### 五層分離

```
Product      商品定義：id, kind, price, currency, scope, effects[]
Shop         上架與陳列：分頁、限時、Battle Pass 進度
Purchase     交易單：決定性冪等鍵，走既有 transaction ledger
Entitlement  擁有權：帳號級，永久（造型、通行證、解鎖）
Inventory    可消耗品：次數、有效期
Effect       效果宣告：純資料，不是程式
```

### 商品類型（規劃範圍，不預先限縮）

選手／英雄造型、CS 武器造型、戰隊制服／Logo／基地／場館外觀、表情／特效／勝利動畫、訓練／教練／球探／恢復／設施等經營型商品、額外戰術與陣容配置選項、選手成長與能力培養商品、Battle Pass／Season Pass／限定活動商品。

### Effect：只宣告作用點，不含實作

```js
{ target: "training.efficiency",   op: "mul", value: 1.15, scope: ["career"] }
{ target: "recovery.energyPerDay", op: "add", value: 2,    scope: ["career"] }
{ target: "cosmetic.heroSkin",     value: "chichuan_v2",   scope: ["career","competitive"] }
{ target: "tactic.unlock",         value: "m9_split_push", scope: ["career","competitive"] }
```

接線表（**沒有任何一條直接進 Battle Engine**）：

| Effect target | 落在 |
|---|---|
| `training.*` | `applyCourse` |
| `recovery.*` | `applyDailyRecovery` |
| `growth.*` | `applyMatchProgress` |
| `tactic.unlock` | `MobaTacticConfig` 的可選卡片集合 |
| `cosmetic.*` | 呈現層讀 Entitlement |
| career 能力型商品 | 改 `players[].stats` / 上限，最終仍走既有 `configurePlayers` |

### `CompetitivePolicy`：可驗證、可演進的 P2W 防線

**不是永久不可變的產品政策，是有版本的 policy 物件。**

```js
CompetitivePolicy.v1 = {
  policyId: "mvp-no-direct-power",
  version: 1,
  allowedTargets: ["cosmetic.*", "tactic.unlock", "roster.slot", ...],
  forbiddenOps: { on: ["stats.*", "growth.*", "power.*"], ops: ["mul", "add"] },
  rationale: "MVP 期間真人競技不販售直接數值增益",
}
```

> **不變式**：任何 `scope` 含 `"competitive"` 的 Effect，必須通過當前生效的 policy。

verifier 驗的是「Effect 是否符合當前 policy」，不是「是否在某張固定表裡」。換商業模式＝換一份 policy 並記錄理由，斷言自動跟著改，不需要動 Shop 程式、也不需要拆掉防線。`Product` 上記錄 `validatedAgainstPolicy: "mvp-no-direct-power@1"`，policy 改版時能查出哪些既售商品要重審。

**設計原則**：AI 生涯／單機經營可以有明顯的成長與能力型商品；真人 Ranked / Competitive PvP 不得以「付費＝更高數值」形成直接 P2W，付費戰術或能力相關內容應做成橫向選擇、解鎖速度或 Build 多樣性。

### 貨幣紅線

- `funds`：只由比賽獎金、贊助、週結算產生。經營型商品用它買。
- `tokens`：課金或活動獲得。只能買 Entitlement 型商品。
- **`tokens → funds` 禁止任何路徑。**
- `Product.currency` 必填，且與 `Product.kind` 的對應由 policy / verifier 管控。

## 九、MVP 定義與流程

### MVP 驗收標準（一句話）

> 玩家能完成一個 MOBA 常規賽賽季：8 隊賽程 → AI 背景賽快速模擬 → 玩家比賽日使用既有 Battle Pipeline 親自出賽 → Standings → 最終名次 → 名次獎金。

### 賽季生命週期

```
賽季開始（day 1）
  └→ 建立 Competition（MOBA 常規賽）
     └→ 建立 Stage（round_robin，8 隊雙循環 = 56 場）
        參賽者 = 玩家 1 隊 + AI 7 隊
        └→ 賽程產生器排定 56 場 Fixture 到 84 天內
           seed = hash(meta.seasonSeed + seasonNumber)
           ⇒ 同一賽季重排逐場相同，主客場對稱

每天 advanceDay(1)
  ├→ 當日有玩家的 Fixture → 停止推進並提示出賽
  ├→ 當日 AI vs AI 的 Fixture → simulateFixture() → FixtureOutcome
  └→ 逾期未完成的 Fixture → forfeited

賽季結束（day 84）
  ├→ FinalStandings snapshot（不可變）
  └→ settleCompetitionAward()：依最終名次發獎金（cat: "award"）
```

玩家一季實打 14 場、AI 之間 42 場由模擬器產生。

### 唯一時鐘的契約變更（D15）

`advanceDay(n)` 是既有的唯一時鐘（訓練結算、週結算、疲勞恢復全掛在上面）。行事曆驅動接上去後會出現既有系統沒有的情境：**玩家按「推進 7 天」，中間第 3 天有他的比賽。**

處置：**在比賽日前停下**。`advanceDay(7)` 實際只推 2 天，回傳擴充為 `{ daysAdvanced, stoppedBy }`，`stoppedBy` 帶可顯示的中文原因（「第 N 天有聯賽比賽」）。既有呼叫端只讀陣列部分的不受影響——沿用 Milestone P1 在回傳陣列上掛 `.trained` 的同一手法。

否決的兩個替代方案：照推並自動判棄權（玩家會因手滑丟掉整季）、由 UI 層擋（就是「畫面自己判規則」，本專案已明令禁止）。

⚠ **這是全案唯一會修改既有 verifier 斷言的地方**（`check_finance_n` 系列有斷言在測 `advanceDay`）。必須在 Q3 的報告裡單獨明講，不得與其他改動混在一起。

### 模擬器的能力模型（D16）

```
teamStrength(roster) → 單一實力值 → 配合 seed → FixtureOutcome
```

`teamStrength` 是把 16 項能力壓成一個數的純函式。這讓 D9（AI 選手共用 `playerModel.js`）真的成立——16 項能力有被用到，不只是好看。

⚠ **誠實揭露且刻意如此**：MVP 的模擬勝率**不保證**與 LogicEngine 一致。校準需要用引擎跑一批玩家 vs AI 的真實對局回頭調 `teamStrength` 的權重與勝率曲線，那是獨立一輪的工作（見 R3），列第二階段。

### 賽季快進（D17）

MVP 只提供 debug 用的賽季快進，沿用 `devFastForward`（TD-16）的做法——**走完整結算路徑，不繞過任何結算**。用途是驗收「賽季能不能跑完」。

正式的「模擬出賽」（玩家主動讓某場由模擬器代打）**列第二階段第一優先**，不在 MVP。契約已支援（`resultSource: "simulated"` + `origin.kind: "fixture"`），缺的是產品決策：代打成績算不算 Standings、算不算獎金、算不算贊助績效。

### Fixture 狀態機

```
scheduled ──→ launched ──→ completed
        ↘                ↘
          forfeited ←──────
```

- `launched` **不可回到 `scheduled`**（堵死「快輸時中離規避敗場」）
- 玩家中離：`resumeSession` 期限內回來可續打（沿用 O6 既有的 `tokenUsed` 與 `connection` 正交設計，不新增機制）
- 超過賽程日結束仍未 `completed` ⇒ 自動 `forfeited` 判負
- **MVP 的棄權只有敗場**，不追加聲望／金錢／升降級懲罰

### 玩家出賽流程（複用既有管線）

```
賽程日 → 玩家按「出賽」
  → 既有 squadCheck / validateSquad（O1）
  → 既有 MatchEntryRequest（O3）
  → competitionGateway.issueFor(fixture, entryRequest)  ← 新增，唯一新東西
  → Assignment(origin: fixture)
  → 既有 Room → Session → Launch → GameView → BattleResult
  → 既有 settleMatchResult / applyMatchProgress
  → Fixture.status = completed，寫入 FixtureOutcome
```

## 十、開發順序

### MVP：五個 Milestone

| | 內容 | 可獨立驗收的判準 |
|---|---|---|
| **Q1** | `team.id` + `meta.seasonSeed`（皆不可變，含舊存檔 migration）+ `MatchOrigin.v1` | 見下方「Q1 的三條判準」 |
| **Q2a** | 7 支 AI 隊伍（唯讀 roster）+ `Competition`/`Stage`/`Fixture` 契約 + `round_robin` + 賽程產生器 | 賽季開局排出 56 場 fixture；同 seed 逐場相同；雙循環主客場對稱 |
| **Q2b** | `FixtureOutcome` + `teamStrength` + 決定性模擬 + Standings 推導 | 跑完整季 AI 賽果，重跑逐值相同；積分榜純推導、tiebreaker 決定性 |
| **Q3** | 接 `advanceDay`（含 D15 契約變更）+ `competitionGateway` + 玩家賽事出賽 + resume / forfeit | 玩家能在賽程日出賽並完賽；中離可恢復；逾期自動判負；`launched` 不可回退；`advanceDay` 遇比賽日停下 |
| **Q4** | `FinalStandings` + `settleCompetitionAward` + 賽季封存 | 賽季結束產生不可變最終名次；名次獎金入帳且冪等（重複結算不重複發錢） |

原本的 Q2 內部有一條硬相依（模擬器要跑必須先有 AI 能力資料；Standings 要驗證必須先有模擬賽果），是三段串行工作被綁成一包，故拆為 Q2a / Q2b。**拆分不是把 MVP 做大，是切到可驗收的粒度**——Q2a 交付時就能看到一張真的賽程表。

每個 Milestone 附一支 verifier，規模比照 N（32 條）／O（40 條）。

### Q1 的三條判準（D18）

全套 `verify.mjs` 現況是 **16/18**（`experience26 §17` = TD-19、`runtime29 §29` = TD-21，且 §17 會往上串紅到 talent27 / stats28 / runtime29）。因此 Q1 的判準**不得**寫成「全綠」，改為三條可執行判準：

1. `check_match_entry_o3`、`check_matchmaking_o4`、`check_match_room_o5`、`check_match_session_o6`、`check_authoritative_o7`、`check_result_flow_o71` **各自 exit 0**。
2. 這六支的**既有斷言一條都沒改**——`git diff` 對 `tools/check_match*.mjs` 只有新增行。
3. 同一份 `MatchEntryRequest` 走排隊路徑，改動前後產生的 `ticketId` / `assignmentId` / `roomId` / `sessionId` **逐字元相同**。

第 3 條才是真正在驗「逐值不變」；前兩條是防護網。基線見 §13。

## 十一、風險

| # | 風險 | 說明與處置 |
|---|---|---|
| R1 | **TD-21（順序公平性 20pp）會被聯賽放大** | 20pp 系統性偏差 × 一個賽季的場數，會讓積分榜失真。快速模擬不受影響（不跑引擎），玩家實打的場次會。**建議 TD-21 在第二階段之前解決**；MVP 期間至少在文件記錄此限制 |
| R2 | **Replay 容量（TD-19，2492 KB／場）** | Competition **不得**存 replay，只存 `FixtureOutcome` |
| R3 | **模擬與引擎的勝率分布不一致** | 玩家會發現「我打贏的隊在 AI 之間卻常輸」。需用引擎跑樣本校準模擬參數——**獨立一輪的校準工作，不可順手做** |
| R4 | **`FixtureOutcome` 容量未實測** | 估 ~200 bytes／場 ⇒ 56 場 ≈ 11 KB／賽季／賽事。但 TD-19 證明本專案的容量直覺不可靠。**MVP 必須實測**，並訂硬上限與汰舊策略（例如只保留最近 N 賽季逐場，更早的只留最終名次） |
| R5 | **行事曆 + 疲勞可能卡死玩家** | 主力全傷停但賽程照走 ⇒ 棄權連鎖。MVP 只判負不放大後果；輪替名單下限與後果設計留到第二階段做升降級時處理 |
| R6 | **`CompetitivePolicy` 白名單是主觀判斷** | verifier 只能擋「是否符合 policy」，擋不了「這個橫向解鎖其實很強」。需要人裁決，policy 每次增列都要複審 |
| R7 | **`seasonData.js` 兩類 Analytics 混在一起** | 接 Competition 前必須先拆，否則第一天就會踩到 |
| R8 | **`economyConfig.js` 費率仍是第一版基準** | Roadmap 自己標了「待轉會與合約系統完成後再校正」。加入賽事名次獎金會動一次現金流平衡，需要重新檢視 |
| R9 | **`advanceDay` 契約變更會動既有 verifier 斷言** | 全案唯一一處。`check_finance_n` 系列有斷言在測 `advanceDay`。必須在 Q3 單獨處理並在報告明講，不得與其他改動混在一起 |
| R10 | **MVP 模擬勝率與引擎不一致是已知且刻意的** | 見 D16。玩家可能發現「我打贏的隊在 AI 之間卻常輸」。校準列第二階段第 2 項，MVP 期間屬已知限制而非缺陷 |
| R11 | **MVP 沒有正式的模擬出賽，玩家一季須實打 14 場（約 5–7 小時）** | 配上「逾期自動判負」，體驗上等於「不親自打完就丟分」。MVP 以 debug 快進驗收賽季完整性；正式解法是第二階段第 1 項。驗收時若得到「賽季能跑但沒人想跑完」的結論，屬預期內 |
