# Retention Foundation v1 設計（V7B）

> 2026-08-27　狀態：**v1 已實作**（`check_retention_v7b` 58/58、瀏覽器驗收見 §8）
> 相關：`docs/design/Season_vNext_長期生涯與競賽框架.md`、`docs/handoff/05_Sprint紀錄.md`

---

## 1. 這個系統要解決什麼

遊戲裡可以做的事很多（對戰、訓練、球探、賽季、休賽期），但**沒有一處告訴玩家
「今天要做什麼」**。玩家打開遊戲得自己想；想不出來的那一天，就不會打開。

Retention v1 給的是**三個時間尺度上的「下一步」**：

| 尺度 | 回答的問題 | 量體 |
|---|---|---|
| 今日目標 | 我今天做什麼？ | 3 個，約 10–20 分鐘 |
| 本週目標 | 這一週該累積什麼？ | 3 個，正常玩就會完成大部分 |
| 賽季目標 | 這一年要達成什麼？ | 4 個，都不需要冠軍 |

---

## 2. 三條硬紅線

這一類系統很容易做壞。以下三條寫死在驗證器裡（`tools/check_retention_v7b.mjs`）：

1. **日常目標不得直接給永久戰力。**
   否則「每天上線點一點」會變成最有效率的養成路徑，而本作的養成主線是
   訓練與比賽（PCGM）。v1 的獎勵**只有俱樂部點數**。
2. **日目標不得要求玩家去推正式季賽。**
   季賽是賽程排定的，不是想打就有。放進日常任務等於在沒有比賽的日子
   給玩家一個做不到的格子。
3. **賽季目標不得以冠軍為前提。**
   「沒奪冠也要有完整賽季進度」是規格。四個賽季目標看的是名次線、累積積分、
   青訓人次與財務流量，沒有一個要求第一名。

---

## 3. 時間綁的是**世界時間**，不是真實時間

**沒有 ServerTime，也不會有。** 日／週／年一律由 `meta.days` 推導：

```
日 = meta.days
週 = deriveTime(days).week
年 = careerYearOf(days).year        ← 與休賽期／生涯年度同一條時間
```

### 為什麼

真實時間會產生兩個本作承受不起的後果：

1. **玩家離線時進度自己流失。** 單機經營遊戲不該有這種焦慮。
2. **掛機等時間變成一種玩法。** 世界時間才是本作真正的稀缺資源
   （老化、合約、體力、賽程全部掛在它上面）。

綁世界時間之後有一個很好的性質：**今天的目標只有玩家自己推得動**
⇒ 沒有時限焦慮，也刷不動（推一天要付出老化與合約的代價）。
這與 V2 的每日競技容量是同一條規則，不是第二套時間觀。

## 4. 目標內容

### 4.1 今日目標（池 5 取 3）

| id | 名稱 | 條件 | 導向 |
|---|---|---|---|
| `play` | 今日出賽 | 打 1 場對戰（任何層級） | 快速對戰／一般對戰 |
| `train` | 安排訓練 | 替任一名選手安排 1 堂課 | 訓練 |
| `scout` | 球探回報 | 對 1 名新秀進行偵查 | 球探 |
| `win` | 拿下勝利 | 贏 1 場一般對戰 | 一般對戰 |
| `tryout` | 試一次陣容 | 打 1 場快速對戰 | 快速對戰 |

每一個都是「做一次」。三個加起來落在 10–20 分鐘：一場對戰約 5–8 分鐘，
訓練與球探各是一次點擊。

### 4.2 本週目標（池 5 取 3）

| id | 名稱 | 條件 | 主題 |
|---|---|---|---|
| `volume` | 本週出賽 | 5 場（任何層級） | 基本量 |
| `rotate` | 輪替陣容 | 7 名不同選手出賽 | 輪替 |
| `youth` | 新人上場 | 21 歲以下累積 2 人次 | 新人 |
| `variety` | 兩套打法 | 2 種不同先發陣容 | 不同陣容 |
| `streak` | 本週戰績 | 贏 3 場一般對戰 | 成績 |

每日競技容量 3 場 ⇒ 一週上限 21 場。**5 場是兩天的量**，刻意遠低於上限：
週目標的主題是**輪替**，不是刷場次。

### 4.3 賽季目標（4 個固定，不抽）

| id | 名稱 | 條件 | 進度來源 |
|---|---|---|---|
| `rank` | 賽季名次 | 常規賽排名進入前 4 | **推導**自賽季積分榜 |
| `circuit` | 巡迴成績 | 本年度累積 100 點巡迴積分 | **推導**自 `circuitPoints` |
| `youth` | 青訓成果 | 本年度 U21 累積出賽 20 人次 | 計數器 |
| `finance` | 財務目標 | 本年度累積 800 萬對戰收入 | 計數器 |

⚠ 名次與巡迴積分是**推導**的，不是計數器——賽季自己已經有帳本，
再存一份必然漂移。沒有賽季時據實顯示「本季尚未開賽」，不猜一個名次。

## 5. 獎勵：俱樂部點數（Club Points）

| 尺度 | 點數 |
|---|---|
| 今日 | 10 |
| 本週 | 40 |
| 賽季 | 300 |

v1 的**唯一出口**是**俱樂部聲望等級**——純展示、不影響任何數值：

```
見習俱樂部 0 → 職業 500 → 精英 2000 → 名門 6000 → 傳奇 15000
```

### 為什麼 v1 不做兌換

兌換球探情報／青訓名額／商業解鎖都是**真正的產品功能**，各自要接既有系統
（`scouted`、招募池、贊助）。硬塞進 v1 會讓這一輪從「立起框架」變成
「同時改四個系統」。v1 先讓點數**累積得起來、看得見、有等級**，
兌換出口列為 v2（見 §9）。

## 6. 架構

```
src/platform/retention/
  retentionObjectives.js   目標池、獎勵表、決定性抽選、尺度前綴（純規格）
  retentionState.js        計數器／集合／領取、推導 view（純函式）
```

### 6.1 存的是什麼

```js
retention: {
  schema: "Retention.v1",
  clubPoints: 0,
  counters: { "d84:match": 2, "w12:win": 3, "y3:matchIncome": 1200000 },
  sets:     { "w12:players": ["p1","p3"], "w12:lineups": ["p1+p2+p3+p4+p5"] },
  claims:   { "d84:daily:play": true },
}
```

**目標清單本身不落盤**——它是 `(尺度前綴, teamId)` 的決定性函式。
同一天重整、換裝置、重讀存檔都會看到同一組（用亂數就會出現「重整換一組簡單的」）。

### 6.2 過期不必寫清除程式

所有 key 都帶尺度前綴。換一天，昨天那些 key 就再也沒有人讀 ⇒ **語意上自動失效**。
`pruneScopes` 只是把它們從存檔掃掉（省空間），不是正確性的一部分。
領取紀錄同樣帶前綴 ⇒ 同一個目標換一天就是新的一格，不可能重複領。

### 6.3 為什麼是計數器而不是事件流水

一個生涯年度 84 天、上百場比賽。流水會無限成長，還得訂「保留幾筆」的上限——
而那個上限一旦砍到賽季目標需要的範圍，**年度進度就會默默變少**。
計數器沒有這個問題：一個尺度一格，過期的整格丟掉。

### 6.4 寫入點只有既有的三個

| 活動 | 寫入點 | 為什麼是這裡 |
|---|---|---|
| 比賽 | `progress/applyMatchProgress.js` | 全專案**唯一**的結算入口；掛別處必漏來源 |
| 訓練 | `profileStore.assignTraining` | 玩家今天做的事是「安排」，不是課程結束 |
| 球探 | `profileStore.setScouted` | 只在偵查等級**真的往上走**時記，否則重複點就能刷滿 |

⚠ 函式叫 `recordMatchActivity`，**不叫** `recordMatch`：Legacy 的
`EsportsGame.jsx` 已經有一個同名不同事的 `recordMatch`。

### 6.5 快速練習的邊界

練習**只計「今天打了一場」**（日目標 `play` / `tryout` 需要它），
不計勝場、不計收入、不算輪替、不算青訓——與 V0D「零永久影響」一致。

## 7. UI

- **目標頁**：`src/screens/manage/ObjectivesScreen.jsx`（路由 `objectives`）
- **桌面入口**：首頁「管理工具」的「俱樂部目標」磚，帶一個**聚合**徽章
- **手機入口**：底部「更多」sheet 的「俱樂部目標」
  ⚠ 手機版**不渲染** `Utility`，所以桌面那個磚在手機上不存在。
  第一版漏掉這一項，手機玩家根本進不去——瀏覽器實測抓到。
- **有東西可領時**，手機首頁「還需要處理」會多一張卡

### 不做逐項紅點

規格明文擋掉「十幾個紅點任務」。首頁只有**一個**聚合數字，目標頁也只有分組聚合。
紅點多了就不是提示，是噪音。

### 領取是手動的

目標達成不會自動入袋。玩家需要一個明確的「我今天做完了」的動作，
而不是被動地看到數字自己變。

## 9. v1 刻意不做（＝ v2 的清單）

| 項目 | 為什麼不在 v1 |
|---|---|
| **俱樂部點數的兌換出口** | 要接 `scouted` / 招募池 / 贊助三個既有系統，各自是獨立的產品決定 |
| **不同戰術目標** | `MatchProgressTransaction.metadata` 是白名單，加 `tacticId` 要動被凍結的契約 |
| **Season Pass / 戰令** | 規格明文排除 |
| **Alliance / 公會** | 規格明文排除 |
| **Ranked / 牌位 / 排行榜** | 規格明文排除；一般對戰的定位是「日常低壓力實戰」 |
| **ServerTime** | 見 §3，這是**永久**排除，不是延後 |
| **總收入型財務目標** | v1 只算對戰收入；要含贊助得再掛一個週結算的寫入點 |
