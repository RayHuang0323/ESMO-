## 0. 一句話

**生涯時間買的是「人才深度與組隊選擇」，不是「線上戰力上限」。**
把這句話變成三個可驗證的結構：**兩個時鐘不互通、線上零永久成長、陣容上限只存在於線上**。

## 2. 核心問題的結構分析

使用者的題目：

> 生涯可以快轉、選手又會永久成長，那怎麼避免玩得快的人在線上天然碾壓其他玩家？

拆開來看，它其實是**一個資源錯配**：

```
CareerTime   = 私有資源。每個存檔自己一條，玩家可以快轉，
               取得速度取決於「誰有空、誰願意按」。
ServerTime   = 公共資源。全世界同一條，誰都快轉不了。

永久能力     ← 由 CareerTime 產生
線上名次     ← 若也由永久能力決定
⇒ 線上名次 = 私有資源的函式 = 「誰有空」的排行榜。
```

⇒ **問題不在「成長」，也不在「快轉」，而在「永久能力直接換算成線上戰力」這條邊。**
要修的是那條邊，不是兩端。

### 2.1 為什麼單靠配對評分（MMR）在 ESMO 不夠

一般線上遊戲用 MMR 就解決了：強的人自然被配到強的人。ESMO 不行，理由很具體：

**ESMO 是經營模擬，比賽由 AI 打完，玩家不操作。**
在 FPS/MOBA 裡「操作技術」佔勝負大半，MMR 量的是技術；
在 ESMO 裡勝負主要由**陣容能力**決定 ⇒ 純 MMR 會收斂成一條**陣容戰力排行榜**，
也就是「生涯肝度排行榜」——正好是要避免的東西。

⇒ **ESMO 必須有「帶什麼進場」的限制，不能只有「配到誰」的限制。**

### 2.2 三個候選方案

| 方案 | 做法 | 判定 |
|---|---|---|
| **A. 只有 MMR** | 依戰績配對 | ❌ 見 §2.1，收斂成肝度榜 |
| **B. 線上統一數值** | 線上用固定能力，生涯不影響 | ❌ 使用者明確反對的「割裂」；生涯培養失去線上意義 |
| **C. 上限 + 分級 + 評分** | 陣容有預算上限，依預算分級，級內用 MMR | ✅ **採用** |

## 3. 兩個時鐘契約（FINAL）

```
        CareerTime（每個存檔一條，可快轉）        ServerTime（全世界一條，不可快轉）
        ────────────────────────────────        ──────────────────────────────────
        meta.days（唯一寫入者 advanceDay）        真人配對
        訓練 / 永久成長 / 年齡                    真人競技賽季與排行榜
        生涯季賽賽程                              定時賽事的報名與開賽時刻
        財務 / 粉絲 / 戰績                        線上每日配額的重置
        體力恢復                                  （未來）連線狀態恢復
        未來：衰退 / 退休 / Off-season

                   兩條時間**沒有換算率**。
        它們透過 SquadSnapshot 單向接觸：CareerTime 產生陣容，
        ServerTime 消費陣容快照。快照之後，兩邊互不影響。
```

### 3.1 為什麼是「沒有換算率」而不是「1 Event = N Career Days」

上游文件 §4 提過 `EventTimeBlock { careerDaysConsumed: 1 or 2 }`，也就是**有換算率**。
本輪**推翻這個方向**，理由是上游自己的 grilling G4 已經走到一半：

G4 發現「真人 Event 是現實排定的，玩家控制不了頻率 ⇒ 勤奮參與 = 老得快 = 懲罰參與」，
於是採納了 Event Window（窗口內不額外消耗）。但只要 `careerDaysConsumed` 這個欄位還在，
**窗口外的情況就仍然有換算率，而換算率就是漏洞的形狀**：

- 換算率 > 0 ⇒ 打線上會老 ⇒ 懲罰參與（G4 原本要擋的）
- 換算率 = 0 ⇒ 那這個欄位就不該存在

⇒ **直接把換算率刪掉：線上活動一律 `careerDaysConsumed = 0`，不分窗口內外。**
Event Window 從「豁免規則」降級成**純排程資訊**（哪幾天有賽事可報名），不再是時間計價。

這讓契約少一個欄位、少一條分支、少一個要 balance 的數字。

### 3.2 不變式（本節即為 `TwoClocks.v1` 的內容）

| # | 不變式 | 擋住什麼 |
|---|---|---|
| **I1** | ServerTime 的任何事件**不得寫入** `meta.days` | 線上活動偷推生涯日曆 |
| **I2** | 線上比賽的結算路徑**不得寫入** `players[].stats`（永久能力） | 刷線上換永久能力 |
| **I3** | 線上比賽**不得寫入** `finance` / 粉絲 / 生涯戰績 | 經由經濟迂迴換戰力 |
| **I4** | 線上戰力 = `f(SquadSnapshot)`，輸入**不含** `meta.days` / `careerYear` / 即時體力 | 快轉直接換線上優勢 |
| **I5** | `meta.days` **不得**成為線上進場條件；ServerTime **不得**成為生涯操作條件 | 兩個時鐘互相卡住對方 |
| **I8** | 賽事開賽時刻**只由** ServerTime 決定 | 生涯快轉影響盃賽 |

（I6 / I7 / I9 見 §6、§7、§11。編號在 §9 統一收整。）

## 4. 四種玩法的最終責任（FINAL）

⚠ 這張表取代上游文件 §9。差異在 §12 逐條說明。

| | **① 快速練習** | **② 生涯季賽** | **③ 真人競技** | **④ 真人定時賽事** |
|---|---|---|---|---|
| **時鐘** | 都不屬於 | CareerTime | ServerTime | ServerTime |
| **origin.kind** | `practice` ✅已有 | `fixture`（正式）／`ticket`（一般競技） ✅已有 | `online` 🆕 | `event` 🆕 |
| **growth source** | `practice` ✅已有 | `official` / `competitive` ✅已有 | `online` 🆕 = **0** | `online` 🆕 = **0** |
| **消耗世界時間** | 0 | 正式賽 0（日曆點）；一般競技 0（吃每日容量 3） | **0** | **0** |
| **永久能力成長** | **0** | 正式賽最高；一般競技中 | **0** | **0** |
| **金錢** | 0 | ✅ | **0** | **0** |
| **粉絲** | 0 | ✅ | **0** | **0** |
| **生涯戰績** | 不計 | ✅ | 不計 | 不計 |
| **產出** | 手感、陣容資訊 | 冠軍、獎金、粉絲、生涯紀錄 | 評分、牌位、排行榜 | 名次、積分、榮譽 |

| **本輪狀態** | ✅ 已實作 | ✅ 已實作 | 📄 **只定契約** | 📄 **只定契約** |

### 4.1 為什麼線上兩層的成長是 0 而不是「少量」

上游 §9 給 Live Event 的是「中高」永久成長。本輪推翻，理由是**任何非零值都會把問題往下推一層**：

> 若線上成長 > 0，則「線上能力」= f(線上場次) = f(玩家有多少現實時間)。
> 分級與預算**擋不住這一條**——因為成長會讓你往上跨級。
> ⇒ 分級只是把「誰有空」的排行榜延後幾週出現，沒有消除它。

**0 是唯一守得住的線**，而且它有現成的實作樣板：快速練習（V0D）已經證明
「零成長 / 零獎勵 / 不計戰績」這組規則可以在**不新增第二條管線**的前提下實現，
而且有 70/70 的驗證器釘住。線上直接沿用同一組形狀。

**主題上也站得住**：現實中的電競選手不是靠打冠軍賽變強的，
奪冠拿到的是**名聲**不是**能力**。線上是**驗證場**，生涯才是**養成場**。

> 📌 **LATER（不是現在）**：若上線後發現線上參與度不足，可考慮
> 「線上表現存進一個池子，只在 CareerTime 內、且有每日上限地轉換成成長」。
> 但那要另一整套預算機制，且會重新打開 I2。**現在不做，也不預留欄位。**

## 5. 生涯選手如何安全帶進線上（FINAL）

一句話：**帶人過去，不帶時間、不帶狀態、不帶回報。**

```
CareerTime 這一側                    │  ServerTime 這一側
                                     │
  players[] （真實、會成長、會老）      │
        │                            │
        │  進場時取快照                │
        ▼                            │
  SquadSnapshot.v1 ──────────────────┼──▶  定價 price()  ──▶ 分級 Bracket
   · 五名選手的能力**值**（非參照）      │            │
   · 狀態/士氣一律正規化為基準值         │            ▼
   · mode（moba / cs）                 │      級內配對 Rating
   · 不可變、有雜湊、進場即凍結          │            │
                                     │            ▼
                                     │      結果：評分 / 名次 / 榮譽
        ◀────────────  ✗  ────────────┼───────  （不回流）
        任何永久能力 / 金錢 / 粉絲       │
```

### 5.1 為什麼一定要「快照」而不是直接讀 `players[]`

三個具體理由，每一個都對應一個漏洞：

1. **盃賽跨現實時間**（Swiss → Playoff → Final 可能跨數小時）。
   若讀即時 `players[]`，玩家可以在賽事進行中回生涯訓練／快轉，**中途換強**。
   ⇒ 快照凍結，賽事全程用同一份。
2. **定價與模擬必須同源**（§6.3）。快照是「同一份輸入」的載體。
3. **未來接真人伺服器時，伺服器要能獨立驗算**。快照是可傳輸、可雜湊、可重算的。
   `playerCondition.js` 已經是完全決定性的（「伺服器可以獨立驗算客戶端送回的狀態」），
   快照讓這個性質延伸到整個陣容。

### 5.2 不變式

| # | 不變式 |
|---|---|
| **I10** | `SquadSnapshot` 在報名／進場時產生，**賽事期間不可變**；生涯側的任何變動不影響已產生的快照 |
| **I11** | 快照存**值**不存參照（不得是 `players[]` 的指標） |
| **I12** | 快照的雜湊必須涵蓋所有影響模擬的欄位（否則伺服器驗算會通過一份被竄改的陣容） |

## 6. 推薦的線上公平模型：**CBR 三層**（FINAL 為結構，LATER 為數值）

**Cap（陣容上限）→ Bracket（分級）→ Rating（評分）**

三層各自回答一個不同的問題，順序不可交換：

```
Cap      「你能帶什麼？」      ── 陣容定價 ≤ 該級上限
  ↓
Bracket  「你會碰到誰？」      ── 由陣容定價決定你的級別下限
  ↓
Rating   「你們誰比較強？」    ── 級內用戰績排序（這裡才是競技本體）
```

### 6.1 Cap —— 薪資帽的形狀

**定價 = 既有 `teamStrength.v1`（`calcPower` 五人合成），不新造第二套戰力公式。**

這一點很重要：ESMO 已經有一個被 Q2b 規格 D16 要求「必須真的吃 16 項能力」的合成模型。
線上定價**必須用它**，否則會出現「定價看的能力」與「模擬看的能力」不同 ⇒ 未被定價的能力
就是免費戰力（§11-A12）。

> **主題契合**：這就是職業運動的**薪資帽**。ESMO 是電競經營遊戲，
> 「線上聯賽有薪資帽、生涯自己的隊沒有」是玩家一秒就懂的設定，
> 不需要教學，也不需要解釋為什麼。

### 6.2 Bracket —— 級別由陣容決定，不由生涯年資決定

- 你送出的陣容定價，決定你**最低**能進哪一級。**不能往下沙包**。
- 往上打（用弱陣容進強級）是允許的，那是玩家自己選擇面對更強對手。
- ⇒ **生涯肝度讓你往上跨級，不讓你在同級內變強。**

這一句就是整個設計的答案。Career Year 10 的玩家進頂級，
碰到的是其他頂級陣容（可能是另一個 Year 10，也可能是 Year 3 的天才隊）。
他買到的是**入場資格與選擇餘裕**，不是**同級內的碾壓**。

### 6.3 定價與戰力必須同源（**這一條是本輪最重要的實作約束**）

`calcPower()` 目前把**士氣與狀態**算進戰力。若照搬：

> 玩家可以刻意讓選手體力見底 ⇒ 定價下降 ⇒ 掉到低級 ⇒
> 但如果線上把狀態正規化，他們**打起來卻是滿血** ⇒ **完美沙包**。

⇒ **不變式 I13：線上定價與線上模擬必須吃同一份快照、同一組正規化規則。**

具體做法（契約層，不是實作）：快照產生時，`condition` 與 `morale`
一律寫成**基準值**；定價與模擬都讀快照 ⇒ 兩者結構上不可能分歧。

⚠ 這也表示：**線上不吃體力、也不扣體力**。體力是生涯的輪換資源，線上不碰它。

### 6.4 為什麼不是「分級競技」單獨一項

分級若沒有上限（Cap），級別要靠什麼判定？靠 Rating ⇒ 回到 §2.1 的肝度榜。
靠生涯年資 ⇒ 懲罰玩得久的人，且可以開新存檔規避。
⇒ **Cap 是 Bracket 的度量衡**，兩者是同一個機制的兩面，不是兩個選項。

### 6.5 這一層的數值**現在不決定**

**LATER**：級別數量、各級上限、上限是絕對值還是百分位、是否隨賽季浮動、
配額大小、Rating 演算法（Elo / Glicko / 其他）。
這些都要等真的有線上樣本才有意義，**現在寫死等於瞎猜**。

## 7. 為什麼這個模型長期不會崩

### 7.1 天花板才是真正的防線

分級與上限處理的是**同級內的公平**。長期公平靠的是另一件事：**永久能力有硬上限**。

`potentialSpace.js`（V0B，gamma 0.6）保證 `room = 0` 時成長因子**恰好是 0**——
上限是硬的，不是逼近。加上 `ageEfficiency`（34 歲 = 20 歲的 29%），結果是：

> **時間讓你更快抵達天花板，時間不會抬高天花板。**

⇒ Career Year 20 的隊伍**不會**比 Career Year 6 的隊伍強，只要後者招到同等潛力的選手。
頂級的差異因此收斂到**潛力、球探、招募、陣容契合**——那是設計題，不是肝度題。

⇒ 這也回答了「老玩家是否天然碾壓新玩家」：**在一個有天花板的系統裡，不會。**
新玩家要追上的是「幾年」，不是「無限」。而那個「幾年」正是上游已裁決的產品驗收目標
（Year 1 可輪換 / Year 2 穩定主力 / Year 3–4 接近巔峰）。

### 7.2 零回報順帶消滅了小號問題

因為線上**不產生任何可帶回生涯的東西**，用弱陣容去低級屠殺的收益是「低級的評分」——
一個沒有任何用途的數字。**沒有誘因，就不需要反制機制。**

這是零回報設計的意外紅利：一般遊戲要花很大力氣做的反小號系統，這裡結構上不需要。

## 8. 狀態 / 疲勞：**建議不要分成兩套**（FINAL）

使用者提的是「生涯狀態 vs 真人競技狀態」兩套恢復。**我的建議是不要分**，改用下面這組。

### 8.1 為什麼不分

1. **「現實時間恢復」正是使用者自己擔心的產品陷阱**——手遊體力條。
   使用者在 grilling 清單裡已經自己列了「真實時間恢復是否變成逼玩家等待」。
   答案是：**會**。而且這是玩家最討厭的機制之一。
2. **專案已經做過同一個選擇了。** V2 決定競技比賽的時間成本時，
   實跑比較四種做法，明確**否決了「D 競技點數條（一條與體力平行的新資源）」**，
   選了「C 每日容量」。理由逐字寫在 `worldClock.js`：
   > 「時間不是『一場比賽的價格』，而是『一個世界日裡能做多少事』」

   線上遇到的是同一個問題，**沒有理由給出相反的答案**。
3. **兩個體力數字在 UI 上無法解釋。** 選手頁要顯示哪一個？

### 8.2 改採的三層

| 層 | 機制 | 恢復 |
|---|---|---|
| **生涯體力** `players[].energy` | 維持現況：出賽扣、連續出賽加扣、低於 15 不可出賽 | CareerTime（`restPerDay`） |
| **線上狀態** | **正規化**——不是一個資源。線上不吃體力也不扣體力 | 不需要恢復 |
| **線上場次量** | **現實時間配額**（每現實日 N 場競技） | ServerTime 自動重置 |
| **賽事內疲勞** | **賽事局部**——只在一場定時賽事的 Swiss/Playoff 之間有意義 | 賽事結束即消滅，**永不寫入 `players[]`** |

### 8.3 為什麼「配額」不等於「逼你等」

- 配額用完 ⇒ 今天的**線上競技**打完了，但**生涯完全不受影響**，玩家還有整個生涯可以玩。
  這跟「體力空了，整個遊戲停住」是不同的體感。
- **定時賽事不吃配額**（它由開賽時刻決定，不是由玩家頻率決定）⇒
  勤奮參賽的人不會因為配額被鎖在門外。這是 G4「不得懲罰參與」的延伸。
- 配額大小屬 §6.5 的 LATER 數值。原則：**只擋極端刷分，不擋正常遊玩。**

### 8.4 不變式

| # | 不變式 |
|---|---|
| **I14** | 線上比賽**不讀也不寫** `players[].energy` / `matchStreak` |
| **I15** | 賽事內疲勞的生命週期**不得超出該場賽事**，且不得序列化進存檔 |
| **I16** | 線上配額由 ServerTime 重置，**不得**被 CareerTime 推進所重置 |

## 11. Grilling — 自我壓力測試

格式：**攻擊 → 在本設計下會怎樣 → 殘留風險**。
（依 `grilling` 的 frontier 方法，但本輪由設計者自問自答，不中斷使用者。）

### A1. 狂快轉生涯 ⇒ 線上戰力優勢？
**擋住，但不是靠分級擋的。** 分級只保證你碰到同級的人；真正的防線是 §7.1 的**硬天花板**：
`potentialSpace` 在 `room = 0` 時恰好是 0，`ageEfficiency` 讓 34 歲只剩 29% 效率。
⇒ 快轉讓你**更快到達**天花板，不會**抬高**天花板。頂級最後收斂到「大家都接近潛力上限」，
差異落在潛力與招募，那是設計題。
**殘留**：快轉仍然縮短「抵達頂級所需的現實時間」。這是單機養成遊戲的本質，
且因為線上零回報，它換不到任何線上以外的東西。**接受。**

### A2. 狂打真人競技 ⇒ 刷永久能力？
**結構上不可能。** `MATCH_SOURCE.online` 的 `sourceBase = 0`，走的是與快速練習同一組
已驗證的零成長規則（I2/I3/I14）。**殘留：無**，但必須有 sentinel，否則未來某一輪
「順手」把 online 調成 0.1 就破了。

### A3. 老玩家天然碾壓新玩家？
**同級內不會**（§6.2 級別由陣容定價決定，不由年資）。
**跨級不會相遇**。**長期不會**（§7.1 天花板）。
**殘留**：同級內，老玩家因為候選人多，能在同一個預算下組出**契合度更好**的五人。
這是真實優勢，但**有界**，而且正是使用者要的「人才深度與組隊選擇」。**接受並視為設計目標。**

### A4. 陣容上限讓養成失去意義？
**這是本模型最大的風險，靠 I6 擋住**：**上限只存在於線上，生涯比賽永不套用**。
生涯的冠軍、Major、年度總決賽全部無上限 ⇒ 把選手練到頂在生涯側**永遠有價值**，
在線上側則換成**跨級資格**。
**殘留**：若未來有人「順手」把預算套用到生涯賽（例如做聯賽平衡時），養成當場失去意義。
⇒ I6 必須有 sentinel。**已列入 §10.2。**

### A5. 生涯與線上完全切開 ⇒ 太割裂？
**沒有完全切開。** 切斷的**只有回報流**，共用的是**選手、陣容、戰術、模擬器**——
也就是遊戲的主體。玩家帶去線上的是自己養了四年的隊，只是不把獎盃換成能力。
**殘留**：線上零回報可能導致參與度不足。⇒ 已列 §4.1 的 LATER
（「有上限、只在 CareerTime 內轉換」），但**現在不做也不預留欄位**——
預留欄位就是預留漏洞。若真的要做，重開一輪 grilling。

### A6. 現實時間恢復 ⇒ 逼玩家等待？
**已從設計中移除。** §8 不做線上體力條，只做配額；配額用完生涯照玩；
定時賽事不吃配額。
**殘留**：配額本身仍是一種等待。⇒ 原則寫死為「只擋極端刷分，不擋正常遊玩」，
數值屬 LATER，且上線後必須量測「觸頂玩家佔比」。

### A7. 真人盃賽被生涯時間影響？
**不會**（I8 + I10）。開賽時刻只由 ServerTime 決定；陣容在報名時凍結成快照。
玩家在賽事進行中快轉生涯，賽事**逐值不受影響**。
**殘留**：玩家可能覺得「我明明練強了為什麼賽事裡還是舊數值」。⇒ **UI 責任**：
報名時必須明示「本賽事使用此刻的陣容快照」。列入 LATER 的 UI 需求。

### A8. 多玩 MOBA / CS 繞過公平限制？
**生涯側已經擋住**（V2：容量計數器掛在 `meta`，切換 mode 買不到第二份額度）。
**線上側靠 I9**：分級、配額、評分、獎勵**一律 per mode**，不得跨模式轉移。
**殘留**：若未來做「俱樂部總聲望」聚合兩個模式，那就是繞道。
⇒ 約束：**聲望類聚合只能是顯示用，不得換成任何戰力或資源。**

### A9. 沙包：刻意壓低定價進低級？
**§6.3 的 I13 擋住**，而且這是本輪最容易被實作漏掉的一條。
`calcPower()` 現在吃士氣與狀態 ⇒ 若定價吃、模擬不吃，就是完美沙包。
⇒ 定價與模擬**吃同一份快照、同一組正規化**，結構上不可能分歧。
**殘留**：若未來有人給線上加上「狀態影響」而忘了同步定價，漏洞立刻回來。⇒ sentinel 必要。

### A10. V3 快轉會不會讓時間變成免費的？
**這一條是本輪對 Roadmap 最重要的發現。**

V3（大顆時間操作）讓玩家可以一次推很多天。時間的**代價**目前有兩層：
- ✅ **已存在**：`ageEfficiency`——快轉會讓選手變老，成長效率下降（34 歲 = 20 歲的 29%）
- ❌ **尚未存在**：衰退（V4）與退休（V5）

⇒ **在 V4/V5 之前，快轉的代價只有「成長變慢」，沒有「能力下降」與「選手消失」。**

這**不足以阻擋 V3**，因為 `ageEfficiency` 已經讓「無腦快轉到全員滿能力」行不通
（等你快轉完，他們已經老到長不動了）。但它是一個**有時效的已知缺口**，
必須登記，並在 V4/V5 落地時回頭複驗。

**另一個 V3 專屬的洞：容量囤積。**
若 V3 一次推 7 天，玩家會不會拿到 21 場競技容量？
查過現況：`competitiveBlockOf(stored, day)` 在 `stored.day !== today` 時 `used` 歸 0，
容量恆為 3 ⇒ **現況正確，不會囤積**。但這是**碰巧正確**，沒有任何測試釘住它。
⇒ **I7 必須在 V3 補上 sentinel**（讓容量跨日累積 ⇒ 紅）。

### A11. 快轉會不會讓「訓練」變成無限？
訓練是 89% 的成長來源，且只被體力與課程天數限制。快轉推進天數 ⇒ 回體力 ⇒ 可以再練。
⇒ **快轉確實是通往天花板的主要途徑。**
但：① 有天花板（§7.1）② 會變老 ③ **換不到線上優勢**（本檔整份的重點）。
**殘留**：這是**生涯側的平衡問題**，不是線上公平問題。登記為風險，
留給 V4/V5 之後的 balance 輪次。

### A12. 未被定價的能力 = 免費戰力？
若定價用 A 公式、模擬用 B 公式，兩者涵蓋的能力不同 ⇒ 差集就是免費戰力，
玩家會全部堆在那裡。
⇒ **§6.1 強制定價委派 `teamStrength.v1`（即模擬用的同一支）**，不得自建公式。
**殘留**：`teamStrength.v1` 自己承認「未與 LogicEngine 校準」。
⇒ 若線上真的用 LogicEngine 打，而定價用 teamStrength，**差集又出現了**。
**這是一條真實的未解風險**，登記為 TD，V7 之前必須處理。
