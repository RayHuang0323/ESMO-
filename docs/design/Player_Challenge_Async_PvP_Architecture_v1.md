# Player Challenge (Async PvP) Architecture v1

> 架構設計。**本輪不改任何 `src/`**：不實作 Pricing Authority / Cap / Bracket /
> LadderRating / Ranked，不動 MOBA / CS battle runtime，不改 `teamStrength` 權重，
> 不實作 monetization，不重做 General Match。
>
> 承接 `ESMO_Core_Loop_Mode_Differentiation_v1.md`（28859a2）的全部結論，
> 並納入本輪 Owner Decisions 1–5。

---

## 0. 一句話

**這一整套架構的支點是「引擎是決定性的」。**

一場對戰是 `模擬(seed, 我方快照＋我方戰術, 對方快照＋對方預存方案)` 的純函式。
一旦這句話成立，非同步 PvP 的每一個難題都會塌成同一個答案：
**存輸入，不存輸出**；**同一組輸入就是同一場比賽**。

由此直接推出去重、重整、回放、rematch、防洗牌五件事的語意（§4），
而且不需要為它們各發明一條規則。

## 3. `SquadSnapshot.v1`：為什麼它現在才有理由存在

### 3.1 它與 `MatchEntryRequest.v1` **方向相反**，而且兩者都對

這是本輪最重要的一個釐清，弄錯會把兩份契約合成一份錯的。

| | `MatchEntryRequest.v1` | `SquadSnapshot.v1` |
|---|---|---|
| 描述的是 | **我**的出賽申請 | **對手**的凍結狀態 |
| 帶不帶數值 | **絕對不帶**（遞迴掃描擋下） | **必須帶** |
| 為什麼 | 伺服器手上有我的真實資料，客戶端說什麼都不算 | **對手不在線上，沒有人可以去查** |
| 誰有權產生 | 我的客戶端（伺服器重驗） | **只有擁有那條生涯的一方**（或伺服器代其產生） |

⇒ 「只送身分不送值」這條紅線**不適用於快照**，因為它的前提（有一個線上權威可查）
在非同步情境下不成立。反過來，快照因此必須靠**雜湊 ＋ 簽發者**建立可信度。

⚠ **挑戰者的客戶端永遠不得構造對手的快照。** 這是本架構的信任邊界。
挑戰者只能引用一份**已發布**的快照（by hash），不能提供它的內容。

### 3.2 `SQUADSNAPSHOT_FIRST_REAL_CONSUMER = Player Challenge`

在 Player Challenge 之前，快照確實沒有真實消費端：

- Career 賽季讀即時 `players[]`（`simulateFixture` 直接吃 roster）。
- 定價（`teamStrength`）今天沒有任何線上消費端。
- Cap / Bracket / Rating 全都不存在。

⇒ 先前把 `SquadSnapshot.v1` 排進去會是**沒有 consumer 的 dead module**，
Owner 的顧慮成立。**Player Challenge 是第一個「非有它不可」的消費端**——
因為對手離線，除了快照之外沒有別的方式取得他的陣容。

⚠ **但本輪仍然不建它。** 本輪只到架構；Challenge 的實作要到下一輪。
現在建，它到下一輪之前仍然是 dead module。⇒ 快照與 Challenge **同一輪落地**。

### 3.3 快照必須包含什麼（由 271b31d 直接決定）

I11「存值不存參照」與 I12「雜湊涵蓋所有影響模擬的欄位」在
`Season_vNext_生涯與線上競技公平架構.md` 已立。271b31d 讓 I12 有了**具體清單**：

| 必須入快照 | 理由 |
|---|---|
| 五個席位的身分與位置 | 沒有它重播不出來 |
| 16 項能力值 | 引擎吃它（改門檻／機率／節奏／深度） |
| **英雄熟練 loadout（power / tough 乘數）** | ⚠ **271b31d 實測：這是勝負的主要決定者**（×1.25 ⇒ 勝率 94.4%）。漏掉它，重播會對不上 |
| 戰術預設（doctrine、戰術 id、路線計畫） | 防守方的行為由它決定 |
| Ban/Pick 偏好（MOBA）／地圖偏好（CS） | 賽前流程需要對方的選擇 |
| `condition` / `morale` / `energy` | **一律寫入基準值**（I13），不寫真實值 |

⚠ 最後一列是 271b31d 那條沙包管道的堵法：這三個欄位在 `LogicEngine.js`
出現 **0 次**，卻能讓 `calcPower` 擺動 28.7%。快照把它們正規化成基準值之後，
「壓低狀態換到弱分級、打起來卻滿血」在結構上不可能發生。

⚠ **不得入快照**：俱樂部資產（`coachCatalog` 的教練與收藏）、
發展點能力（`careerOnly`）、生涯年份、Club Level、粉絲數、財務。
`tools/check_club_assets_v1.mjs` 已經在守前兩項，Challenge 落地時把清單接上去即可。

### 3.4 雜湊有一個**騙不了人**的驗證方式

因為引擎是決定性的：

> 用儲存的輸入重跑，若重播不出當初的結果 ⇒ **快照少了東西**。

⇒ I12 不需要靠人工清點欄位來保證。一支
`check_challenge_replay`「重算結果必須逐值等於當初記錄的結果」的驗證器，
會在漏欄位的當下就變紅。**這是本架構唯一一條可以自我證明的不變式**，
應該優先做，而且它同時保證了 §4.3 的「不存回放」是安全的。

## 4. 非同步模型

**`ASYNC_MODEL = 快照對快照，挑戰方即時、防守方預存，結果由決定性模擬導出。`**

```
   防守方（離線）                          挑戰方（在線）
   ─────────────                          ─────────────
   生涯推進中，某個檢查點                   打開挑戰看板
   發布 SquadSnapshot ＋ 預存防守方案   ──▶  選一個對手（看得到資訊，看不到戰力標籤）
                                            決定先發、戰術、Ban/Pick
                                              │
                                              ▼
                       seed = hash(兩份快照雜湊 ＋ 兩邊戰術)
                                              │
                                              ▼
                            決定性模擬 ──▶ ChallengeResult
                                              │
                       ┌──────────────────────┴──────────────────────┐
                       ▼                                             ▼
              挑戰方：挑戰紀錄 ＋ 情報 ＋ meta            防守方：下次上線看到「你被挑戰了」
              **不寫任何生涯成長**                        **不寫任何生涯成長**
```

### 4.1 seed 的推導方式決定了一切

```
challengeId = hash( challengerSnapshotHash | defenderSnapshotHash
                  | challengerTactic | defenderStandingOrders )
seed        = challengeId
```

⚠ **刻意不含嘗試次數、不含時間戳、不含亂數。**
與 `matchEntry.js` 的 `transactionId` 同一套手法（同一份陣容同一天送兩次 ⇒ 同一個 id）。

由這一條直接得到四件事，**不需要再各寫一條規則**：

| 問題 | 答案 |
|---|---|
| **去重** | 同一組輸入 ⇒ 同一個 `challengeId` ⇒ 天然去重 |
| **重整 / 連點 / 回上一頁** | 重算出同一個 id ⇒ 命中既有紀錄，不會產生第二場 |
| **洗結果** | **不可能**。不改任何輸入就重打，會得到逐值相同的結果 |
| **回放** | 不必存。有 id 就有 seed，有 seed 就重算得出 |

### 4.2 `SNAPSHOT_CREATION_RULE`

**由擁有那條生涯的一方發布，在生涯狀態自然落定的檢查點。**

- **自動發布**：跟著既有的存檔時機（`advanceDay` 一定會 save），
  **每個生涯日最多一份**。
- **手動發布**：「更新我的防守陣容」，同樣受每日一份的節流。
- ⚠ **不得**在每次陣容編輯時發布——那會讓玩家能高速輪換快照，
  也會讓看板上同一支隊伍出現十幾個版本。
- ⚠ **不得**由挑戰方觸發對手的快照產生（§3.1 的信任邊界）。

發布時就地做 I13 的正規化（狀態三欄寫基準值），**不是**在比賽時才正規化——
在比賽時做，定價與模擬就有機會拿到不同的輸入，那正是 I13 要擋的分歧。

### 4.3 `SNAPSHOT_EXPIRY_RULE`

**取代制，不是到期制**，外加一層新鮮度過濾：

1. 新快照發布 ⇒ 舊快照**被取代**，但**不刪除**（歷史挑戰要能重播）。
2. **挑戰看板只提供近期發布的快照**（新鮮度門檻；產品基準先取
   **真實時間 14 天**，⚠ 這是起始基準不是最終數值）。
3. **已受理的挑戰鎖住當時那份快照**，即使中途被取代也不換（= I10）。
4. 快照在畫面上**永遠標示發布日期**與「距今多久」。

**對方離線後如何使用**：不需要處理——那就是它的設計目的。
快照 ＋ 預存方案就是完整輸入，**防守方在比賽時不會被詢問任何事**。

**對方 Career 繼續推進是否影響已建立的 challenge**：
**不影響**（I10）。已建立的挑戰跑的是凍結那一份，結果標註快照日期。

### 4.4 `REMATCH_SNAPSHOT_RULE`

因為引擎是決定性的，「完全一樣的 rematch」在定義上不存在——那是同一場比賽。
所以 rematch 只有兩種，各自的規則不同：

| 種類 | 用哪份快照 | 給不給 meta 獎勵 | 產品意義 |
|---|---|---|---|
| **再試一次**（改我方戰術／陣容，打**同一份**舊快照） | 舊快照 | **不給** | 這是**學習沙盒**：可重複、可對照，正是「我要調整後再挑戰」 |
| **正式再戰**（打對方**最新**快照） | 最新快照 | 給 | 對手已經變了，這是新的一場 |

⚠ **預設是「正式再戰」抓最新快照**，「再試一次」要玩家明確選擇並清楚標示。
⚠ 「再試一次」不給獎勵，是為了擋住「對決定性模擬暴力搜尋到贏為止」——
那不是學習，是窮舉。**但保留它**，因為對照式重試正是 Owner 要的賽後學習形狀。

⚠ 誠實記下限制：玩家仍可在舊快照上窮舉出一套解，再拿去打新快照。
新快照不同 ⇒ 解不會完整轉移，但**不是零轉移**。這條在 v1 接受，不假裝已解決。

## 5. 對手探索：`OPPONENT_DISCOVERY_MODEL`

### 5.1 `CHALLENGE_BOARD_RECOMMENDED = YES`

**Challenge Board（挑戰看板），一次提供 4–5 個候選；不做自動 50/50 配對。**

理由不只是「Owner 指定」，而是**現況只允許這一種**：
自動配對必須由系統宣告「這兩隊實力相近」，而 271b31d 已經證明系統
**沒有能力做這個宣告**。看板把宣告換成**描述**，選擇權交回玩家
⇒ 系統不必說出它證明不了的話。

### 5.2 五個候選位，每一位都由**觀測值**定義，不由推估戰力定義

| 候選位 | 挑法 | 顯示的是 |
|---|---|---|
| **可以先試手** | 這份快照被挑戰過且**被攻破率高** | 「12 次挑戰，守下 3 次」 |
| **勢均力敵** | 被攻破率接近一半 | 「18 次挑戰，守下 9 次」 |
| **硬仗** | 被攻破率低 | 「15 次挑戰，守下 13 次」 |
| **特殊陣容** | 與**你慣用的**組成差異大（不同 doctrine、位置分布異常、年齡結構極端） | 「控圖流／先發平均 21.2 歲」——**完全不宣告強弱** |
| **近期突出** | 近期連勝、剛發布、剛換過陣容 | 「三天內換過先發」 |

⚠ **每一個標籤都必須是「有樣本數的觀測事實」，不是形容詞。**
寫「12 戰 3 守」，不寫「較弱」。
⚠ **樣本不足就明說**：新快照沒有紀錄 ⇒ 「尚無挑戰紀錄」，**不推估、不補值**。
⚠ 這些數字是**這份快照的被挑戰結果**，不是那位玩家的實力評分，
文案不得寫成後者。

### 5.3 可以揭露的對手資訊（都已經有資料來源）

| 玩家會看到 | 來源 | 為什麼是真人感而不是換名字 |
|---|---|---|
| 俱樂部名／隊徽／隊色／成立年 | `teamIdentity.js` | 是玩家自己取的 |
| 年度冠軍等榮耀 | `Honor.v1` | 生成隊伍沒有履歷 |
| 五名先發、位置、年齡 | 快照 | **不平均**是人的痕跡（例：先發裡插一個 18 歲） |
| 核心選手（隊內最突出的一位） | 快照 | 玩家可以針對他 |
| **流派傾向**（強攻／控圖／應變）與使用次數 | `ClubMastery.v1` ＋ `Doctrine.v1` | ⚠ **生涯累積、永不過期**，是最誠實的風格證據 |
| 常用戰術 / 戰術多樣性 | `ClubMastery.v1` 的戰術計數 | 「他八套只用兩套」可以被針對 |
| 近期挑戰結果（守方） | Challenge history | 觀測值，不是評分 |
| **最近是否換過陣容** | 快照發布時間 ＋ `rosterVersion` 變動 | 「三天內換過先發」＝ 舊情報失效 |

⚠ `Doctrine.v1` 的三條流派各自帶著 `claim`，**每一句都寫得出取捨**
（強攻「容錯低、被拖久會失勢」／控圖「需要時間、怕被快攻打穿」／
應變「上限高、前期要吃得住壓力」）。⇒ 揭露流派**本身就是可針對的資訊**，
而且不涉及任何強弱宣告。這是本節最好用的一塊資料，而且它已經在了。

⚠ **不得揭露**：對手的即時生涯狀態、財務、未出賽的名單深度、
發展點投資明細（那些是 `careerOnly` 的競技力，揭露等於情報外洩）。

### 5.4 `CURRENT_PRICING_REQUIRED = NO`

Unranked 不需要 Cap，不需要 Bracket，不需要 Rating
⇒ **完全不依賴 `teamStrength` 的定價品質**，也就不被 271b31d 擋住。

⚠ 明確禁止：**不得**把 `calcPower` 換個名字當成看板上的「戰力」「評分」「星等」。
Owner Decision 5 也禁止 Career Year 當主要公平軸、禁止宣稱 Club Level 等於戰力。
本設計三者都沒有用到。

### 5.5 `FAIR_MATCH_GUARANTEED = NO`（照實說）

**沒有可信定價就不可能保證公平**，本設計不假裝做得到。
它做的是**避免極差的首局體驗**，用四個不需要定價的手段：

1. **玩家自己選**：從 5 個描述清楚的候選裡挑，打到硬仗是選擇不是埋伏。
2. **冷啟保護**：第一次使用看板的玩家，候選優先填入被攻破率高的快照；
   ⚠ 樣本不足的快照**不放進首局看板**（不確定的東西不丟給新玩家）。
3. **依你最近的結果調整**：連敗數場 ⇒ 看板偏向被攻破率高的候選。
   ⚠ 這是**看板組成**的調整，不是難度動態調整，也不碰任何模擬參數。
4. **零永久損失**：輸掉不掉任何東西（§7.2），首局挫折的代價本來就低。

|---|---|---|
| `MatchSquad.v1` / `MatchEntryRequest.v1` | **原樣沿用** | 我方送單不變，仍然只送身分 |
| `MatchmakingTicket.v1` | **沿用，狀態流變短** | 看板挑人 ⇒ `validating → matched`，**不經 `queued`**（沒有隊要排） |
| `MatchAssignment.v1` | **沿用，換內容** | 對手欄位改帶**快照雜湊**（引用，不是內容） |
| `MatchRoom.v1` | ⚠ **這一段不能原樣沿用**（§6.2） | |
| `MatchSession.v1` | **原樣沿用** | 它本來就綁「**雙方**隊伍版本 ＋ seed ＋ 一次性 launchToken」，幾乎是為 async 寫的 |
| `MatchOrigin.v1` | **加一個 kind**：`challenge` | |
| `MobaReplay.v1` | **沿用播放器，不存檔** | 由 seed 重算（§4.3） |
| Career 練習賽 | **完全不動** | 成長 1.0、吃容量、規則逐值不變 |

### 6.1 為什麼是沿用而不是重寫

票券合法轉移表、指派單只能由 gateway 產生、場次一次性令牌、
`MatchOrigin` 串接、賽前層級橫幅——Player Challenge **每一項都需要**。
重寫會得到逐項相同的東西，外加一輪新 bug。

### 6.2 ⚠ Ready check 必須誠實地收掉

`MatchRoom.v1` 的核心是「**雙方**都確認才能進場」＋倒數。
非同步之下防守方不在線上，**沒有人可以確認**。

⇒ 房間狀態走 `waiting → confirmed`，並標示
`opponentConfirmedBy: "snapshot"`——**發布快照本身就是他的事前同意**。

⚠ **不得為了讓它「有臨場感」而假裝跑一段倒數等待。**
那與 V0D 的 `repractice` 事故是同一類錯誤：**玩家以為在做 A，系統其實在做 B**。
畫面要寫的是「對手已預先提交防守陣容（9 月 3 日）」，
不是「等待對手確認…」。

### 6.3 場次已經有 async 需要的形狀

`MatchSession.v1` 檔頭寫的是「場次綁定 roomId / assignmentId / ticketId /
模式 / **雙方隊伍版本** / 比賽 seed / 簽發者」。
對 Challenge 而言，「對方的隊伍版本」就是**防守方的快照雜湊**，
「比賽 seed」就是 §4.1 推導出來的 `challengeId`。⇒ 欄位不必新增，語意直接對上。

## 7. 獎懲邊界

### 7.1 需要第五個 `MATCH_SOURCE` 層級

現行四格全部不合用：`practice` 是零獎勵測試場、`competitive` 給生涯成長、
`official` 進賽季帳本、`unknown` 是資料遺失。

⇒ 新增 **`challenge`**，成長倍率 **0.0**。

⚠ **不得**用「`competitive` ＋ 一個布林旗標」代替。那是 TD-36 的形狀：
兩件不同的事塞進同一格，然後其中一件永遠調不動。
⚠ `GROWTH_SOURCES` 已經預留了 `ranked`（註解自陳「只是契約可擴充性，
沒有任何 write path」）⇒ 契約本來就預期會長出線上層級，加格子不算破壞設計。

### 7.2 `CAREER_WRITEBACK = NONE`

| | |
|---|---|
| 生涯選手成長 | **0**（不呼叫 `applyMatchProgress`） |
| 體力 / 狀態消耗 | **0** |
| 世界時間推進 | **0**（`WORLD_TIME_COST.challenge = 0`） |
| 正式賽季名次 / 巡迴積分 | **0** |
| LadderRating | **0**（不存在） |
| 每日練習賽容量 | **不吃**（容量是為了節流生涯成長，Challenge 沒有生涯成長可節流） |
| 永久 roster 損失 | **不可能發生**（輸掉不掉任何東西） |

**兩層防護**：
1. **主要規則**：Challenge 的結算走自己的路徑，**根本不呼叫** `applyMatchProgress`。
2. **後備**：萬一有人接錯線，`challenge` 來源的成長倍率是 **0.0**、
   `teamRewardsFor` 早退 ⇒ 就算走進去也拿不到東西。

⚠ 只有第 1 層是設計，第 2 層是防呆。驗證器要同時釘住兩層，
否則第 1 層被繞過時沒有人會發現。

### 7.3 `CHALLENGE_WRITEBACK`（可以寫回哪裡）

| 寫回 | 內容 |
|---|---|
| **Challenge history** | 對手俱樂部身分、快照日期與雜湊、我方陣容與戰術、結果、關鍵事件、`challengeId` |
| **對手情報** | 對方的流派／常用戰術／核心選手（供下次針對） |
| **防守紀錄** | 我的快照被誰挑戰、守下幾次（⇒ §5.2 的觀測值來源） |
| **Club Points** | ⚠ 依 Retention contract，**但本輪不定數值** |
| **社群 / 聲望資訊** | 挑戰次數、守成率一類的展示資料 |

⚠ **Owner Decision 1、2 的落點**：Challenge **不得**成為新的每日出賽壓力。
- Challenge **不可**進入 `DAILY_POOL` 的出賽類目標。
- 每日最多 **1 個**目標強制出賽，且必須存在
  「巡場 → 經營決策 → 推進世界日」這條**完全不比賽**也能完成的完整路徑。
- 練習賽容量 3 是 **ceiling**：UI 不得呈現成「今日 0/3」這種待辦感。

### 7.4 Ranked 的介面位置（**本輪不實作、不定數值**）

Owner Decision 3 的方向先記在架構裡，避免下一輪把路堵死：

- Rated quota 掛在 **ServerTime**，不是生涯日 ⇒ 需要一個與 `worldClock` **平行**
  的伺服器日概念。⚠ 不得把它接到 `worldClock`，那會讓線上推進生涯時鐘。
- 產品基準 **3 場／伺服器日**（起始基準，非最終數值）。
- 用完之後 Player Challenge / Practice / Career **照常可玩**。
- **Rated quota 永不可付費增加。**

### 7.5 商業化（沿用 28859a2 的結論，Owner Decision 4 收緊）

**NO**：Career reset、額外成長場次、額外 Rated quota、
任何可轉化為線上戰力的加速。
**未來可評估**：額外 Save Slot（各生涯獨立、不互相輸送資源）。
本輪**不實作、不定價**。

## 8. 玩家體驗的三個檢核

### 8.1 `PLAYER_CAN_UNDERSTAND_OPPONENT = YES`

§5.3 那張表全部有現成資料來源，其中 `ClubMastery.v1` 的流派與戰術計數
是**生涯累積、永不過期**的風格證據——這一項單獨就足以讓對手不只是一個名字。

### 8.2 `PLAYER_HAS_MEANINGFUL_PREMATCH_DECISION = YES`

判準三條（可能選錯 / 結果看得出差別 / 事後知道為什麼），
Challenge 讓前兩條**變強**，因為決策第一次有了**可針對的對象**：

- 看到對手是「控圖流、八套戰術只用兩套」⇒ 我選強攻試著打穿。
- 看到對手「三天內換過先發」⇒ 我手上的情報可能過期，要保守一點。
- 看到對手核心在下路 ⇒ 我的 Ban/Pick 與路線計畫有明確目標。

⚠ 這也讓 §4.4 的「再試一次」有意義：**改一個變數再打一次**，
是玩家自己做的對照實驗。

### 8.3 `PLAYER_HAS_MEANINGFUL_POSTMATCH_LEARNING = YES`

Owner 要的三句話，各自對應一個已經存在的資料來源：

| 玩家要能說出 | 靠什麼 |
|---|---|
| 「我這次針對成功」 | 我宣告的戰術 `evidence` 目標 vs 實際觀察值（`MOBA_TACTICS[].evidence` 已有） |
| 「我低估了他的某個配置」 | 賽後把**賽前看到的對手資訊**與**實際發生的事**並排 |
| 「我要調整後再挑戰」 | §4.4 的「再試一次」：同一份快照、改我方變數、可對照 |

⚠ 上一輪（Team Development Expansion v1）做的四個洞察面板
（`mobaTacticInsight` / `mobaMatchOverview` / `csTacticInsight` / `csMatchOverview`）
就是這件事的載體。Challenge **不需要新造賽後分析**，只需要多喂一組
「賽前對手情報 vs 實際」的對照。
